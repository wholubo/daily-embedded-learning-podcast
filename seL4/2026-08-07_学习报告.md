# 每日嵌入式学习：seL4

## 1. GitHub 项目链接与一句话介绍

- 仓库：https://github.com/seL4/seL4 （国内可经 Gitee 镜像 https://gitee.com/mirrors/seL4 访问，镜像同步日期 2026-07-25）
- **一句话介绍**：seL4 是一个以"形式化验证正确性"为核心卖点的微内核操作系统，用约万行级的 C 代码提供进程隔离、能力机制、线程调度和快速 IPC，让安全关键系统在软件层面获得"数学上可证明"的可靠性，广泛用于国防、航空、汽车、无人机等不允许崩溃的场景。

## 2. 为什么今天选它

- **活跃度实锤**：仓库当前版本号 16.0.0-dev，而 16.0.0 正式版发布于 2026-07-22，距今不到三周，属于 BREAKING 大版本。README 上一排 CI 徽章（push、sel4test-deploy、C parser、compilation-checks、Proof Sync、Manual）说明代码、测试、证明、文档四条流水线都在持续运转。Gitee 官方镜像 2026-07-25 还在同步，说明上游提交密集。
- **16.0.0 的更新内容本身就很能说明问题**：MCS（混合关键性调度）配置在 64 位 RISC-V 上正式完成了功能正确性证明，AArch64 的 MCS 证明还在进行中；同时修复了一个 AArch32 上"用已解除映射的 frame 能力做 cache maintenance 会导致内核崩溃"的 Critical 级漏洞，和一个 x86-64 上 restore_vmx 的虚拟机逃逸漏洞。注意它的发布说明里"安全漏洞"是和"证明进展"写在一起的——这是 seL4 项目独有的工程文化。
- **工程完整度**：这不是一个玩具内核。它有 1527 个文件条目，src 与 include 各 400 多个文件，libsel4 用户侧绑定 428 个文件，tools 构建工具 97 个，还有 LaTeX 写的官方参考手册（manual 目录）、51 套平台/特性配置文件。支持 ARMv7、AArch64（含树莓派 4 的 bcm2711、树莓派 5 的 bcm2712、i.MX8/9、HiKey、OdroidC2/C4）、RISC-V 32/64、x86-64，支持 SMP 和虚拟化。
- **为什么适合软件工程师**：seL4 是嵌入式领域里"软件工程方法论密度"最高的项目之一——能力系统像权限模型、同步 IPC 像 RPC、形式化验证像把类型系统推到极致、Untyped 内存模型像手动内存池。你已有的并发、安全、构建系统知识在这里几乎全部用得上，同时又处处遇到嵌入式特有的硬约束：没有 MMU 的平台上地址空间就是物理内存、中断与时钟决定一切、上下文切换成本以周期计、内核里不允许动态分配和递归。

## 3. 项目解决的问题

- **真实场景**：航空电子、军用系统、自动驾驶、医疗设备、工业控制器里，一个内核崩溃可能导致灾难。传统做法是靠"测试充分"来建立信心，但测试覆盖不了所有输入组合。seL4 的答案是：用定理证明器（Isabelle/HOL）证明内核源码确实实现了它的规范，再证明编译后的二进制也满足同样性质，从而把"内核不会做错事"从工程承诺变成数学结论。它被 DARPA 的 HACMS 项目用来改造无人直升机（Little Bird）的飞控，把"被远程攻破"变成"被证明不可能"。
- **它解决的日常问题**：给你一个高性能的进程/组件隔离底座——不同安全等级的子系统（比如飞控核心 vs 通信模块）跑在同一个芯片上互不干扰，一个组件被攻破或崩溃不会波及其他组件。
- **与普通软件项目的差异（嵌入式特有约束）**：
  - 硬件资源：没有磁盘、没有大内存，内核里不能 malloc，能力对象的创建必须由用户预先划出内存（Untyped）。
  - 时序：中断延迟、调度延迟要可分析，MCS 模式给每个调度上下文配时间预算，防止关键任务饿死。
  - 可靠性：不能靠重启解决，所以需要形式化验证 + 最坏执行时间（WCET）分析。
  - 启动方式：没有 bootloader 帮你初始化一切，内核引导代码自己整理物理内存、建能力空间，最后把"第一进程"（rootserver）拉起来。

## 4. 技术架构分析

**总体结构**：seL4 是第二代 L4 微内核（原 L4 是 Jochen Liedtke 在 90 年代提出的"第二还是第三台机器"微内核构想）。内核里只放最少的事：线程调度、IPC、能力管理、虚拟内存管理、中断分发；文件系统、驱动、协议栈全部是用户态组件。

**仓库模块布局（基于 16.0.0-dev 真实目录树）**：

- `src/`（437 个文件）：内核 C 源码。其中 `src/kernel/` 是内核骨架——`boot.c` 引导、`thread.c` 调度与线程、`cspace.c` 能力查找、`faulthandler.c` 故障处理、`stack.c` 内核栈、`sporadic.c` 偶发任务调度支持（MCS 的一部分）；`src/object/` 是内核对象实现——`cnode.c`（能力节点）、`tcb.c`（线程控制块）、`endpoint.c`（同步 IPC 端点）、`notification.c`（异步通知）、`untyped.c`（内存重分类）、`schedcontext.c`/`schedcontrol.c`（MCS 调度对象）、`reply.c`（回复对象）、`interrupt.c`、`domain.c`、`objecttype.c`；`src/api/` 是系统调用层——`syscall.c` 分发、`faults.c` 故障消息编码；`src/arch/` 是架构相关代码（arm/32、arm/64 的 head.S、traps.S、c_traps.c、idle、vspace、registerset、fpu 等），`src/machine/` 是机器层（io、fpu、registerset、profiler）。
- `include/`（422 个文件）：内核头文件，按 arch/mode/plat 分层，`plat/machine/hardware.h` 这类文件是板级硬件抽象的关键。
- `libsel4/`（428 个文件）：用户侧系统调用接口与 ABI 绑定。`libsel4/include/sel4/sel4.h` 是总入口，往下是 `syscalls.h`、`invocation.h`、`bootinfo.h`、`faults.h`、`interfaces/sel4_client.h`（自动生成的客户端封装）。
- `tools/`（97 个文件）：构建与辅助工具。
- `configs/`（51 个文件）：平台/特性配置，例如 `AARCH64_bcm2711_verified.cmake`（树莓派 4 验证配置）、`AARCH64_MCS_verified.cmake`。
- `manual/`（48 个文件）：LaTeX 版官方参考手册源码。

**关键设计机制**：

1. **能力（capability）即一切**：线程能碰什么，取决于它持有哪些能力。内核对象（TCB、端点、能力节点、页表、Untyped 内存块）只能通过能力引用；能力存放在 CNode（能力节点）里，构成"能力空间 CSpace"。查找能力用 `lookupSlot` → `resolveAddressBits` 在能力树里逐级解析。
2. **Untyped 内存模型**：内核启动时只创建极少数对象，把剩余物理内存作为"Untyped 能力"交给 rootserver；用户需要对象时调用 retype 把 Untyped 内存"切"成具体对象。对象生命周期由用户管理，内核不做垃圾回收。
3. **同步 IPC 与异步 Notification**：endpoint 提供同步 rendezvous 式收发；notification 类似 eventfd/信号量，用于异步事件。
4. **MCS 调度**：每个调度上下文有预算（budget）和周期，内核在 `updateTimestamp`/`checkBudget` 里记账，预算耗尽触发调度；配合域调度（domain scheduler）实现混合关键性——安全关键任务有硬性时间保证，普通任务用剩余预算。
5. **故障即 IPC**：用户线程访问非法地址、触发未知系统调用、发生 VM 故障时，内核不是杀死进程，而是通过 `handleFault` 把一个"故障消息"IPC 给该线程注册的 fault handler（可以是另一个用户态组件），让策略在用户态决定。
6. **构建系统**：CMake + 各平台 cmake 配置文件，`config.cmake` 控制特性开关，`gcc.cmake`/`llvm.cmake` 选编译器；验证配置与普通配置用同一份源码，靠预处理产出"验证用源码"给证明工具链。

## 5. 源码陪读：今天只读哪几个文件

推荐按以下顺序读，总阅读量约 2000 行以内，1.5 小时内可完成：

1. **`libsel4/include/sel4/sel4.h`**（先读，10 分钟）
   阅读目标：从"用户视角"看内核暴露了什么——它只是把 `syscalls.h`、`invocation.h`、`bootinfo.h`、`faults.h`、`interfaces/sel4_client.h` 串起来的门面。搞懂这一层，你就明白"系统调用"在 seL4 里不是一个 open/read/write 列表，而是一套能力调用（invocation）协议。
2. **`src/api/syscall.c`**（核心，40 分钟）
   阅读目标：看系统调用怎么分发。重点看 `handleSyscall` 的入口、`handleInvocation`（isCall/isBlocking/canDonate 参数的含义）、`handleRecv`/`handleReply`/`handleYield`、`handleInterruptEntry`（中断入口里 `checkInterrupt` → `schedule` → `activateThread` 的路径，以及 MCS 下的 `updateTimestamp`/`checkBudget`）。这是整个内核的"API 网关"。
3. **`src/kernel/cspace.c`**（20 分钟）
   阅读目标：看能力查找的真实实现——`lookupCap` → `lookupSlot` → `resolveAddressBits` 如何沿着 CNode 树解析一个 32/64 位能力指针，如何返回 `lookup_fault`（InvalidRoot、MissingCapability、DepthMismatch、GuardMismatch，这些错误码在 `faults.c` 里用 compile_assert 和用户侧 ABI 对齐）。你会直观理解"能力树解析"就是一次受控的指针解引用。
4. **`src/kernel/thread.c`**（30 分钟）
   阅读目标：看调度器本体——`schedule` → `chooseThread` → `switchToThread`，`setPriority`/`setMCPriority`、`setDomain`、`scheduleTCB`、`possibleSwitchTo`、MCS 的 `postpone`/`setNextInterrupt`。体会"调度决策"与"上下文切换"是如何分离的。
5. **`src/kernel/boot.c`**（可选进阶，30 分钟）
   阅读目标：看一个微内核怎么"从零起来"——`merge_regions`/`reserve_region` 整理物理内存，`create_root_cnode`/`create_domain_cap`/`create_ipcbuf_frame_cap`/`create_untypeds` 建立初始对象，`create_idle_thread`、`init_sched_control`、`clock_sync_test`，最后 `bi_finalise` 把 bootinfo 交给 rootserver。这是嵌入式"上电即确定性初始化"思维的典型教材。

## 6. 核心模块/函数导读

1. **`handleInvocation`（src/api/syscall.c）**：系统调用的总闸。调用者通过某个能力发起 invocation（比如"往这个 endpoint 发消息""把这个能力复制到那个 CNode"），`handleInvocation` 先解析能力指针、做权限校验，再按对象类型分发到 `invokeXxx`。对应软件工程概念：一个按 resource + action 路由的 API 网关，但这里的"鉴权"不是查数据库，而是看调用者手里有没有那个能力。
2. **`lookupCap`/`lookupSlot`/`resolveAddressBits`（src/kernel/cspace.c）**：能力解析三件套。`lookupCap` 是入口，`lookupSlot` 取出线程的 CNode（`TCB_PTR_CTE_PTR(thread, tcbCTable)`），`resolveAddressBits` 沿能力树逐级下钻。性能上这是热路径——每次系统调用、每次 IPC 都要走一遍，所以实现里全是 `unlikely` 分支和位运算。对应：DNS 解析/路由表查找，但发生在内核态、纳秒级预算内。
3. **`schedule`/`chooseThread`/`switchToThread`（src/kernel/thread.c）**：调度器三函数。`schedule` 决定"下一个该跑谁"（可能什么都不做，因为当前线程仍可运行），`chooseThread` 从就绪队列里挑，`switchToThread` 做真实的上下文切换。MCS 下还有 `postpone`（预算耗尽时把调度上下文推迟到下一周期）和 `setNextInterrupt`（按最近截止时间设置内核定时器）。对应：操作系统的进程调度器，但对象是"调度上下文"而非进程，且要满足可证明的最坏情况响应时间。
4. **`create_root_cnode`/`create_untypeds`/`bi_finalise`（src/kernel/boot.c）**：引导期三部曲。内核在启动时手工搭建初始能力空间（`create_root_cnode` 里用 `CONFIG_ROOT_CNODE_SIZE_BITS` 决定能力树大小、guard 位怎么分配），把剩余内存打包成 Untyped 能力（`create_untypeds`），最后 `bi_finalise` 把 bootinfo 结构交给第一个用户进程。对应：容器镜像的 init 进程 + 云平台的"初始租户资源配置"，但这一切发生在几十毫秒的上电窗口内，没有热插拔和动态发现。
5. **`updateTimestamp`/`checkBudget`（MCS，syscall.c/thread.c 中的调度记账）**：混合关键性调度的"心跳"。每次内核入口更新时间戳，检查当前调度上下文的预算是否耗尽，预算没了就触发调度。对应：看门狗/配额系统——但粒度是微秒级、且在中断上下文里同步执行，任何一处溢出或绕回（wrap-around）都是漏洞。
6. **`resetUntypedCap`/`alignUp`（src/object/untyped.c）**：内存重分类的底层。retype 一个 Untyped 能力时，内核按对齐要求把内存切块，原能力被重置。对应：内存池分配器，但"分配"是显式的、一次性的、可撤销的（revoke 能力可递归收回），没有 malloc/free 的隐式生命周期。

## 7. 软件工程师类比解释

1. **能力（capability）≈ AWS IAM 权限/访问令牌**：你持有某个能力，就能对该对象做对应操作；内核不关心"你是谁"，只关心"你手里有什么"。令牌可以传递、可以派生（derive 出权限更小的版本），吊销通过 revoke 递归实现。
   - 局限：IAM 是集中式授权服务、有身份概念；seL4 的能力是分布式持有的内核对象，没有"用户/角色"这种主体抽象，也没有审计日志。
2. **微内核 + 用户态驱动 ≈ 微服务架构**：驱动、文件系统、协议栈都是独立用户态组件，通过 IPC 通信，一个崩溃不影响内核。内核像 API 网关/控制平面，组件像服务。
   - 局限：没有网络边界、没有独立部署与滚动升级（在 MCS 之前甚至没有动态加载）；每次 IPC 都有真实的上下文切换与消息拷贝成本，服务间调用在微服务里是毫秒级，在 seL4 里是以百纳秒计的同步调用。
3. **形式化验证 ≈ 把类型系统/静态分析推到极致**：Rust 的类型系统在编译期排除内存错误，seL4 的 Isabelle/HOL 证明在构建期排除"实现违反规范"的所有可能执行路径。2014 年它还把证明延伸到了编译后的二进制。
   - 局限：证明的是"实现符合规范"，规范本身写错了照样错；硬件（cache、MMU、中断控制器）行为是信任根，证明不了芯片；证明成本极高（最初约 20 万行证明对应约 8700 行 C，多年人月投入），普通产品团队负担不起。
4. **同步 IPC（endpoint）≈ RPC/消息队列**：跨组件通信原语，send/recv/reply 成对出现，调用方可以阻塞等待回复。
   - 局限：seL4 的 endpoint IPC 是无缓冲的同步 rendezvous——没有队列、没有超时、没有重试、没有序列化，双方必须同时到场；死锁与背压要应用层自己设计，这跟带缓冲、带超时的消息队列差别很大。
5. **Untyped 内存 + retype ≈ 手动内存池/Rust 所有权**：内核不预先创建对象，用户从 Untyped 里"开垦"；retype 后原 Untyped 能力消失，资源所有权线性转移，很像 Rust 的 move 语义；能力可以 mint/derive 出受限副本，又像 Rust 的 &mut 借用。
   - 局限：没有编译器帮你检查借用规则，违反能力语义的错误要到运行时（sel4test 或验证证明）才暴露；而且这是"内存即对象"的底层资源模型，不是语言层面的抽象。

## 8. 今日 10 个嵌入式概念卡片

1. **微内核（microkernel）**：一句话：只在内核态保留调度、IPC、能力、内存映射等最小功能，其余全放用户态。软件工程类比：控制平面与数据平面分离的网关。常见场景：安全关键系统的隔离底座。坑点：微内核不是"性能差"的同义词——seL4 的 IPC 以百纳秒计，瓶颈在消息拷贝和缓存，不在架构。
2. **能力（capability）**：一句话：一种不可伪造的、可传递的权限凭证，持有即有权。类比：Bearer Token。场景：跨安全等级组件的资源授权。坑点：能力泄漏等于权限泄漏，必须设计好分发与 revoke 策略。
3. **CNode / CSpace（能力空间）**：一句话：存放能力的内核对象，按 radix+guard 组织成树，能力指针就是树里的路径。类比：带权限的虚拟文件系统/路由表。场景：系统调用前的权限解析。坑点：能力树深度和 guard 位设计直接影响解析开销与灵活性，改配置要重新验证。
4. **Untyped 内存与 retype**：一句话：启动时把空闲物理内存作为"未定型"能力交给用户，用户按需 retype 成具体对象。类比：内存池 + Rust 所有权。场景：内核对象创建的确定性管理。坑点：没有 GC，忘了 revoke 就泄漏；对齐错误会直接失败。
5. **同步 IPC（endpoint）**：一句话：无缓冲的 rendezvous 式消息传递，收发双方同时到场才完成。类比：无队列的 RPC。场景：组件间高频小消息。坑点：接收方不在场时发送方必须阻塞或换非阻塞调用，容易死锁。
6. **Notification（异步通知）**：一句话：一种轻量异步信号对象，类似 eventfd，用于"事件发生了"而不带大数据。类比：信号量/事件循环的唤醒源。场景：驱动中断事件到用户态组件。坑点：通知只代表"发生过"，不代表"几次"，需要配套计数语义的设计。
7. **调度上下文与预算（MCS budget）**：一句话：MCS 模式下每个调度上下文有周期和预算，预算耗尽即被换出，保证最坏情况响应时间可分析。类比：SLA 配额/限流器。场景：混合关键性系统（飞控+通信）。坑点：预算太小导致频繁调度抖动，预算太大失去时序隔离。
8. **域调度（domain scheduler）**：一句话：把 CPU 时间切成固定时间片（domain），各域按静态轮转，域内再按优先级调度。类比：时间分片的多租户调度。场景：不同安全等级任务的时间隔离。坑点：静态轮转灵活性低，不适合负载剧烈变化。
9. **形式化验证（formal verification）**：一句话：用定理证明器证明源码（乃至二进制）满足规范，覆盖所有输入。类比：类型系统+模型检查的终极形态。场景：不允许崩溃的国防/航空系统。坑点：验证的是规范下的行为，规范错误、硬件错误不在证明范围内；成本极高。
10. **故障即 IPC（fault as IPC）**：一句话：用户线程出错时，内核把故障打包成消息发给该线程的 fault handler，策略由用户态决定。类比：把 SIGSEGV 变成一次可编程回调。场景：组件崩溃隔离、故障恢复。坑点：fault handler 本身出错会递归触发，要设计兜底。

## 12. 工程点评

- **可维护性**：源码分层非常清晰（src/kernel、src/object、src/api、src/arch、libsel4），命名规范统一，但学习曲线陡峭；发布说明有严格的兼容性分级（SOURCE/BINARY/BREAKING），CHANGES.md 要求每个改动登记，工程纪律一流。
- **可移植性**：架构/模式/平台三层抽象（arch/mode/plat），一套源码支持 ARMv7、AArch64、RISC-V、x86-64；新增平台主要是写板级硬件文件和 cmake 配置。移植成本在微内核里算低的，但每个新平台都要重新跑验证，验证成本高。
- **可靠性**：这是项目的立身之本——形式化证明 + 二进制验证 + WCET 分析 + 独立的 sel4test 测试套件 + 漏洞披露流程。16.0.0 里连"缓存维护操作未检查映射状态"这种边角路径都被证明过程逼出来并修复，说明验证确实在反哺工程质量。
- **可测试性**：sel4test 是官方测试框架，跑在 QEMU 和真实硬件上；内核内置 benchmark（tracepoints、utilisation tracking），profile 工具齐全。测试与验证双轨并行。
- **量产/运维**：生态有 CAmkES 和新的 Microkit 静态组件框架，适合构建确定性的量产系统；但驱动、文件系统都要用户态自备或从生态移植，团队需要能读懂证明工具链的人，量产的隐性成本远高于普通 RTOS。许可证上内核是 GPL-2.0-only、libsel4 是 BSD-2-Clause，商业闭源使用需要仔细评估内核部分的传染性（业界通常的做法是内核之外的用户态组件用自己的许可证）。

## 13. 明天可以延展的方向

1. **seL4 Microkit / CAmkES 组件框架**：看"静态组件系统"如何把多个 seL4 组件+连接器编译成确定性系统镜像——这是从"读懂内核"走向"用它做产品"的桥梁。
2. **sel4test 与验证基础设施**：研究官方测试套件如何组织，以及 Isabelle/HOL 的 C 解析器（C parser）如何把 C 源码变成可证明的模型——理解"验证工程"本身也是一门工程。
3. **横向对比内核设计**：把今天学的 seL4（微内核+能力+验证）与之前学过的 FreeRTOS、Zephyr、ThreadX 的宏内核/模块化设计对比，重点比较：内存保护模型、IPC 性能、调度可分析性、认证路径——这份对比表可以作为你选择产品内核的决策工具。
