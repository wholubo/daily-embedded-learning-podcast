# 每日嵌入式学习：VESC

> 学习日期：2026-08-06 ｜ 目标读者：有软件工程背景、正在转向软硬一体产品工程的工程师

## 1. GitHub 项目链接与一句话介绍

- 仓库链接：https://github.com/vedderb/bldc
- **一句话介绍**：VESC 是 Benjamin Vedder 从大学毕设一路做成开源电动滑板与机器人行业标配的电机控制器固件，在 STM32 上同时实现了方波 BLDC 与矢量 FOC 两套驱动，配套 VESC Tool 上位机，是开源世界里最完整的"电机控制产品级固件"。

## 2. 为什么今天选它

- **活跃度**：仓库约 3300 star，GPL-3.0 协议，今天（2026-08-06）还有提交：合并 lispBM 更新、修复 const 堆保存逻辑、精简旧终端命令、PR 减少 flash 占用。一个从 2014 年前后持续迭代到今天、横跨近十年的固件项目，生命力极强。
- **工程完整度**：这不是一个 demo 或库，而是一整条产品链路——ChibiOS RTOS、双电机支持、13 种编码器驱动、CAN/USB/UART/BLE 四路通信、独立引导加载器、flash EEPROM 仿真、约 35 种故障码、上位机生态（VESC Tool 可刷固件、调参、实时画图）。
- **学习价值**：它是"一个人把毕设做成行业标准"的范本。`motor/mcpwm_foc.c` 单文件 5421 行，是硬实时控制代码的极致形态，恰好能回答软件工程师最该问的问题：在 25 微秒的预算里，代码该怎么组织。
- **与历史选题不重复**：VESC 是 Vedder 自研代码库，与之前讲过的 SimpleFOC（Arduino FOC 库）、Bluejay/AM32（ESC 固件）没有同源关系，选题方向（电机控制）有延续性但代码与架构完全不同。

## 3. 项目解决的问题

- **真实场景**：电动滑板、电动自行车、机器人关节、鼓风机、电动冲浪板。用户要的不是"让电机转"，而是"让电机像一个可控的扭矩源"：踩下油门要多少扭矩就给多少，刹车要能回收能量，堵转要立刻保护，掉电要保存配置。
- **比普通软件多了什么**：
  - 功率级：三相 MOSFET 桥 + 栅极驱动（DRV 芯片），固件要管死区时间、防止上下桥直通；
  - 电流采样：相电流经采样电阻和运放放大后进 ADC，采样时刻必须和 PWM 载波同步，否则采到开关噪声；
  - 时序约束：FOC 电流环在一个中断里算完，约 25 微秒预算，PWM 频率最高约 40 kHz（通过分频器可解耦到 100 kHz）；
  - 可靠性约束：过压、欠压、过流、MOSFET 过热、电机过热、编码器断线都要有故障码和降级行为；配置要能在掉电瞬间安全写入 flash；
  - 类比一句话：普通软件关心"逻辑对不对"，电机固件关心"在 25 微秒内算完、并且十年不出错"。

## 4. 技术架构分析

基于公开源码梳理（均为仓库内真实文件）：

- **分层结构**：
  1. 硬件抽象层：`hwconf/hw.h` 定义引脚、电压分压、电流放大系数等宏，每块板卡一个 conf 文件（如 VESC 100/250），`make <目标板>` 选择编译目标，支持几十种板卡；
  2. RTOS：内置 ChibiOS 3.0.5，负责线程调度、虚拟定时器、信号量；
  3. 电机控制层：`motor/mcpwm.c`（3021 行，方波 BLDC + 霍尔）、`motor/mcpwm_foc.c`（5421 行，矢量 FOC），上层用 `motor/mc_interface.c`（3087 行）做统一门面，屏蔽两套实现的差异，并支持双电机切换；
  4. 应用层：`applications/app.c` 把外部输入（遥控器 PPM、电位器 ADC、UART、CAN、NRF 蓝牙、脚蹬 PAS、甚至 Wii 手柄）映射成电流/速度/位置控制；
  5. 通信层：`comm/packet.c` 帧协议 + `comm/commands.c` 命令分发 + `comm/comm_can.c`（CAN 多机）+ `comm/comm_usb.c`；
  6. 上位机：VESC Tool（Qt 写），走同一套 packet 协议，刷固件、调参、实时画图。
- **启动流程（main.c）**：上电先处理 `crash_info`（.noinit 段内存，跨复位保留，记录启动次数、复位原因、停机原因）→ 初始化 ChibiOS 与 HAL → 关断使能引脚防浮空大电流 → 初始化内存池、事件、定时器、GPIO、中断 → 加载配置（flash EEPROM 仿真）→ 用 STM32 硬件 CRC 校验整个 flash，损坏则红灯闪烁死循环 → 检查"是否把 HALL2 引脚短接到 SWCLK 调试引脚"（一个硬件技巧：用户短接这两个脚再上电就恢复出厂配置）→ 初始化电机接口、命令服务、USB、应用层、CAN、NRF → 创建三个线程（LED 线程按故障码闪烁、周期线程回传转子位置并做 HSI 振荡器温度补偿、低优先级 flash 完整性巡检线程）→ 配置超时保护（油门超时刹车、急停开关）→ 通过 CAN 广播上线帧。
- **控制环路**：电流环在 ADC/PWM 中断里跑（`mcpwm_foc_isr_motor` → `control_current`），做 Clarke/Park 变换、dq 轴 PI、逆 Park + SVPWM 生成三相占空比；速度环、位置环在 RTOS 定时器/线程里跑。FOC 计算约 25 微秒，`FOC_CONTROL_LOOP_FREQ_DIVIDER` 让控制环每 N 次中断执行一次，从而把 PWM 频率与计算频率解耦（注释里明确写了 100 kHz PWM + 分频 3 的用法）。
- **传感器与无感方案**：`encoder/` 目录下 13 种编码器驱动（ABI 正交、AS5047 SPI 磁编、BiSS-C、旋变、正弦余弦、PWM 编码等）可插拔；无感模式用反电动势观测器（`mcpwm_foc_get_phase_observer`），低速/零速用高频注入 HFI（`hfi_update`），FOC 内部同时维护"观测器角度、编码器角度、霍尔角度"三套角度并互相校验（主循环里就读取观测器与编码器的角度差）。
- **配置系统**：`datatypes.h` 里的 `mc_configuration`/`app_configuration` 巨型结构体（foc_current_kp/ki、foc_motor_r/l、foc_motor_flux_linkage、foc_sl_*、foc_hfi_*、hall_table[8] 等），结构体自带 crc 字段做完整性校验；通过 `ld_eeprom_emu.ld` 链接脚本把 MCU 内部 flash 模拟成 EEPROM 使用（`flash_helper.c` 读写、擦除、跳转引导加载器）；所有配置下发前经过硬件限幅（`commands_apply_mcconf_hw_limits`），防止把电流上限调到硬件承受不了。
- **通信/升级**：`packet.c` 帧格式——起始字节 2/3/4（分别表示 1/2/3 字节长度），payload，CRC16，停止字节 3；流式解析器逐字节喂入、失步自动重同步。固件升级走独立仓库 `vedderb/bldc-bootloader`，可用 VESC Tool 通过 USB 刷写，也可 STLink 直刷。
- **脚本化扩展**：固件内置 lispBM（嵌入式 Lisp 解释器，今天刚合并更新），用户可以在固件里写自定义控制逻辑；还支持把自定义 QML UI 编译进固件，在 VESC Tool 里显示专属界面。

## 6. 核心模块/函数导读

- **`control_current(motor, dt)`（mcpwm_foc.c）**：FOC 电流环本体，在中断上下文执行，dq 轴 PI 控制。它是整个固件的"心脏跳动"——所有速度环、位置环的输出最终都变成它的电流给定。工程角色：硬实时热点路径，约 25 微秒预算；旁边有 `FOC_PROFILE_*` 宏可以按行记录每条代码的执行时间，把"性能剖析器"直接做进中断里。
- **`mcpwm_foc_set_current / mc_interface_set_current`**：对外统一的电流控制入口。前者是 FOC 内部实现，后者是门面，负责加锁、选电机、转发给 FOC 或方波实现。工程角色：API 边界，所有上位机命令和 app 输入都汇聚到这里。
- **`commands_process_packet`（commands.c，2556 行）**：命令分发中心，按 COMM_PACKET_ID 路由到"读配置、写配置、控制电机、实时画图、刷固件"等动作，相当于固件里的 HTTP 路由表。`commands_printf` 把日志同时送到 USB/UART/CAN，`commands_send_plot_points` 支持向 VESC Tool 实时推送曲线。
- **`conf_general_store_mc_configuration` + `flash_helper.c`**：配置持久化。用 `ld_eeprom_emu.ld` 把内部 flash 模拟成 EEPROM，写入带 CRC16；`flash_helper_verify_flash_memory` 用 STM32 硬件 CRC 单元（CRC->DR 寄存器）整片校验，损坏就拒绝启动。工程角色：掉电安全的最后防线。
- **`app_set_configuration` + `app_disable_output`（app.c）**：输入映射与安全关断。`app_to_use` 决定当前用哪种输入（PPM/ADC/UART/NUNCHUK/PAS/NRF/CUSTOM）；`app_disable_output` 用 ChibiOS 虚拟定时器实现"禁输出 N 毫秒"——遥控器断连时把电机输出关掉，这是产品安全设计，不是功能。
- **`main.c` 的 crash_info 与故障码体系**：`.noinit` 段内存跨复位保留启动次数与复位原因（FAULT_CODE_BOOTING_FROM_WATCHDOG_RESET 就是检测到看门狗复位）；约 35 种故障码从过压、欠压、过流、MOSFET 过热到编码器 SPI 断线；LED 线程用"红灯闪 N 次"编码故障码，维修现场不用电脑就能读故障。

## 7. 软件工程师类比解释

1. **mc_interface 门面 ≈ 统一支付网关**：上层（app、命令、CAN）只调 `mc_interface_set_current`，内部路由到 FOC 或方波实现，就像支付网关后面接多家银行。局限：这里还夹着 RTOS 线程切换、中断优先级和全局锁，不是纯接口抽象，调用时机错了会出时序问题。
2. **packet.c 流式解析 ≈ TCP 粘包拆包 + 帧同步**：逐字节喂入、靠起始/停止字节找边界、CRC16 验错、失步后滑动重同步，等价于你熟悉的 LengthFieldBasedFrameDecoder。局限：MCU 上没有堆、没有对象池，缓冲区是固定数组，长度上限写死在宏里，解析器要自己管理 memmove。
3. **commands_process_packet ≈ REST 路由/消息总线**：COMM_PACKET_ID 就是 API path，payload 是紧凑二进制 body。局限：没有 HTTP 语义，没有版本协商，字段增删全靠结构体版本和手工兼容，这正是嵌入式协议最常见的坑。
4. **EEPROM 仿真 + CRC16 ≈ 带校验的数据库记录**：配置结构体像一行带 checksum 的记录，写入要保证"要么完整、要么可检测损坏"。局限：flash 有擦写次数上限、没有事务并发控制，写一半掉电只能靠校验发现后回退默认值。
5. **电流环 ISR ≈ 高频交易的最内层热点路径**：25 微秒预算、无锁、无动态分配、无日志，和交易系统里纳秒级 tick 处理一样是"性能即正确性"。局限：MCU 单核，靠关中断保证原子性，加一行 printf 就可能让电流环超时，调试手段极其受限。
6. **故障码 + LED 闪烁 ≈ HTTP 状态码 + 结构化日志**：一个数字编码一类故障，方便现场定位。局限：只有一颗 LED，信息量极小，深层诊断还得靠 VESC Tool 连电脑。

## 8. 今日 10 个嵌入式概念卡片

1. **FOC 矢量控制**：把三相电流变换到随转子旋转的 dq 坐标系，让"扭矩"和"磁场"解耦成两个独立的 PI 回路。类比：把混在一起的请求按业务维度拆分治理。场景：无刷电机高性能驱动。坑点：依赖转子角度，角度不准一切白搭。
2. **Clarke/Park 变换**：先把三相 abc 电流投影成两相 αβ，再旋转到 dq。类比：坐标系变换像"换视角看同一份数据"。场景：FOC 数学基础。坑点：浮点误差会累积，角度查表与插值要小心。
3. **SVPWM 空间矢量调制**：用相邻电压矢量的时间加权合成任意方向电压矢量（`update_valpha_vbeta`）。类比：用两个离散档位 PWM 出任意占空比，像用色块抖动逼近渐变色。场景：三相桥占空比生成。坑点：调制比超限会进入过调制区，波形畸变。
4. **PWM 同步电流采样**：电流采样点对齐到 PWM 载波中心，避开开关噪声。类比：在数据库低峰期跑批任务，避开高峰抖动。场景：相电流 ADC 采样。坑点：采样时刻偏一点，反馈噪声就爆表。
5. **死区时间**：上下桥切换之间插入的"两边都关断"时间，防止直通短路。类比：发布时先摘流量再切换，避免新旧同时在线。场景：任何三相桥驱动。坑点：死区会引入电流畸变，需要软件补偿（VESC 有专门的 deadtime 计算函数）。
6. **反电动势观测器（无感）**：用电机模型从电压电流估算转子角度，省掉编码器。类比：用系统状态估计代替传感器，像用卡尔曼滤波预测延迟数据。场景：低成本无感驱动。坑点：零速附近反电动势为零，必须配合高频注入。
7. **高频注入 HFI**：在低速/零速时注入高频电压，利用磁凸极性定位转子。类比：用 ping 包探测不可见网络拓扑。场景：零速无感启动。坑点：注入幅值/频率要权衡噪声与鲁棒性，参数极多（foc_hfi_* 一整套配置）。
8. **EEPROM 仿真**：把内部 flash 当 EEPROM 用，配置带 CRC 落盘。类比：把配置当数据库行，带校验和防损坏。场景：掉电保存用户设置。坑点：flash 擦写寿命有限、写一半掉电会损坏，必须校验+回退。
9. **看门狗与崩溃诊断**：.noinit 内存跨复位保留复位原因，看门狗复位有专门故障码。类比：应用崩溃后留下的 core dump 与启动计数。场景：现场设备故障排查。坑点：.noinit 段内容在断电后会丢失，只能覆盖"软复位"场景。
10. **硬件限幅（hw limits）**：上位机下发的任何配置都要过一遍硬件能力边界检查（`commands_apply_mcconf_hw_limits`）。类比：服务端校验不能信客户端传参。场景：防止用户把电流上限调爆硬件。坑点：限幅是"最后一道闸"，不是安全设计本身。

## 9. 30～60 分钟动手任务

**步骤**：

4. 用 Python 实现帧编码器：payload + CRC-16/CCITT-FALSE（多项式 0x1021，初值 0，查表法），对照 `util/crc.c` 的 `crc16_tab` 表头（0x0000, 0x1021, 0x2042...）验证你的实现和 C 代码一致；
5. 试着用 gcc 编译 `tests/packet_recovery/main.c`（连同 util 下相关源文件），在宿主机上跑通它的协议恢复测试。

**验收标准**：能默写启动流程 8 步；能画出 packet 帧格式；Python 编码器对任意 payload 算出的 CRC16 与 C 查表实现一致；若编译成功，packet_recovery 测试通过。

## 10. 3 道深度追问题

1. **时序**：为什么 FOC 电流环必须放在 ADC 中断里，而不是放进 RTOS 高优先级线程？如果把 `FOC_CONTROL_LOOP_FREQ_DIVIDER` 设成 3（PWM 提到 100 kHz、电流环每 3 次中断执行一次），对电流环带宽、MOSFET 开关损耗、ADC 采样噪声各有什么影响？
2. **软件视角转嵌入式**：你在后端给配置热更新时习惯加 schema 版本和迁移脚本。VESC 的 `mc_configuration` 是固定结构体 + CRC16，固件升级后结构体字段漂移会怎样？为什么它需要 confgenerator 默认值回退和"配置重置"机制？在不能联网 OTA、不能跑迁移脚本的现场，你会怎么设计兼容？
3. **并发/资源**：双电机模式下 `mc_interface_select_motor_thread` 用全局变量标记"当前电机"，上位机线程和 LED 线程同时读状态时存在竞态。VESC 用 `mc_interface_lock` 缓解，请分析这个锁的粒度问题：为什么锁不能解决"ISR 里读电机状态"的并发？如果让你重构，你会用什么方案？

## 11. 今日复盘问题

如果让你把一个"毕设级"固件变成能卖钱的产品，你会先补哪三件事：文档、自动化测试、还是故障恢复？注意 VESC 自己的选择是"先堆功能、再回头清理"——看它最近的提交：精简终端命令、压缩 flash 占用、合并 lispBM。这个顺序对吗？

## 12. 工程点评

- **可维护性**：目录分层清晰（motor/comm/encoder/app/util），但单文件超大（mcpwm_foc.c 5421 行、commands.c 2556 行）、全局状态多，属于"天才单干"风格，靠注释和纪律维持，协作成本高。
- **可移植性**：hw.h + 每板 conf 的硬件抽象可编译几十种板卡，是亮点；但深度绑定 STM32F4 和 ChibiOS 3.0.5（老版本 RTOS），换 MCU 平台基本等于重写电机层。
- **可靠性**：故障码体系（约 35 种）、flash 硬件 CRC 整片校验、看门狗复位检测、油门超时保护、.noinit 崩溃信息——现场可运维性极强。
- **可测试性**：tests/ 有宿主机测试（角度、浮点序列化、协议恢复），说明作者意识到核心算法要能在 PC 上跑；但控制环路本身没有自动化测试，靠 VESC Tool 当"活体测试台"，这是单人项目的现实妥协。
- **量产/运维**：VESC Tool 远程调参、刷固件、实时画图，CAN 多机编址与转发，生态成熟到养活了一整条电动滑板供应链；但 GPL-3.0 协议对想闭源商用的公司不友好，这也是很多商业产品绕开它的原因。

## 13. 明天可以延展的方向

1. **对比学习引导加载器**：读 `vedderb/bldc-bootloader`，把它和之前学过的 MCUboot、wolfBoot 的升级策略（双 bank、签名校验、回滚）做对比，理解"产品级 OTA"的取舍。
2. **深挖 FOC 数学与整定**：用 Python 复现 Clarke/Park 变换和 `control_current` 的 dq 轴 PI，再用 `conf_general_calc_apply_foc_cc_kp_ki_gain` 的思路（给定时间常数算 kp/ki）做一次电机参数整定实验。
3. **嵌入式脚本引擎**：看 lispBM 如何塞进固件（对比 MicroPython 和 JS 引擎的 footprint 与实时性代价），思考"给嵌入式产品留脚本后门"的工程取舍。
