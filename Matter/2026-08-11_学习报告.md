# 每日嵌入式学习：Matter（connectedhomeip）

## 1. GitHub 项目链接与一句话介绍

- 仓库链接：https://github.com/project-chip/connectedhomeip
- **一句话介绍**：Matter（曾用名 Project CHIP）是一套由连接标准联盟 CSA 推动、基于 IP 的智能家居应用层互联标准及其开源参考实现，让不同品牌的灯、锁、传感器、音箱之间像网页走 HTTP 一样说同一种"设备语言"，实现跨生态互通。

## 2. 为什么今天选它

- **活跃度**：仓库创建于 2020 年 3 月，当前约 8.9k star、2.4k fork，2026 年 8 月 11 日当天仍有提交；最新发布版本 v1.5.1.0（2026 年 4 月 13 日发布）。背后由 Google、Apple、Amazon、Samsung 等巨头组成的 CSA 联盟共同维护，是智能家居领域事实上的互联标准。
- **工程完整度**：这不是一个玩具项目，而是一套完整的分层协议栈参考实现：数据模型、交互协议、安全会话、可靠消息、多平台移植层、OTA、诊断、CI 测试矩阵（单元/集成测试、Cirque 多节点测试、QEMU 测试、夜间测试），并配套 ZAP 配置代码生成工具链。
- **学习价值**：它是极少数"同一份 C++ 代码既能编译到 Linux 主机上跑，也能交叉编译到 ESP32、nRF52840、STM32 这类 MCU 上跑"的代码库。软件工程师可以先用自己熟悉的 Linux 环境把整个协议栈跑通，再逐步体会 MCU 上的内存、时序、功耗约束，正好契合"从纯软件到软硬一体"的学习路径。
- **与历史项目的区分**：此前学过 OpenThread（Thread 网络协议栈）、NimBLE（BLE 协议栈）、ESPHome/Tasmota（设备固件），但 Matter 是站在它们之上的"应用层互联标准 + 认证体系"，角度完全不同，且不在历史去重列表中。

## 3. 项目解决的问题

**真实产品场景**：智能家居碎片化。买回家的灯、锁、传感器各自绑定自己的生态（Alexa、Google Home、Apple HomeKit、SmartThings），互相不连通；厂商想进入多个生态，就得为每个生态各做一套适配和认证。Matter 的答案是定义一个统一的应用层标准：设备厂商只实现一次，就能被任何支持 Matter 的生态控制；用户的数据和授权留在本地，不依赖任何单一云厂商。

**和普通软件项目相比，多了哪些约束**：

- **硬件约束**：协议栈要能跑在只有几百 KB RAM、1～2 MB Flash 的 MCU 上。代码里处处体现这种"省着花"的思维，比如 `src/lib/core/CHIPConfig.h` 中 `CHIP_CONFIG_SECURE_SESSION_POOL_SIZE` 直接由 `CHIP_CONFIG_MAX_FABRICS * 3 + 2` 在编译期算出——会话对象是编译期定长的对象池，而不是运行时 `new` 出来的堆对象，避免动态内存碎片。
- **资源约束**：报文要尽量小，所以自研了紧凑的 TLV 二进制编码；配对码只有 11 位十进制数（约 36 bit 熵），安全设计必须假设口令低熵。
- **时序约束**：没有操作系统兜底时，握手超时、重传间隔都要显式计算。例如 `CASESession.h` 里的 `ComputeSigma1ResponseTimeout`，要根据对端上报的 MRP（可靠消息协议）参数来推算超时，而不是拍脑袋定一个固定值。
- **可靠性约束**：设备可能随时掉电、断网、被恢复出厂设置；配网中断、消息丢失、重放攻击都要在应用层处理（MRP 重传 + 消息计数器防重放）。
- **安全约束**：量产设备要烧录 DAC 设备认证证书；配网用 PAKE 口令协议；运行期会话用证书双向认证；访问控制（ACL）默认拒绝，授权完全由用户控制。

## 4. 技术架构分析

**分层结构**（据仓库 README 与公开文档）：自顶向下依次是 Application 应用层（灯的开关、调色等业务逻辑）→ Data Model 数据模型（Cluster / Attribute / Command / Event）→ Interaction Model 交互模型（Read / Write / Invoke / Subscribe 四种操作）→ Action Framing + Security（动作帧与安全层，消息签名、会话密钥）→ Message Framing + MRP（消息帧与可靠消息协议）→ Transport（TCP/UDP over IPv6，配网阶段可走 BLE 承载）→ IP 层（IPv6、6LoWPAN，底下是 Thread 802.15.4 或 Wi-Fi）。

**配网与控制主流程**（以"手机把一盏灯加入家庭并控制它"为例）：

1. 设备上电，未配网时进入 commissioning 模式：BLE 广播或通过 DNS-SD 被控制器发现（仓库里能看到 `src/app/server/CommissioningWindowManager.cpp`、`ThreadRendezvousAnnouncement.cpp`、Linux 平台下的 `NFCCommissioningManagerImpl.cpp`——连 NFC 碰一碰配网都有实现）。
2. 控制器读取用户扫描二维码得到的配对码（setup code，示例里默认 20202021）。
3. 双方跑 PASE（SPAKE2+ 口令认证密钥交换）建立临时加密会话，防止配对码在空气中被离线爆破。
4. 在 PASE 会话内下发 Wi-Fi/Thread 网络凭据、完成设备证书签发，设备正式加入一个 Fabric（信任域）。
5. 运行期改用 CASE（Sigma 协议）做证书双向认证，建立长会话。
6. 控制命令经 Interaction Model 的 Invoke 到达对应 Cluster 处理器（如 OnOff），落到业务回调，最终驱动 GPIO/PWM。

**配置与构建系统**：用 ZAP 工具维护 `.zap` 配置文件描述设备支持哪些 Cluster，然后代码生成（codegen）产出框架代码，手写业务逻辑填充其中；构建用 GN + Ninja（`scripts/activate.sh` 创建 Python 虚拟环境）。这种"配置驱动代码生成"的模式在 MCU SDK 里非常典型。

**平台抽象**：`src/platform/<平台>/` 目录按平台隔离差异，Linux 平台基于 GLib 事件循环（`PlatformManagerImpl.h` 里能看到 `GLibMatterContextInvokeSync`），把事件投递到主循环线程；持久化用 KVS 键值存储（Linux 下是 `CHIPLinuxStorageIni.cpp`，落盘为 ini 文件）。其余如 OTA（`OTAImageProcessorImpl.cpp`）、诊断、故障注入（clusters 列表里能看到 fault-injection-server）都是为量产设计的模块。

## 5. 源码陪读：今天只读哪几个文件

1. `examples/lighting-app/linux/main.cpp` — 应用入口。阅读目标：看 `main()` 和 `ApplicationInit()` 如何把"Matter 协议栈"和"业务逻辑"粘起来；注意 `emberAfOnOffClusterInitCallback` 里的 `emberAf` 前缀——这是从 Zigbee Ember 时代继承下来的命名，Matter 的 Cluster 代码生成体系（ZAP）正是从 Nest 的 Zigbee 工具链演化来的（TLV.h 文件头版权还写着 Nest Labs 2013-2017，是这段历史的证据）。
2. `src/app/server/Server.cpp` — 协议栈总装车间。阅读目标：从第 230 行 `Server::Init` 开始，看整个协议栈的初始化顺序：事件循环、DNS-SD、commissioning 窗口、各子系统注册；这是"Matter 设备的 main 函数"。
3. `src/protocols/secure_channel/PASESession.cpp` — 配网握手状态机。阅读目标：依次读 `Pair()`、`SendPBKDFParamRequest`、`SendMsg1`、`HandleMsg1_and_SendMsg2`、`HandleMsg2_and_SendMsg3`、`HandleMsg3`、`DeriveSecureSession`，理解 SPAKE2+ 四步握手是怎么用状态机实现的，以及 `GeneratePASEVerifier` 里 PBKDF2 迭代次数参数的意义。
4. `src/lib/core/TLV.h`（连同 `TLVReader.h`、`TLVWriter.h`）— 紧凑序列化格式。阅读目标：文件头注释说它"与 JSON 序列化有很多共同点，但在线上传输时紧凑得多"，读 TLV 的 Tag-Length-Value 三段式设计，想想为什么嵌入式场景需要它。
5. `src/app/clusters/on-off-server/OnOffCluster.cpp` — 一个 Cluster 的落点。阅读目标：看第 129 行 `OnOffCluster::SetOnOff(bool on)`，理解"代码生成框架 + 手写业务"的分界线在哪里。

**阅读顺序**：1 → 2 → 5 → 4 → 3。先看外围入口和业务落点建立直觉，再钻进 TLV 和密码学状态机这两个最"嵌入式"的部分。

## 6. 核心模块/函数导读

- **`Server::Init`（src/app/server/Server.cpp）**：整个设备的启动总装函数，约 500 行。它把 PlatformManager、DNSSD、CommissioningWindowManager、各子系统一一初始化并注册，最后启动事件循环。对应到工程上就是"嵌入式设备的 main 函数"；理解它能看懂整个协议栈的启动时序。与启动流程、平台层（src/platform）直接相关。
- **`PASESession::Pair` / `WaitForPairing` / `HandleMsg1_and_SendMsg2` / `HandleMsg2_and_SendMsg3` / `HandleMsg3`（src/protocols/secure_channel/PASESession.cpp）**：配网阶段的 SPAKE2+ 口令认证密钥交换状态机。`Pair` 是发起方入口，`WaitForPairing` 是接收方入口，后面几个 Handle 函数就是状态机的转移表。工程角色：把"用户输入的 11 位配对码"安全地变成临时会话密钥，这是整个信任链的第一环。`GeneratePASEVerifier` 里的 PBKDF2 迭代次数是可配置的，出厂前要按设备算力调校——典型的嵌入式"安全性与算力/功耗的权衡"。
- **`CASESession::PrepareForSessionEstablishment` / `DeriveSecureSession`（src/protocols/secure_channel/CASESession.h）**：运行期证书双向认证（Sigma 协议）。`ComputeSigma1ResponseTimeout` 根据对端 MRP 参数推算握手超时，是"时序工程"的教科书例子：在不可靠的无线链路上，超时定短了握手失败率高，定长了用户体验差。
- **`OnOffCluster::SetOnOff`（src/app/clusters/on-off-server/OnOffCluster.cpp）**：一个具体命令的执行落点。从芯片到灯的调用链：芯片收到报文 → 安全层解密 → Interaction Model 分发 → Cluster 处理器 → 应用回调（`MatterPostAttributeChangeCallback`）→ 驱动层。读懂这条链，就读懂了整个协议栈的"最后一公里"。
- **`CodeUtils.h` 的错误处理宏（src/lib/support/CodeUtils.h）**：`ReturnErrorOnFailure`、`SuccessOrExit`、`VerifyOrDie`。嵌入式 C++ 不用异常，错误要么逐层返回（`CHIP_ERROR`），要么直接死（`VerifyOrDie` 打印文件行号后中止）。这套宏是全仓库的"语法糖"，读代码前先认识它们，阅读速度会翻倍。它与构建系统、启动流程的关系：编译期断言、启动期自检都依赖这种"fail fast"哲学。

## 7. 软件工程师类比解释

- **Matter 协议栈 ≈ 后端 RPC 框架 + 网关 SDK**：Cluster 像资源端点，Interaction Model 的 Read/Write/Invoke/Subscribe 对应 GET/PUT/POST/订阅推送。**这个类比的局限**：Matter 是二进制 TLV + 有状态加密会话 + 证书体系，不是无状态 HTTP，也没有中间层可以随便改写报文。
- **Fabric ≈ 多租户隔离**：一个设备可以同时加入多个家庭/生态，每个 Fabric 有独立密钥和访问控制，类似一个服务同时服务多个租户。**这个类比的局限**：Fabric 数量有硬上限（SDK 默认 `CHIP_CONFIG_MAX_FABRICS = 16`，会话池按它编译期定长分配），租户撤销是设备端证书级操作，不是云端数据库改一行。
- **PASE/CASE 握手 ≈ TLS 1.3 + mTLS**：PASE 像"用一次性口令做 PSK 握手"，CASE 像双向证书认证。**这个类比的局限**：SPAKE2+ 是 PAKE，设计目标就是口令低熵也能防离线爆破，和 TLS 的证书体系思路不同；Matter 没有在线 CA 吊销，靠 DAC 证书链 + 黑名单机制。
- **TLV 编码 ≈ MessagePack/Protobuf**：都是紧凑的结构化二进制编码。**这个类比的局限**：TLV 没有编译期 schema 强类型（更像 MessagePack），约束靠 Cluster 定义和规范，解析时必须防御恶意长度和嵌套深度。
- **MRP 可靠消息 ≈ TCP 重传 + 指数退避**：在 UDP 之上做应用层确认与重传。**这个类比的局限**：MRP 没有拥塞控制、没有流控，重传间隔是静态配置（区分空闲/活跃两种），电池设备要调大间隔省电，市电设备可以调小间隔求快。
- **事件循环（Linux 上的 GLib 主循环）≈ Node.js 事件循环**：单线程、非阻塞、回调驱动。**这个类比的局限**：Matter 回调链有严格的时序预算，不能像 Node 那样随意把逻辑异步化；没有 GC，对象靠引用计数和编译期对象池管理。

## 8. 今日 10 个嵌入式概念卡片

**1. Cluster（簇）**
一句话解释：设备能力的最小组织单元，一组相关的属性、命令和事件，比如 OnOff、TemperatureMeasurement。
软件工程类比：微服务里的资源端点集合。
常见工程场景：一盏灯 = OnOff + LevelControl + ColorControl 多个 Cluster 的组合。
容易误解/坑点：Cluster 是规范定义死的，不能自己发明协议字段，厂商扩展要走官方规范流程。

**2. Attribute / Command / Event（数据模型三件套）**
一句话解释：属性是状态（灯亮没亮），命令是动作（开灯），事件是异步通知（过温告警）。
软件工程类比：属性像数据库字段，命令像 RPC 方法，事件像 Webhook。
常见工程场景：控制器订阅灯的 OnOff 属性，状态变化实时推送。
容易误解/坑点：写属性要考虑 ACL 和 timed write（防竞态的定时写），不是随便 set。

**3. Fabric（信任域）**
一句话解释：一组设备和控制器共享信任关系的集合，相当于一个"家庭网络"。
软件工程类比：多租户系统里的租户。
常见工程场景：一个灯同时加入 Apple 和 Google 两个家庭。
容易误解/坑点：SDK 默认最多 16 个 Fabric，会话池按上限编译期分配，超了要踢掉旧 Fabric。

**4. Setup Code 与 PASE（SPAKE2+）**
一句话解释：11 位配对码配合 SPAKE2+ 口令认证密钥交换，建立第一条加密通道。
软件工程类比：用一次性密码做 TLS-PSK 握手。
常见工程场景：扫码配网、NFC 碰一碰配网。
容易误解/坑点：配对码不是密码，不能复用；PBKDF2 迭代次数要按设备算力调，太慢影响配网体验。

**5. CASE（Sigma 协议）**
一句话解释：配网之后，设备与控制器用证书双向认证建立运行期会话。
软件工程类比：mTLS。
常见工程场景：日常开关灯、读状态。
容易误解/坑点：握手超时要参考对端 MRP 参数计算，无线环境下固定超时必踩坑。

**6. DAC / PAI（设备认证证书链）**
一句话解释：每台量产设备烧录的证书链（设备证书 + 产品中间证书 + 联盟根），证明"我是正版设备"。
软件工程类比：设备身份证 + CA 链。
常见工程场景：防伪造设备混入家庭网络。
容易误解/坑点：私钥必须放在安全元件/TPM 里，放在普通 Flash 里被读出来，认证体系就崩了。

**7. TLV 编码**
一句话解释：Tag-Length-Value 三段式紧凑二进制编码，官方注释说它"和 JSON 类似但线上传输紧凑得多"。
软件工程类比：MessagePack。
常见工程场景：所有 Matter 报文的载荷序列化。
容易误解/坑点：解析不可信输入时要限制长度和嵌套深度，否则是缓冲区攻击入口。

**8. MRP（可靠消息协议）**
一句话解释：UDP 之上的应用层确认与重传机制，分空闲/活跃两种重传间隔。
软件工程类比：TCP 重传 + 退避。
常见工程场景：Thread 无线网络这种高丢包环境。
容易误解/坑点：没有拥塞控制；电池设备必须调大重传间隔换续航。

**9. ACL（访问控制列表）**
一句话解释：谁（subject）能对哪个 Cluster 的哪些操作（客体）做什么，默认拒绝。
软件工程类比：IAM 策略。
常见工程场景：只允许特定控制器操作特定设备。
容易误解/坑点：ACL 存在设备本地 KVS 里，改动要按规范广播通知，不能想当然同步。

**10. 事件循环与对象池**
一句话解释：单线程事件驱动 + 编译期定长的对象池，避免动态内存碎片。
软件工程类比：Node.js 事件循环；对象池像连接池。
常见工程场景：MCU 上跑完整协议栈。
容易误解/坑点：任何阻塞调用都会卡死整个栈；池子满了新会话直接失败，要会看 `CHIP_CONFIG_SECURE_SESSION_POOL_SIZE` 这类编译期预算。

## 9. 30～60 分钟动手任务

**目标**：不买任何硬件，在本机（Linux/WSL）跑通"Matter 设备 + Matter 控制器"的最小闭环：让 chip-tool 给 lighting-app 配网，然后开灯关灯。

**步骤**：

1. 克隆仓库：`git clone --depth 1 https://github.com/project-chip/connectedhomeip.git`（完整首次编译依赖较多，建议磁盘留 10GB 以上）。
2. 安装依赖（按 examples/lighting-app/linux/README.md 的清单）：`sudo apt install git gcc g++ python3 pkg-config libssl-dev libdbus-1-dev libglib2.0-dev ninja-build python3-venv python3-dev unzip`。
3. 激活构建环境：`cd connectedhomeip && source scripts/activate.sh`（创建 Python 虚拟环境并下载工具链）。
4. 构建控制器 chip-tool：`cd examples/chip-tool && gn gen out/debug && ninja -C out/debug`。
5. 构建设备 lighting-app：`cd ../lighting-app/linux && gn gen out/debug && ninja -C out/debug`。
6. 终端 A 启动设备：`./out/debug/chip-lighting-app`，观察启动日志里的端口、Fabric 初始化和 DNS-SD 通告。
7. 终端 B 配网：`./out/debug/chip-tool pairing onnetwork 1 20202021`（节点号 1，配对码 20202021；若发现不到设备，把设备 IP 作为第四个参数补上）。
8. 控制：`./out/debug/chip-tool onoff on 1 1`，再 `./out/debug/chip-tool onoff off 1 1`，同时看设备端日志里 `MatterPostAttributeChangeCallback` 的打印。

**验收标准**：chip-tool 输出 Success；设备端日志出现命令执行与属性变更回调；能来回开关灯。看到回调打印的那一刻，你就亲眼见证了"报文 → 安全层 → Interaction Model → Cluster → 业务回调"整条链。

**替代方案**：如果编译环境受限，把任务降级为纯阅读：读 docs/guides/ 下的 simulated_device_linux.md（官方"Linux 模拟设备"指南）和 access-control-guide.md，给 PASESession 的四个 Handle 函数手画一张状态转移图。注意首次完整编译可能超过 60 分钟，可以把任务拆两天：今天完成 clone + activate + gn gen，理解 GN 工程结构；明天再跑 ninja 和配网。

## 10. 3 道深度追问题

1. **（时序/并发/资源）** PASESession 的握手一共四条消息。假设设备是电池供电的 Thread 节点，把 MRP 空闲重传间隔从 300ms 调到 5 秒，对握手成功率和电池寿命分别有什么影响？为什么 `ComputeSigma1ResponseTimeout` 要根据对端上报的 MRP 参数动态计算，而不是写死一个"足够大"的超时？
2. **（软件视角 → 嵌入式视角）** 你在后端习惯了"抛异常 + 中间件统一捕获"的错误处理；Matter 用 `CHIP_ERROR` 返回值逐层传播，辅以 `ReturnErrorOnFailure`、`VerifyOrDie`。请把一段你熟悉的业务代码改写成嵌入式风格：哪些错误应该返回给调用方，哪些应该直接 `VerifyOrDie` 停机？判断依据是什么？
3. **（工程判断）** Matter 允许一个设备同时加入多个 Fabric，且 ACL 默认拒绝、授权完全交给用户/控制器。如果你是设备厂商，你的产品默认要开放哪些 Cluster 给"新加入的家庭"？为什么规范宁可牺牲"开箱即用"的便利，也要把授权默认收紧？

## 11. 今日复盘问题

如果给你一块 2MB Flash、320KB RAM 的 MCU 移植 Matter，你会优先砍掉哪一层或哪个特性来塞进内存预算？砍完之后，Matter 认证测试里哪些测试项会因此失败？——这个问题没有标准答案，但能逼你把"分层架构"和"资源预算"两张图在脑子里叠在一起。

## 12. 工程点评

- **可维护性**：目录即架构（src/app、src/transport、src/protocols、src/platform），分层清晰；但仓库体量巨大、生成代码多，普通开发者上手门槛高，属于"联盟级"维护模式。
- **可移植性**：平台抽象层 + 每平台独立 example，Linux 上能跑通全套流程，是学习协议栈的绝佳入口；20+ 平台 CI 持续构建（ESP32、nRF、STM32、EFR32、Telink、TI、i.MX、Tizen 等）。
- **可靠性**：MRP 重传、消息计数器防重放、ACL 默认拒绝、定时写防竞态；CI 里有 Cirque 多节点测试和 QEMU 测试，覆盖真实组网场景。
- **可测试性**：这是嵌入式项目里少见的"测试基础设施先行"的仓库：单元测试、集成测试、Python 测试、模拟器测试一应俱全，还有故障注入 cluster 专门用来验证异常路径。
- **量产/运维**：DAC 证书体系、OTA 升级、诊断日志 cluster、故障注入——处处为量产设计；但产品过 Matter 认证的流程和成本不低，这是标准的"工程重量"所在。
