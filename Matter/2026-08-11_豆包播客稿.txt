今天这一期，我们不讲电路板，也不讲寄存器，我们讲一个软件工程师最容易上手的嵌入式项目：Matter 智能家居互联标准，以及它的开源参考实现 connectedhomeip。如果你写过后端接口、做过鉴权、搞过多租户系统，那这个项目几乎就是为你准备的，因为它本质上是一套跑在灯、锁、传感器上的分布式协议栈，而且同一份 C++ 代码，既能编译在 Linux 电脑上跑，也能交叉编译到 ESP32 或者 nRF52840 这样的小芯片上跑。这是理解软硬一体产品最直观的一扇门。

先说说它的来龙去脉。2019 年 12 月，亚马逊、苹果、谷歌、三星这些巨头，联合当时还叫 Zigbee 联盟的组织，宣布了一个叫 Project CHIP 的项目，全称是 Connected Home over IP，也就是基于 IP 的互联家居。2020 年 1 月 17 日，Matter 工作组正式成立。2021 年，项目改名为 Matter，Zigbee 联盟也改组成了连接标准联盟，简称 CSA。2022 年 10 月，Matter 1.0 正式发布，智能家居行业第一次有了一个跨品牌、跨生态的统一应用层标准。之后基本保持一年一到两个大版本的节奏：1.1、1.2、1.3、1.4，2025 年推出了 1.5，而就在 2026 年 4 月，官方发布了 1.5.1 这个维护版本。到今天，这个仓库在 GitHub 上有接近九千颗星，两千四百多个 fork，而且直到我写稿的这一天，代码仓库都还在持续更新。

那 Matter 到底解决什么问题呢？一句话：智能家居碎片化。你买一个智能灯，它可能只认自己家的 App，只进得了自己的生态，亚马逊的语音助手控制不了它，苹果的家庭 App 也看不见它。厂商想进多个生态，就得给每个生态各写一套适配，做多轮认证，成本极高。Matter 的做法是，在 IP 之上定义一个统一的应用层协议：设备厂商只要实现一次，任何支持 Matter 的 App 和生态都能控制它，而且所有控制都在本地网络完成，不依赖任何一家云。

但对做软件的人来讲，这个项目最值钱的地方，是它处处写满了嵌入式的约束。首先是硬件约束：这套协议栈要能跑在只有几百 KB 内存、一两兆 Flash 的单片机上。你在代码里会看到，安全会话的对象池大小，是在编译期直接用最大 Fabric 数量乘以三再加二算出来的，也就是说，会话对象全是编译期定长的，不是运行的时候 new 出来的，为的就是避免动态内存碎片。其次是报文约束：协议要省流量，所以自己设计了一套叫 TLV 的紧凑二进制编码，官方注释原话是，它和 JSON 有很多共同点，但在线上传输的时候紧凑得多。然后是时序约束：设备没有操作系统兜底，握手超时、重传间隔全靠显式计算，代码里有个函数专门根据对端上报的 MRP 重传参数来推算握手超时，而不是写死一个固定值。最后是安全约束：量产设备要烧录设备认证证书，配网用的是 PAKE 口令协议，运行期会话是证书双向认证，访问控制默认全部拒绝。

从架构上看，Matter 是一套严格分层的协议栈。最上面是应用层，就是你产品的业务逻辑，比如灯的开和关。往下是数据模型，定义了簇、属性、命令、事件这四个概念，一个簇就是设备的一项能力，灯的开关能力就是一个叫 OnOff 的簇。再往下是交互模型，只有四种操作：读、写、调用和订阅，读属性、写属性、调用命令、订阅变化，全部是这四种。再往下是消息帧和安全层，负责签名和加密，然后是可靠消息协议，在 UDP 之上做确认和重传，最下面是传输层和 IP 层，走 IPv6，物理链路可以是 Wi-Fi，也可以是 Thread 这种低功耗无线网格网络，配网阶段还能走蓝牙。

整个配网和控制的主流程，你可以想象成一次带安全认证的入职流程。设备上电，处于未配网状态，通过蓝牙广播或者网络发现服务被手机找到。用户扫包装盒上的二维码，得到一串十一位的配对码。双方用 SPAKE2+ 这个口令认证密钥交换协议，建立第一条加密通道，这一步叫 PASE。为什么要用这么讲究的协议？因为配对码只有十一位数字，熵很低，普通密码协议扛不住离线暴力破解，而 PAKE 协议专门解决这个问题。通道建好之后，手机通过这条安全通道，把 Wi-Fi 或者 Thread 的网络凭据发给设备，给设备签发证书，设备正式加入一个叫 Fabric 的信任域。以后日常控制，就走另一套叫 CASE 的证书双向认证流程，建立长期会话。最后，手机发的开灯命令，经过交互模型分发到 OnOff 簇的处理函数，再回调到应用层，最终驱动 GPIO 把灯点亮，就这么一条链。

接下来是今天的源码陪读。我建议你按这个顺序读五个文件。第一个是 examples 目录下 lighting-app 这个示例的入口文件 main.cpp，看主函数和初始化函数怎么把协议栈和业务粘在一起。注意里面有个回调函数带 emberAf 前缀，这是从 Zigbee 时代继承下来的老名字，Matter 的代码生成工具链 ZAP 就是从 Nest 公司的 Zigbee 工具演化来的，连 TLV 头文件的版权声明里都还留着 Nest Labs 的字样，这是很直观的一段技术史。第二个是 src 目录下 app server 里面的 Server.cpp，从它的 Init 函数开始读，这是整个协议栈的总装车间，五百多行，把事件循环、服务发现、配网窗口一个个初始化起来。第三个是 secure channel 目录下的 PASESession.cpp，读 Pair 函数和几个 Handle 消息的函数，你会看到 SPAKE2+ 的四步握手就是一个个状态转移。第四个是 TLV 相关的头文件，理解紧凑编码的 Tag 长度值三段式结构。第五个是 OnOff 簇的实现文件，看 SetOnOff 这个函数，理解哪些代码是工具生成的框架，哪些是你自己写的业务。

如果用软件工程的话来翻译这个项目：簇和属性，就像后端的资源端点；读、写、调用、订阅，就像 GET、PUT、POST 加上 WebSocket 推送。Fabric 就是多租户，一个设备可以同时属于好几个家庭，每个家庭一套独立密钥和权限，就像你的服务同时服务好几个租户。不过这个类比有个明显的局限：Fabric 数量有硬上限，SDK 默认最多十六个，而且会话池是按这个上限在编译期分配好的，不是云上数据库随便加一行。PASE 和 CASE 可以类比 TLS 握手和双向证书认证，但 PAKE 协议的设计目标本身就不同，而且 Matter 没有在线证书吊销，靠证书链加黑名单。TLV 可以类比 MessagePack 或者 Protobuf，但它没有编译期的强类型约束。可靠消息协议可以类比 TCP 的重传，但它没有拥塞控制，重传间隔要按设备是电池供电还是市电供电来配置。事件循环可以类比 Node.js，但你不能随便把逻辑异步化，回调链有严格的时序预算，内存也是手动管理的。

这里有几个概念，我建议你记在小本子上。第一个是簇，设备能力的最小单元，一盏灯就是开关、亮度、颜色好几个簇的组合，注意簇是规范定义死的，不能自己发明字段。第二个是 Fabric 信任域，注意它有数量上限，超了就要踢掉旧的家庭。第三个是配对码和 PASE，记住配对码不是密码，它是一次性使用的低熵输入，靠 PAKE 协议保证安全。第四个是 DAC 设备认证证书，每台量产设备都要烧录证书链，私钥必须放在安全元件里，放在普通 Flash 里被读出来，整个认证体系就白搭了。第五个是 MRP 可靠消息协议，它在 UDP 之上做确认和重传，没有拥塞控制，电池设备要调大重传间隔换续航。第六个是 ACL 访问控制列表，默认拒绝，授权完全由用户决定，这和你熟悉的 IAM 策略是一回事，只不过它存在设备本地的存储里。

今天的动手任务，不需要任何硬件，一台 Linux 电脑就能完成。第一步，克隆 connectedhomeip 仓库，建议加 depth 1 参数只拉最新一次提交。第二步，按官方文档安装依赖，主要是编译器、ninja 构建工具、Python 虚拟环境这些。第三步，执行 activate 脚本激活构建环境。第四步，构建两个程序：一个是控制器 chip-tool，一个是模拟设备 lighting-app。第五步，开两个终端，一个跑设备，一个跑控制器。第六步，用控制器给设备配网，命令大致是 pairing onnetwork，节点号一，配对码 20202021。第七步，用控制器发开关命令，你会看到设备端日志打印出属性变更回调。看到那个回调打印的瞬间，你就完整见证了报文从网线进来，经过安全层解密、交互模型分发、簇处理器，最后落到业务回调的整条链路。要注意，首次编译可能要一个小时以上，可以把任务拆成两天，今天先完成克隆、激活环境和生成构建配置，理解一下工程结构，明天再编译和配网。

最后留三道思考题。第一道，关于时序和资源：PASE 握手一共四条消息，如果设备是电池供电的 Thread 节点，把重传间隔从三百毫秒调到五秒，对握手成功率和电池寿命分别有什么影响？为什么握手超时要根据对端上报的参数动态计算，而不是写死一个足够大的值？第二道，请你把一段熟悉的后端代码改写成嵌入式风格，想清楚哪些错误应该返回给调用方，哪些应该直接停机，判断依据是什么。第三道，如果你是设备厂商，你会在默认情况下开放哪些能力给新加入的家庭，为什么规范宁可牺牲开箱即用的便利，也要把授权默认收紧？

今天的复盘问题也很有意思：如果给你一块两兆 Flash、三百二十 KB 内存的单片机移植 Matter，你会先砍掉哪一层？砍完之后，认证测试里哪些项目会挂？这个问题没有标准答案，但它能逼你把分层架构图和内存预算图在脑子里叠到一起。

明天你可以接着往三个方向走：一是深读 CASE 会话的 Sigma 状态机，和 TLS 1.3 画一张对比时序图；二是用 ZAP 工具给示例设备加一个自定义簇，走一遍改配置、生成代码、编译、调试的完整流程；三是把示例交叉编译到 ESP32 或者 nRF52840 上，亲身体验单片机上的内存预算和 Linux 上的差别，这是软硬一体最直观的一课。好，今天的分享就到这里，我们明天见。
