今天要聊的项目，是航模圈里大名鼎鼎的 ExpressLRS。它是一套开源的无线电遥控链路固件，用一句话介绍就是：基于 Semtech 的 SX127x 和 SX1280 这两颗 LoRa 射频芯片，加上 Espressif 的 ESP32 系列处理器，用极小的空中数据包和跳频扩频技术，在二点四吉赫和九百兆赫两个频段上，同时做到低延迟和超远距离，是目前 FPV 穿越机竞速圈事实上的主流遥控协议。

先说为什么今天选它。这个仓库由 ExpressLRS 公司跟开源社区一起维护，最近一次代码合入是二零二六年七月三十一号，也就是一个多星期前的事，当前版本到了四点一零，GitHub 上有五千多颗星，社区非常活跃。更难得的是，它是极少数固件、刷写工具、桌面配置器、文档、单元测试全部齐备的开源嵌入式项目。它自己没有官方硬件，全靠社区贡献的上百种硬件目标，这反而逼出了一套非常工程化的统一固件加运行时硬件探测设计。对想从纯软件转嵌入式的工程师来说，它一晚上能同时覆盖射频驱动、硬实时调度、状态机、串口协议、OTA 升级、配置持久化、双天线分集、动态功率控制，而且每一个问题都能在源码里找到具体答案。

它解决的真实问题是什么呢。穿越机飞手要的是手指到电机的延迟尽量低，竞速的时候需要一千赫兹的包率；而远航飞手要的是几十公里不断链。传统用 FSK 调制的遥控协议，要么延迟高，要么距离短。ExpressLRS 用 LoRa 调制，加上压缩到只有八到十三字节的空中包，再加上八十跳的跳频，把距离和延迟这对矛盾同时优化了。跟普通软件项目相比，它多出来的约束非常具体。第一，电磁频谱是物理的、共享的，二点四吉赫要跟 WiFi 共存，九百兆赫要跟楼宇安防、温控器抢频段，所以必须有法规域和跳频。第二是硬实时，二百五十赫兹意味着发射机每四毫秒必须发出一个包，中断回调里不能有任何不确定的延迟，热路径函数得放进 IRAM。第三，可靠性不能靠 TCP 那套重传，因为链路是单工的广播，只能靠前向纠错、分片重发和链路统计来兜底。第四是资源受限，很多接收机就是一颗 ESP8285，Flash 只有一两兆，RAM 几百 KB，代码必须按目标裁剪。

看一下技术架构。源码里 src 下面的 src 目录是主逻辑，接收机主文件有两千多行，发射机主文件一千五百多行；lib 目录是高度模块化的组件库，有 OTA、FHSS、HWTIMER、CRSF 协议、CRC、FEC、电源管理、两颗射频芯片的驱动，还有 StubbornReceiver 和 StubbornSender 这种专门做可靠遥测的库，加起来大概四十个模块。targets 目录用 PlatformIO 的配置文件组织构建环境，test 目录是跑在本机的单元测试，lua 目录是遥控器上的配置脚本。

发射机的运行流程是这样的。硬件定时器每四毫秒触发一次回调，从遥控器串口读回 CRSF 格式的摇杆数据，打包成 OTA 包，普通数据包或者周期性的同步包，然后通过 SPI 写进射频芯片发出去，再按跳频序列切到下一个频点。同步包携带 nonce、速率、跳频位置这些信息，让接收机对齐时基。接收机这边默认二十毫秒的定时器，收到合法包之后解析出摇杆通道，再按 CRSF 或者 SBUS、PWM 这些协议转发给飞控。

空中协议本身非常值得细看。它分 OTA4 八字节和 OTA8 十三字节两种包。包类型编码在第一个字节的最低两位，分别是摇杆数据、业务数据、同步包和链路统计。摇杆通道用四乘十比特的位域压缩打包，所以八字节就能装下四个通道。OTA8 还额外回传三比特的发射功率。校验方面，OTA4 用八位 CRC，OTA8 用十六位 CRC，而且 CRC 的初始值由 UID 决定，UID 是绑定短语哈希出来的，这就让不同绑定用户的链路在物理层校验上就天然分开，防止串台。

跳频这块，二点四吉赫域在两千四百点四兆到两千四百七十九点四兆之间用八十个频点，九百兆赫按法规域不同，从三个到四十个频点不等，比如 FCC915 域就是四十个。跳频序列长度固定二百五十六，生成的时候必须满足四条硬性要求：每 N 跳要回到同步频点，序列内不能有重复，各频点出现次数尽量均匀，整体要伪随机。同步频点取频点表的正中间。

配置系统也很有特色。绑定短语经过哈希生成六字节的 UID，写进存在 Flash 里的固件选项，配合 ModelMatch 功能，把模型编号异或进同步包，防止同一个 UID 下多架飞机互相干扰。升级途径有 WiFi 刷写、Betaflight 透传和串口刷写三种，配套一个叫 ExpressLRS Configurator 的桌面工具，飞手点点鼠标就能刷固件。

接下来是源码陪读，今天建议按这个顺序读五个文件。第一个是 OTA 点 h 头文件，两百多行，是空中协议的唯一权威定义，重点看两种包的结构、位域布局和 CRC 计算范围，理解为什么八字节能装下四个摇杆通道。第二个是 FHSS 点 cpp，看法规域表、同步频点选取和跳频序列生成的四条要求。第三个是 hwTimer 的头文件，理解 tick 和 tock 双回调、内置频偏补偿和相位对齐机制，这是整个项目实时性的地基。第四个是发射机主文件，先读中间那一段，看同步包生成、速率设置、发送摇杆数据这些热路径函数怎么在一个四毫秒周期里协作。第五个是接收机主文件，先读全局变量区和主循环入口，看天线分集、噪声底、上行链路质量这些健康变量怎么维护，以及断链是怎么检测的。

核心函数导读挑几个讲。首先是 hwTimer 的 tick 和 tock 回调，定时器以半个更新周期交替触发两个回调，发射机默认四千微秒，也就是二百五十赫兹包率，接收机默认两万微秒。两个独立设备各自起振，晶振误差会让收发双方逐渐失步，所以定时器内置了可以增减的频偏补偿，phaseShift 提供一次性相位对齐，这就是无共享时钟的分布式时基同步的嵌入式版本。然后是同步包生成和 nonce 自增，nonce 每发一包加一，既参与跳频位置计算，又是抗重放的随机因子。再有就是跳频序列生成函数，用 UID 当种子把二百五十六长的序列打乱，发射机和接收机只要种子相同，就能各自独立算出完全一致的跳频表，完全不需要协商。还有动态功率算法，输入是遥测回来的链路质量、信号强度和信噪比，链路质量用滑动平均，突然掉二十个点或者低于五十就直接拉满功率，低于八十五升一档，信号强度低于灵敏度加十五升档，高于灵敏度加二十一降档，链路质量稳定在九十五以上才允许用信噪比降功率，开机默认最低功率，这样飞手换电池的时候不会全场炸功率。最后是速率设置函数，会根据遥控器串口波特率自动限制包率上限，防止链路能发但串口来不及喂数据。

用软件工程的话来类比。跳频扩频就像一致性哈希环加故障转移，收发双方用同一个种子算出完全相同的频点序列，某个频点被干扰就相当于节点下线，下一跳自动换频。这个类比的局限是，频率是物理频谱资源，频点之间要满足法规间隔和占空比，不是虚拟节点想加就加。同步包加 nonce 就像分布式系统的时钟同步加单调递增的序列号，局限在于这是单向广播，没有往返测量，做不了闭环校正，只能开机对齐加本地频偏补偿。动态功率就像基于反馈的弹性伸缩，用遥测回报当监控指标，功率当副本数，低了扩容高了缩容，局限是发射功率有法规上限，还会干扰同频段的其他人，而且调节粒度是固定档位不是连续值。CRSF 协议就像二进制 RPC 帧协议，定长帧、地址字节、类型字节、CRC，在双工串口上复用摇杆、遥测、参数读写多路消息，局限是帧长只有几十字节，没有内置重传和流控，可靠性全靠上层链路兜底。统一固件加运行时硬件探测，就像同一个容器镜像在不同环境跑加配置中心下发，一份固件覆盖几十种硬件，靠启动时探测 GPIO 和外设区分板卡，局限是 Flash 和 RAM 太小，探测逻辑必须极简，部分能力还得靠编译期裁剪。

今天的概念卡片一共十张。第一张，跳频扩频，收发双方按约定序列在多个频点间快速跳变传输，抗干扰抗截获，类比一致性哈希环，坑点是序列必须无重复且分布均匀，否则某些频点会被饿死。第二张，LoRa 调制，一种 Chirp 扩频调制，用带宽换灵敏度，能解出低于噪声底的信号，类比 CDMA 的扩频思想，坑点是它占用整段带宽，频谱效率低，二点四吉赫上要跟 WiFi 共存。第三张，CRSF 协议，航模界事实标准的双向串口协议，类比二进制 RPC，坑点是帧内是固定偏移的字节布局，跨版本要小心兼容。第四张，绑定短语和 UID，把用户输入的短语哈希成六字节 UID，收发一致才互通，类比预共享密钥，坑点是短语太短或太常见会增加碰撞概率。第五张，遥测比例，下行遥测包和上行遥控包的比例，比如一比六十四，类比读写分离的带宽配额，坑点是比例过高会挤占遥控通道的空中时间。第六张，链路质量、信号强度和信噪比这三件套，类比可用性、延迟和错误率，坑点是链路质量高但信号强度低，说明正处在灵敏度极限附近，随时可能断。第七张，动态发射功率，根据遥测反馈实时升降功率档位，类比自适应限流，坑点是依赖遥测，遥测关了算法就失效。第八张，tick 和 tock 定时器与时钟漂移补偿，硬件定时器以半个周期交替触发两个回调，内置频偏补偿对抗晶振误差，坑点是中断回调里不能做耗时操作，否则直接破坏包率周期。第九张，IRAM 热路径，把最频繁执行的函数放进 IRAM，避免 Flash 取指延迟造成的不确定时序，类比热数据放内存缓存，坑点是 IRAM 总共才一两百 KB，滥用会导致链接失败。第十张，统一固件加运行时硬件探测，同一份固件覆盖一个系列的所有硬件，类比镜像加配置中心，坑点是探测依赖 GPIO 上拉和外设 ID，探测失败会误判硬件。

动手任务今天也给了，不需要硬件。第一步，用 Python 实现 OTA4 的摇杆通道打包和解包，四个通道按十比特位域连续塞进五个字节，再实现八位 CRC 校验，跑十万次随机往返测试验证零丢失。第二步，实现跳频序列生成，参考源码注释里的四条要求，用八十个频点、序列长二百五十六、同步频点四十生成序列，写断言验证四条约束全部满足。第三步，模拟绑定，用两个不同的短语生成两个种子，验证两个序列完全不同，相同短语序列完全一致。如果本机能装 PlatformIO，还可以跑一下官方的单元测试命令，看看嵌入式项目怎么写可移植的单测。

最后留三道深度追问。第一道是时序题，发射机在二百五十赫兹下一个周期只有四毫秒，读摇杆、打包、SPI 写射频芯片、处理中断全要塞进去，如果定时器回调里偶然出现一次超过四毫秒的执行，会发生什么连锁反应，为什么这些函数要标注成放进 IRAM，而普通后端代码从不需要这种标注。第二道是软转嵌的视角题，后端保证可靠传输靠 TCP 的确认和重传窗口，而 ExpressLRS 的下行遥测用的是分片反复重发加接收方幂等去重，如果硬把确认和滑动窗口套到这条四毫秒单工链路上，会撞上哪些物理约束，什么条件下你才会选择确认重传而不是盲目重发。第三道是工程判断题，二点四吉赫域用了八十个跳频点，九百兆的 FCC915 域只有四十个，EU868 域只有十三个，频点数直接决定同一区域能容纳多少套互不干扰的链路，如果让你评估用绑定短语做链路隔离够不够，你会怎么建模碰撞概率，又会建议增加什么机制。

今天的复盘问题是，如果让你为 ExpressLRS 增加自动选择二点四吉赫和九百兆双频段漫游的能力，你会先改哪个模块，你又如何证明改动没有破坏那条四毫秒的硬实时周期。

工程点评收个尾。可维护性上，lib 目录按单一职责拆成约四十个小库，源码里大量注释在解释为什么，而不是只写是什么，文档站点跟代码同步更新，非常难得。可移植性上，射频驱动拆成公共抽象加两颗芯片各自的实现，上层代码只依赖公共接口，新增硬件只需要加一个目标配置文件。可靠性上，CRC 由 UID 初始化防串台，前向纠错，可靠遥测，频偏校正，模型匹配，双天线分集，层层设防。可测试性上，提供本机平台的单元测试，CRC、跳频、FIFO、MSP、CRSF 都有覆盖，这在嵌入式开源项目里属于标杆水平。量产和运维上，桌面配置器一键刷写，三种升级路径，LED 状态指示，还有变砖恢复流程，把用户是飞手而不是工程师的运维体验做到了产品级。

明天的延展方向有三个。第一，深读 SX1280 驱动，看 SPI 寄存器读写、中断处理、收发切换的时序细节，理解射频驱动和 MCU 的边界。第二，用 LoRa 的调制参数和灵敏度公式，对照各个包率档位，算一算为什么一千赫兹必然比五十赫兹距离短。第三，对比同样用 LoRa 芯片但走公开 Mesh 协议的 Meshtastic，看两者在信道接入、重传、功耗策略上的差异，体会同一颗芯片在不同产品约束下的设计分叉。

这就是今天的 ExpressLRS，一个把协议工程、硬实时和产品化做到极致的开源项目。明天见。
