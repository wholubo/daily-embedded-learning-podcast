# 每日嵌入式学习：ExpressLRS

## 1. GitHub 项目链接与一句话介绍

- 仓库：https://github.com/ExpressLRS/ExpressLRS
- **一句话介绍**：ExpressLRS 是一套开源的航模无线电遥控链路固件，基于 Semtech SX127x/SX1280 LoRa 射频芯片加 Espressif（或 STM32）处理器，用极小的空中数据包和跳频扩频技术，在 2.4GHz 与 900MHz 频段同时做到"低延迟"和"超远距离"，是当下 FPV 穿越机竞速圈事实上的主流遥控协议。

## 2. 为什么今天选它

- 活跃度：仓库由 ExpressLRS LLC 与开源社区共同维护，最新一次合入是 2026 年 7 月 31 日的 PR #3706；当前版本 v4.1.0，官方文档站点持续更新（2026 年 6 月仍有内容修订）；GitHub 约 5.2k star，Discord 社区活跃。
- 工程完整度：这是极少数"固件、上位机刷写工具、配置器、文档、硬件参考、CI、单元测试"全套齐备的开源嵌入式项目。它没有官方硬件，全靠社区上百种硬件目标（target），逼出了非常工程化的"统一固件 + 运行时硬件探测"设计。
- 学习价值：对纯软件工程师来说，它同时覆盖了射频驱动（SPI 时序）、实时调度（4ms 周期硬实时）、状态机、串口协议（CRSF）、OTA 升级、配置持久化、双天线分集、动态功率控制等一整套软硬一体问题，而且每个问题都能在源码里找到具体答案。

## 3. 项目解决的问题

- 真实场景：穿越机飞手需要"手指到电机"的链路延迟尽可能低（竞速时 1000Hz 包率），同时远航飞手需要几十公里不断链。传统 FSK 遥控协议（如 FrSky ACCST）要么延迟高要么距离短。ExpressLRS 用 LoRa 调制 + 压缩到 8~13 字节的空中包 + 80 跳的跳频，把"距离"和"延迟"这对矛盾同时优化。
- 相比普通软件项目多的约束：一是电磁频谱资源是物理的、共享的，2.4GHz 要和 WiFi 共存，868/915MHz 要和楼宇安防、温控器抢频段，所以必须有法规域（regulatory domain）和跳频；二是硬实时：250Hz 意味着发射机每 4ms 必须发出一个包，中断回调里不能有任何不确定延迟，热路径函数要放 IRAM；三是可靠性不能靠 TCP 重传：链路是单工广播，只能用前向纠错（FEC）、分片重发（stubborn sender）和链路统计来兜底；四是资源受限：接收机就是一颗 ESP8285，Flash 只有 1~2MB，RAM 几百 KB，代码要按目标裁剪。

## 4. 技术架构分析

（基于公开源码与官方文档，标注"基于公开文件推断"处为推断）

- 目录结构：`src/src/` 是主逻辑（rx_main.cpp 2182 行、tx_main.cpp 1583 行、rxtx_common.cpp、dynpower.cpp、common.cpp）；`src/lib/` 是高度模块化的组件库（OTA、FHSS、HWTIMER、CrsfProtocol、CRC、FEC、OPTIONS、CONFIG、POWERMGNT、SX127xDriver、SX1280Driver、SX12xxDriverCommon、StubbornReceiver/StubbornSender、MAVLink、MSP 等约 40 个）；`src/targets/` 用 PlatformIO ini 定义构建环境；`src/test/` 是 native 平台单元测试；`src/lua/` 是遥控器 Lua 配置脚本；`src/python/` 是构建辅助工具。
- 运行流程（TX 侧）：硬件定时器 hwTimer 每 4ms 触发一次回调 → 从遥控器串口读 CRSF 摇杆数据 → 打包成 OTA 包（普通数据包或周期性的同步包）→ 经 SPI 写入 SX1280/SX127x 发送 → 按跳频序列切频；同步包携带 nonce、速率、跳频位置等信息，让接收机对齐时基。RX 侧默认 20ms 定时器，收到合法包后解析出摇杆通道，再按 CRSF/SBUS/PWM 等协议转发给飞控。
- 空中协议（OTA）：分 OTA4（8 字节）与 OTA8（13 字节）两种包。包类型编码在首字节低 2 位：RCDATA（摇杆数据）、DATA（上行/下行数据）、SYNC（同步）、LINKSTATS（链路统计）。摇杆通道用 4×10bit 位域压缩打包；OTA8 还带 3bit 发射功率回传。OTA4 用 8 位 CRC，OTA8 用 CRC16，且 CRC 初始值由 UID（绑定短语哈希而来）决定，天然防止不同绑定用户互相串台。
- 跳频（FHSS）：2.4GHz 域在 2400.4~2479.4MHz 内 80 个频点，900MHz 按法规域不同有 3~40 个频点（FCC915 为 40 个）。跳频序列长度固定 256，生成时满足四条硬性要求：每 N 跳回到同步频点、序列内不重复、各频点出现次数尽量均匀、整体伪随机。同步频点取频点表中间位置。
- 配置系统：绑定短语（binding phrase）经哈希生成 6 字节 UID 写入固件选项（firmwareOptions，存于 flash 的 eeprom 模拟区），配合 ModelMatch（把 modelId XOR 进同步包）防止同一 UID 下多架机互相干扰。运行时通过 OPTIONS/hardware.cpp 探测硬件（基于公开文件推断的机制描述），实现"统一固件目标"。
- 通信与升级：遥控器侧走 CRSF 协议（发射机模块与控之间、接收机与飞控之间）；接收机还支持 SBUS、SUMD、HoTT、MAVLink、PWM 输出。升级有 WiFi 刷写（热点/家庭网络两种）、Betaflight Passthrough、串口刷写三种途径，配套 ExpressLRS Configurator 桌面工具。

## 5. 源码陪读：今天只读哪几个文件

阅读顺序如下，按依赖关系从"协议"到"调度"到"实现"：

1. `src/lib/OTA/OTA.h`（约 215 行）——空中协议的唯一权威定义。读目标：看懂 OTA4/OTA8 两种包结构、位域布局、包类型编码、CRC 计算范围，理解"为什么 8 字节能装下 4 个摇杆通道"。
2. `src/lib/FHSS/FHSS.cpp`（约 219 行）——跳频域配置与序列生成。读目标：看法规域表、同步频点选取、freq_spread 计算，以及序列生成的四条要求。
3. `src/lib/HWTIMER/hwTimer.h`——定时抽象。读目标：理解 tick/tock 双回调、内置频偏补偿、phaseShift 对齐机制；这是全项目实时性的地基。
4. `src/src/tx_main.cpp`（1583 行，建议先读 380~660 行区间）——发射机主循环。读目标：GenerateSyncPacketData、SetRFLinkRate、SendRCdataToRF、nonceAdvance 这些热路径函数如何在一个 4ms 周期内协作。
5. `src/src/rx_main.cpp`（2182 行，建议先读 1~260 行全局变量区与主循环入口）——接收机状态机。读目标：看天线分集、geminiMode、RFnoiseFloor、uplinkLQ 这些"链路健康"变量如何被维护，以及断链检测（LastValidPacket）。

## 6. 核心模块/函数导读

- hwTimer 的 tick/tock 回调与 phaseShift：定时器以半个更新周期交替触发 tick/tock，TX 默认 4000µs（即 250Hz 包率），RX 默认 20000µs。两个独立设备各自起振，晶振误差会让收发双方逐渐失步，所以定时器内置可增可减的频偏补偿，phaseShift 提供一次性相位对齐。这是"无共享时钟的分布式时基同步"的嵌入式版本。
- GenerateSyncPacketData 与 nonceAdvance（tx_main.cpp）：同步包每隔 SyncInterval 在同步频点上发送，携带 fhssIndex、nonce、速率枚举、开关通道模式、遥测比例、geminiMode、otaProtocol 和 UID 片段。nonce 每发一包自增，既参与跳频位置计算（OtaNonce % FHSShopInterval），又作为抗重放/串台的随机因子。
- FHSSrandomiseFHSSsequence（FHSS.cpp）：用 UID 做种子把 256 长的跳频序列打乱，保证同步频点周期性出现、无重复、分布均匀。发射机和接收机只要 UID 相同、种子相同，就能各自独立算出完全一致的跳频表——不需要协商过程。
- DynamicPower_Update / DynamicPower_TelemetryUpdate（dynpower.cpp）：动态功率算法。输入是遥测回来的 LQ、RSSI、SNR：LQ 用滑动平均（K=8），突然掉 20 个点或低于 50 直接拉满功率；LQ 低于 85 升一档；RSSI 低于（灵敏度+15）升档、高于（灵敏度+21）降档；LQ 稳定在 95 以上才允许用 SNR 降功率。开机默认最低功率，拔电池换电时不会全场炸功率。
- SetRFLinkRate 与 adjustPacketRateForBaud：根据所选包率（50~1000Hz）设置射频调制参数，并根据遥控器串口波特率自动限制包率上限，防止"链路能发但控的串口来不及喂数据"。
- OtaUpdateCrcInitFromUid：用 UID 初始化 CRC 值，让不同绑定短语的链路在物理层 CRC 上就被区分开，是"绑定"语义在协议底层的落地。

## 7. 软件工程师类比解释

- 跳频（FHSS）≈ 一致性哈希环 + 故障转移：收发双方用同一个种子算出完全相同的频点序列，类似多个服务用同一哈希环把请求路由到同一节点；某频点被干扰相当于节点下线，下一跳自动换频。局限：频率是物理频谱资源，频点间还要满足法规间隔和占空比，不是虚拟节点可以随便增减。
- 同步包 + nonce ≈ 分布式系统的时钟同步（NTP/TSN）加单调递增序列号：同步包广播时基和跳频位置，nonce 类似消息序号防重放。局限：这是单向广播，没有往返测量，无法做闭环时钟校正，只能靠"开机对齐 + 本地频偏补偿"。
- 动态功率 ≈ 基于反馈的弹性伸缩/自适应限流：用遥测回报的 LQ/RSSI 当监控指标，功率当"副本数"，低了扩容（升功率）、高了缩容（降功率）。局限：发射功率有法规上限，而且会干扰同一频段的其他人，调节粒度是固定的功率档位而非连续值。
- CRSF 协议 ≈ 二进制 RPC 帧协议（如 protobuf over WebSocket）：定长帧、8 位地址、类型字节、CRC，双工串口上复用摇杆、遥测、参数读写多路消息。局限：帧长只有几十字节、没有内置重传和流控，可靠性完全靠上层链路兜底。
- 统一固件 + 运行时硬件探测 ≈ 同一容器镜像在不同环境跑 + 配置中心下发：一份固件覆盖几十种硬件，靠启动时探测 GPIO/外设区分板卡。局限：Flash/RAM 只有几百 KB 到几 MB，探测逻辑必须极简，且不可能覆盖所有外设差异（部分能力仍需编译期裁剪）。

## 8. 今日 10 个嵌入式概念卡片

1. **FHSS 跳频扩频**：一句话：收发双方按约定序列在多个频点间快速跳变传输，抗干扰抗截获。类比：一致性哈希环。场景：2.4GHz 80 跳、900MHz 按法规域 3~40 跳。坑点：跳频序列必须无重复且均匀分布，否则某些频点会被"饿死"或排队。
2. **LoRa 调制**：一句话：Chirp 扩频调制，用带宽换灵敏度，能解出低于噪声底的信号。类比：CDMA 的扩频思想。场景：远航 40km@100mW 250Hz。坑点：LoRa 占用整段带宽，频谱效率低，2.4GHz 上要和 WiFi 共存。
3. **CRSF 协议**：一句话：航模界事实标准的双向串口协议，遥控器↔发射模块↔飞控之间传输。类比：二进制 RPC。场景：TX 读摇杆、RX 发遥测。坑点：帧内是固定偏移的字节布局，跨版本要小心兼容。
4. **绑定短语与 UID**：一句话：把用户输入的短语哈希成 6 字节 UID，收发双方 UID 一致才互通。类比：预共享密钥/集群 token。场景：杜绝同频段他人设备串台。坑点：短语太短或太常见会增加碰撞概率；ModelMatch 还要再 XOR 一层 modelId。
5. **遥测比例（Telemetry Ratio）**：一句话：下行遥测包与上行 RC 包的发送比例，如 1:64 表示每 64 个 RC 包插 1 个遥测包。类比：读写分离的带宽配额。场景：动态功率依赖至少每秒 2 个链路统计包。坑点：比例过高会挤占 RC 通道的空中时间，低包率下遥测带宽骤减。
6. **LQ/RSSI/SNR 信号健康三件套**：一句话：LQ 是"收到的包里多少是好的"（百分比），RSSI 是信号强度，SNR 是信噪比。类比：可用性（SLA）、延迟、错误率。场景：OSD 显示、断链判断、动态功率输入。坑点：LQ 高但 RSSI 低说明在灵敏度极限附近，随时可能断；只看 RSSI 会被干扰环境误导。
7. **动态发射功率**：一句话：根据遥测反馈实时升/降射频功率档位。类比：自适应限流。场景：近场低功率省电少干扰，远场自动拉满。坑点：依赖遥测，遥测关了算法就失效；换电池瞬间要防止误拉满。
8. **tick/tock 定时器与时钟漂移补偿**：一句话：硬件定时器以半个周期交替触发两个回调，并内置频偏补偿对抗晶振误差。类比：分布式时钟同步。场景：TX/RX 无共享时钟的链路时基对齐。坑点：中断回调里不能做耗时操作，否则直接破坏包率周期。
9. **IRAM 热路径（ICACHE_RAM_ATTR）**：一句话：把最频繁执行的函数放到 IRAM，避免 Flash 取指延迟（cache miss）造成的不确定时序。类比：热数据放内存缓存。场景：发送/解析包的每包必调函数。坑点：IRAM 总共才一两百 KB，滥用会导致链接失败。
10. **统一固件 + 运行时硬件探测**：一句话：同一份固件覆盖一个系列的所有硬件，启动时探测板卡差异。类比：镜像+配置中心。场景：ESP32 系几十种接收机/发射模块一个包搞定。坑点：探测依赖 GPIO 上拉/外设 ID，探测失败会误判硬件，必须保留编译期裁剪逃生通道。

## 9. 30~60 分钟动手任务

目标：不碰硬件，复现 ExpressLRS 两个最核心的"协议工程"细节，建立对位域打包和跳频序列约束的直觉。

步骤：
1. 用 Python 实现 OTA4 的摇杆通道打包/解包：4 个通道按 10bit 位域连续塞进 5 字节（对照 OTA.h 里 OTA_Channels_4x10 的注释），再实现 8 位 CRC 的校验，做 10 万次随机 round-trip 测试，验证无丢失。
2. 实现 FHSS 序列生成：参考 FHSS.cpp 注释里的四条要求（每 N 跳回到同步频点、无重复、均匀、伪随机），用 80 频点、序列长 256、同步频点 40 生成序列，写断言验证四条约束。
3. 模拟"绑定"：用两个不同"短语"生成不同种子，验证两个序列完全不同；用相同短语验证序列完全一致。
4. （可选）如果本机能装 PlatformIO：`pio test -e native` 跑一遍官方单元测试（test_crc、test_fhss 等），看嵌入式项目怎么写可移植单测。

验收标准：round-trip 测试零失败；FHSS 四条约束断言全部通过；同短语序列一致、异短语序列不同的对比输出正确；若跑了官方测试，能看到测试全部通过。

## 10. 3 道深度追问题

1. （时序）TX 在 250Hz 下一个周期只有 4ms：读摇杆、打包、SPI 写射频芯片、处理中断全都要塞进去。如果 hwTimer 的回调里偶然出现一次超过 4ms 的执行，会发生什么连锁反应？为什么项目要把这些函数标成 ICACHE_RAM_ATTR，而普通后端代码从不需要这种标注？
2. （软→嵌视角）后端保证可靠传输靠 TCP 的 ACK 与重传窗口；ExpressLRS 的下行遥测却用"stubborn sender"（分片反复重发，接收方只做幂等去重）。如果硬把 ACK/滑动窗口套到这条 4ms 单工链路上，会撞上哪些物理约束？什么条件下你才会选择"确认重传"而不是"盲目重发"？
3. （工程判断）2.4GHz 域用了 80 个跳频点，900MHz 的 FCC915 域只有 40 个，EU868 只有 13 个。频点数直接决定了同一区域能容纳多少套互不干扰的链路。如果让你评估"用绑定短语做链路隔离是否足够"，你会怎么建模碰撞概率？你会建议增加什么机制？

## 12. 工程点评

- 可维护性：`src/lib/` 按单一职责拆成约 40 个小库，命名与职责清晰；文档站点与代码同步更新，源码里大量注释解释"为什么"（如 FHSS 序列的四条要求），非常难得。
- 可移植性：射频驱动拆成 SX127xDriver / SX1280Driver / SX12xxDriverCommon 三层，上层代码只依赖公共抽象；构建用 PlatformIO 的 ini 按目标矩阵组织，新增硬件只需加一个目标文件。
- 可靠性：CRC 由 UID 初始化防串台、FEC 前向纠错、stubborn sender 可靠遥测、AFC 频偏校正、模型匹配、双天线分集，层层设防，值得逐层学习。
- 可测试性：提供 native 平台单元测试（`pio test -e native`），CRC、FHSS、FIFO、MSP、CRSF 都有覆盖；这在国内嵌入式开源项目里属于标杆水平。
- 量产/运维：Configurator 一键刷写、WiFi 热点/家庭网络/串口三种升级路径、LED 状态指示、unbrick 恢复流程，把"用户是飞手不是工程师"的运维体验做到了产品级。
