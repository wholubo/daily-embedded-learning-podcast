# 每日嵌入式学习：Crazyflie 飞控固件

## 1. GitHub 项目链接与一句话介绍

**仓库**：https://github.com/bitcraze/crazyflie-firmware

**一句话**：Crazyflie 是 Bitcraze 公司开发的一款开源微型四轴飞行器平台，其固件基于 FreeRTOS 构建在 STM32F4 上，提供完整的飞行控制、传感器融合、通信协议和扩展板（Deck）热插拔支持。

---

## 2. 为什么今天选它

Crazyflie 固件是一个极具工程完整度的开源嵌入式项目，已持续维护超过 12 年（2011 年至今），社区活跃度高，文档完善，是嵌入式软件工程师学习"从裸机到产品级固件"的理想案例。

**适合软件工程师学习嵌入式的原因**：
- 使用 FreeRTOS，与后端工程师熟悉的"服务拆分 + 消息队列"模式高度相似
- 清晰的模块分层：platform → hal → modules → deck，类似微服务架构的依赖倒置
- 有完整的 CI/CD、单元测试、静态分析，工程规范接近工业级
- Deck 扩展机制类似于 Linux 内核的设备树 + 驱动注册，体现"插件化"设计哲学

---

## 3. 项目解决的问题

Crazyflie 解决的是**微型无人机实时飞行控制**问题：在手掌大小的硬件上，以毫秒级周期完成传感器采集 → 姿态估计 → PID/模型预测控制 → 电机输出的闭环控制，同时支持无线通信、日志回传、参数调优和扩展外设热插拔。

**与普通软件项目相比的额外约束**：
- **实时性**：控制环必须在 1kHz（1ms）周期内完成，否则飞行器失稳坠毁
- **资源受限**：STM32F4 仅有 192KB RAM、1MB Flash，堆大小固定 30KB
- **传感器噪声**：IMU 数据需要滤波和校准，不能直接用原始值
- **安全边界**：电机失控可能伤人，必须有看门狗、电机超时保护、低电量自动降落
- **通信延迟**：无线链路（CRTP 协议）有丢包和延迟，控制算法必须容忍通信抖动

## 4. 技术架构分析

基于源码结构推断，Crazyflie 固件采用四层架构：

```
┌─────────────────────────────────────┐
│  应用层 (modules/)                  │
│  - system: 系统初始化与任务编排     │
│  - controller: PID/MPC 飞行控制     │
│  - estimator: 卡尔曼滤波姿态估计   │
│  - commander: 接收遥控指令          │
│  - stabilizer: 1kHz 控制主循环      │
├─────────────────────────────────────┤
│  硬件抽象层 (hal/, platform/)       │
│  - sensors: IMU/气压计/磁力计接口   │
│  - motors: PWM 电机驱动             │
│  - storage: EEPROM/Flash 持久化     │
│  - platform: 板级初始化、时钟配置   │
├─────────────────────────────────────┤
│  驱动层 (drivers/)                  │
│  - I2C/SPI/GPIO 外设驱动            │
│  - NRF24L01 无线收发驱动            │
│  - MPU9250/LPS25H 等传感器驱动     │
├─────────────────────────────────────┤
│  扩展层 (deck/)                     │
│  - Deck 热插拔发现与注册            │
│  - GPIO/Analog/SPI 扩展 API         │
│  - 扩展板驱动（光流、激光测距等）   │
└─────────────────────────────────────┘
```

**启动流程**（基于 `src/init/main.c`）：
1. `check_enter_bootloader()`：检查是否需要进入 DFU 模式
2. `platformInit()`：检测硬件平台，初始化时钟、GPIO
3. `systemLaunch()`：创建 FreeRTOS 系统任务，按优先级启动各模块
4. `vTaskStartScheduler()`：启动调度器，控制权移交 RTOS

**任务优先级体系**（基于 `config.h`）：
- 优先级 5：stabilizer（控制环）、passthrough（直通模式）
- 优先级 4：sensors（传感器采集，1kHz 阻塞等待）
- 优先级 2-3：通信、ADC、光流
- 优先级 0-1：日志、参数同步

**通信协议**：CRTP（Crazy Radio Transfer Protocol），基于 nRF24L01 的轻量级无线协议，支持日志流、参数读写、遥控指令。

## 6. 核心模块/函数导读

### 6.1 `platformInit()` - 板级初始化

**角色**：检测当前运行硬件是否为 Crazyflie 2.x，初始化时钟树、GPIO 默认状态、MCU ID 读取。

**工程意义**：嵌入式固件必须知道自己跑在什么硬件上。`platformInit()` 返回错误码时直接 `while(1)` 死循环，这是嵌入式中常见的"fail-fast"策略——宁可停机也不在错误硬件上运行。

### 6.2 `sensorsWaitDataReady()` - 传感器同步

**角色**：阻塞等待直到传感器数据就绪（通常由 DMA 完成中断或定时器触发），保证控制环以精确 1kHz 运行。

**工程意义**：这是典型的"事件驱动 + 周期任务"混合模式。传感器任务不是 `sleep(1ms)`，而是等待硬件中断，避免累积误差。类比后端中的"消息队列消费者"，但延迟要求是硬实时的。

### 6.3 控制环主循环（stabilizer 任务）

**角色**：以 1kHz 周期执行：读取传感器 → 姿态估计 → 计算控制量 → 输出 PWM。

**工程意义**：这是整个固件的"心脏"。任何超过 1ms 的阻塞都会导致飞行器失稳。类比高频交易系统的撮合引擎——延迟抖动直接导致业务失败。

### 6.4 Deck 发现机制

**角色**：通过 I2C 扫描或 GPIO 检测，自动识别插入的扩展板，加载对应驱动。

**工程意义**：这是嵌入式中的"插件系统"。类比 Linux 内核的 `MODULE_DEVICE_TABLE` 或 Node.js 的 `require()` 动态加载，但必须处理硬件时序（上电顺序、I2C 枚举延迟）。

### 6.5 CRTP 通信栈

**角色**：封装 nRF24L01 驱动，提供日志流、参数读写、遥控指令的可靠传输。

**工程意义**：无线链路不可靠，CRTP 实现了简单的 ACK/重传机制。类比 TCP 在 UDP 上的可靠层，但为了低延迟牺牲了部分可靠性（控制指令不重传，只重传参数）。

## 7. 软件工程师类比解释

| 嵌入式概念 | 软件工程类比 | 类比局限 |
|-----------|-------------|---------|
| FreeRTOS 任务优先级 | 后端微服务优先级队列 | RTOS 优先级是硬抢占，高优先级任务可以打断低优先级；后端队列只是调度顺序，不会中断正在执行的请求 |
| 传感器 HAL | 数据库 ORM | HAL 屏蔽硬件差异，但 ORM 屏蔽的是 SQL 方言；HAL 的延迟是微秒级且确定性的，ORM 延迟不可预测 |
| Deck 热插拔 | Kubernetes Sidecar 注入 | Deck 是物理插入后自动发现并加载驱动；Sidecar 是部署时注入，没有"运行时热插拔"语义 |
| 1kHz 控制环 | 高频交易撮合引擎 | 两者都要求低延迟，但控制环是硬实时（错过 deadline = 坠机），撮合引擎是软实时（延迟高 = 亏钱但不崩溃） |
| CRTP 协议 | gRPC over HTTP/2 | CRTP 是轻量级二进制协议，为低延迟优化；gRPC 基于 HTTP/2，有流控和头部压缩，延迟更高但功能更强 |

## 8. 今日 10 个嵌入式概念卡片

### 卡片 1：硬实时系统（Hard Real-Time）
- **一句话**：必须在严格时间窗口内完成任务，否则系统失败（如飞行器坠毁）。
- **软件工程类比**：SLA 99.999% 的支付系统，但嵌入式是"100% 必须满足"。
- **常见场景**：电机控制、安全气囊触发、医疗起搏器。
- **坑点**：很多人把 `sleep(1ms)` 当硬实时，实际上 OS 调度抖动可能超过 10ms。

### 卡片 2：DMA（Direct Memory Access）
- **一句话**：外设直接读写内存，不经过 CPU，释放 CPU 做其他计算。
- **软件工程类比**：异步 I/O 中的零拷贝（zero-copy），如 Linux 的 `splice()`。
- **常见场景**：ADC 采样、UART 收发、电机 PWM 更新。
- **坑点**：DMA 传输期间 CPU 可能读到半更新的数据，必须用双缓冲或互斥。

### 卡片 3：看门狗定时器（Watchdog Timer）
- **一句话**：硬件定时器，固件必须周期性"喂狗"，否则自动复位 MCU。
- **软件工程类比**：Kubernetes 的 liveness probe，超时重启 Pod。
- **常见场景**：防止固件死循环或任务卡死。
- **坑点**：喂狗操作不能放在高优先级任务里，否则低优先级任务卡死时高优先级仍在喂狗，看门狗不触发。

### 卡片 4：I2C 总线枚举
- **一句话**：主设备扫描 0x00-0x7F 地址，检测哪些从设备应答。
- **软件工程类比**：服务发现（如 Consul、Nacos），但 I2C 是物理层扫描，不是逻辑注册。
- **常见场景**：Deck 扩展板识别、多传感器共存。
- **坑点**：I2C 枚举慢（每个地址需要几毫秒），不能阻塞主控制环。

### 卡片 5：PID 控制器
- **一句话**：根据误差的比例、积分、微分计算控制量，是最经典的闭环控制算法。
- **软件工程类比**：自动扩缩容的反馈控制器（如 K8s HPA 根据 CPU 使用率调整副本数）。
- **常见场景**：温度控制、电机转速、无人机姿态。
- **坑点**：积分饱和（integral windup）会导致超调，必须加限幅或反向积分。

### 卡片 6：FreeRTOS 堆大小
- **一句话**：`FREERTOS_HEAP_SIZE` 是 RTOS 管理的内存池，任务栈和队列从这里分配。
- **软件工程类比**：JVM 的 `-Xmx`，但嵌入式堆是固定大小，溢出直接崩溃。
- **常见场景**：Crazyflie 设置 30KB，STM32F4 总 RAM 192KB，剩余给栈和静态变量。
- **坑点**：`pvPortMalloc()` 失败时不会抛异常，返回 NULL，必须检查。

### 卡片 7：PWM（Pulse Width Modulation）
- **一句话**：通过调节脉冲占空比控制电机转速或 LED 亮度。
- **软件工程类比**：限流算法中的令牌桶，占空比 = 令牌发放速率。
- **常见场景**：电机驱动、舵机控制、背光调节。
- **坑点**：PWM 频率太低时电机会有可听见的啸叫，通常设置在 20kHz 以上。

### 卡片 8：姿态估计（Attitude Estimation）
- **一句话**：融合加速度计、陀螺仪、磁力计数据，计算飞行器的俯仰/横滚/偏航角。
- **软件工程类比**：多数据源融合的用户画像系统，但嵌入式用的是卡尔曼滤波或互补滤波。
- **常见场景**：无人机、VR 头盔、手机屏幕旋转。
- **坑点**：加速度计短期噪声大，陀螺仪长期漂移，必须互补融合。

### 卡片 9：DFU 模式（Device Firmware Upgrade）
- **一句话**：通过 USB 或无线更新固件，无需调试器。
- **软件工程类比**：蓝绿部署或金丝雀发布，但嵌入式 DFU 是全量替换，没有回滚（除非双 bank）。
- **常见场景**：OTA 升级、产线烧录。
- **坑点**：DFU 过程中断电会导致变砖，必须有 bootloader 保护。

### 卡片 10：Deck 扩展机制
- **一句话**：Crazyflie 的模块化扩展接口，支持热插拔光流、激光测距、LED 环等。
- **软件工程类比**：浏览器扩展或 VSCode 插件，通过 manifest 声明能力，运行时加载。
- **常见场景**：科研定制、教育实验。
- **坑点**：Deck 插入时可能产生电源浪涌，必须做软启动和去抖。

## 10. 3 道深度追问题

### 问题 1：时序与并发

**如果传感器任务因 I2C 总线被 Deck 枚举阻塞了 50ms，控制环会发生什么？系统会坠毁吗？**

提示：思考控制环是否依赖最新传感器数据，是否有超时保护，PID 积分器在数据缺失时如何表现。

### 问题 2：软件工程视角转嵌入式视角

**在后端系统中，我们通常用"重试 + 超时 + 熔断"处理服务不可用。如果把这个模式套用到传感器驱动，哪些地方会出问题？**

提示：思考传感器数据的时间敏感性、重试导致的延迟累积、熔断后控制环的行为。

### 问题 3：资源限制

**Crazyflie 的 FreeRTOS 堆只有 30KB，如果要加一个日志任务，每秒记录 100 个浮点数（400 字节），持续 10 秒，需要多少内存？如果放不下，有什么替代方案？**

提示：思考环形缓冲区、压缩存储、流式传输到 PC 端。

## 12. 工程点评

### 可维护性 ⭐⭐⭐⭐⭐
模块分层清晰，HAL 抽象彻底，Deck 机制让硬件扩展不影响核心固件。文档和注释质量高，社区活跃。

### 可移植性 ⭐⭐⭐⭐
平台层抽象了 STM32F4 的具体型号，但底层仍依赖 ST HAL 库。移植到其他 MCU（如 ESP32）需要重写 drivers 层。

### 可靠性 ⭐⭐⭐⭐⭐
有看门狗、电机超时保护、传感器校准检查、低电量保护。12 年的迭代让边界情况处理非常成熟。

### 可测试性 ⭐⭐⭐⭐
有单元测试框架，支持在 PC 上模拟传感器和控制环。但硬件相关的测试（如 Deck 热插拔）仍需真实设备。

### 量产/运维 ⭐⭐⭐⭐
支持 DFU 无线升级、参数持久化、日志回传。但缺乏远程批量管理能力（适合教育/科研，不适合大规模商用机队）。
