# 每日嵌入式学习：RTIC

## 1. GitHub 项目链接与一句话介绍

- 仓库链接：https://github.com/rtic-rs/rtic
- **一句话介绍**：RTIC（Real-Time Interrupt-driven Concurrency）是一个用 Rust 编写、以硬件中断为调度引擎的实时并发框架，让单片机上的多个实时任务像普通 Rust 程序一样安全地并发执行，不需要动态内存分配。

## 2. 为什么今天选它

- **活跃度**：最近一次提交为 2026 年 8 月 12 日（就在本周）；最新版本 v2.3.0 于 2026 年 7 月 8 日发布，v2.2.0 于 2025 年 6 月发布，版本节奏稳定。仓库约 2379 颗星、260 个 fork，是 Rust 嵌入式生态里最核心的框架之一。
- **工程完整度**：它不是一个玩具 demo，而是一个完整的多 crate workspace：应用宏、编译期分析器、运行期原语、同步原语、时钟抽象、多架构后端（Cortex-M 两种后端、RISC-V 三种后端），配套有整本书级别的文档（rtic.rs Book）、每周社区会议和 Matrix 群。
- **学习价值**：它把"调度器、临界区、优先级、定时器队列"这些嵌入式最硬核的概念，用编译期检查和类型系统变成了可读的 Rust 代码。对软件工程师来说，这是理解实时系统内核机制的最佳入口：你能直接读到调度如何发生、锁如何被消除、栈如何被共享，而不是面对一团汇编。
- **为什么适合软件工程师**：你是先会写应用层代码的人，RTIC 的"编译器帮你生成调度代码"的思路，和你在后端见过的代码生成、ORM、DSL 一脉相承；同时它又逼你面对中断、优先级、无堆这些嵌入式特有的约束，正好完成从"纯软件"到"软硬一体"的思维切换。

## 3. 项目解决的问题

- **真实场景**：一个典型的 MCU 产品里，传感器中断、通信收发、控制回路、状态机更新往往同时发生。传统做法是裸机大循环加中断标志位，或者用 C RTOS 手动管理任务和锁。RTIC 解决的是：在资源极其有限（几十 KB RAM、无 MMU、无堆或不想用堆）的单片机上，如何安全地实现抢占式多任务，并且把数据竞争、死锁这类问题尽量在编译期消灭。
- **和普通软件项目相比多出的约束**：
  - 硬件中断优先级只有有限级数（Cortex-M 通常可配置 8～256 级，实际常用 16 级以内），任务优先级映射到硬件上，调度器"住在"中断控制器里，而不是一个软件线程。
  - RAM/ROM 预算以 KB 计，不能随便开线程栈、不能依赖堆分配器；RTIC 的同优先级软件任务共享一个异步栈。
  - 时序是硬约束：中断响应延迟、临界区长度、任务最坏执行时间（WCET）都影响产品是否丢数据、是否错过控制周期。
  - 可靠性要求：现场设备不能随便重启，内存安全、无死锁、无数据竞争是基本盘，RTIC 用编译期检查给出强于运行期互斥锁的保证。

## 4. 技术架构分析

仓库是一个 Cargo workspace，核心 crate 分工如下：

- **rtic（门面 crate）**：用户依赖的入口，重新导出 `#[app]` 宏、`Mutex`/`Exclusive` 等类型，并包含 `export` 模块。`export` 下按后端拆分：`cortex_basepri.rs`（利用 Cortex-M BASEPRI 寄存器）、`cortex_source_mask.rs`（利用 PRIMASK 中断屏蔽）、`riscv_esp32c3/c6`、`riscv_slic`（RISC-V 软件中断后端），通过 `#[cfg(implementation = "...")]` 特性选择编译哪一套实现。这就是"硬件抽象"：同一套任务模型，不同芯片只换后端。
- **rtic-macros（编译期核心）**：`#[app]` 是过程宏属性，管线分五步：`syntax`（解析用户写的任务/资源声明）→ `preprocess`（按后端修正）→ `analyze`（做优先级、资源访问、天花板分析）→ `check`（语义检查）→ `codegen`（生成真正的调度代码和类型）。也就是说，调度器的大部分"逻辑"发生在编译期。
- **rtic-core / rtic-common（运行期原语）**：`Mutex`、`Exclusive` 类型，等待队列（双向链表）、waker 注册等底层机制。
- **rtic-sync（同步原语）**：为无堆系统设计的 `channel`（MPSC 异步通道）、`signal`、`watch`、`arbiter`。channel 内部用 `heapless::Deque` 做空闲队列和就绪队列，数据槽位 `slots: [UnsafeCell<MaybeUninit<T>>; N]` 静态分配，队列长度 N 上限 255，靠临界区加 waker 实现异步收发。
- **rtic-time / rtic-monotonics（时间抽象）**：定义 `Monotonic` trait（单调时钟），并内置了各主流 MCU 的实现：Cortex-M 的 SysTick、RP2040/RP235x、i.MX RT 的 GPT、nRF52 的 TIMER/RTC、Silabs 的 LETIMER/RTCC、ESP32C3/C6 的 SYSTIMER、STM32 的各定时器。软件任务的延时、周期任务都挂在基于该时钟的定时器队列上。
- **book/ 与 examples/**：整本书的源码（by-example 与 internals 两大部分），以及跑在真实板子和 QEMU（lm3s6965）上的示例。

**运行流程**：启动后先执行 `#[init]` 初始化资源与外设，再进入 `#[idle]` 空闲任务；硬件中断到来时，NVIC 按优先级抢占，对应 `#[task(binds = ...)]` 的硬件任务被触发；软件任务由 `spawn` 触发——RTIC 通过写 NVIC 的挂起寄存器软件触发一个专用中断来"唤醒"任务，让硬件完成调度；任务间共享数据通过资源代理 + 临界区访问，临界区用 BASEPRI 临时抬高动态优先级实现，其高度由编译期算出的"资源天花板"决定。

## 5. 源码陪读：今天只读哪几个文件

按顺序读这 5 个文件，从"最小可运行"到"底层机制"：

1. `examples/lm3s6965/examples/smallest.rs` —— 读目标：认识 RTIC 应用的最小骨架（`#[app]`、`init`、`idle`），这是所有应用的起点，且能在 QEMU 里直接跑。
2. `rtic/src/lib.rs` —— 读目标：看 `RacyCell<T>` 如何用 `UnsafeCell` 替代 `static mut` 存储资源，以及它注释里写的三条内存安全保证；这是"Rust 安全封装裸指针"的范例。
3. `book/en/src/internals/ceilings.md` —— 读目标：理解资源天花板（ceiling）怎么算：取所有访问该资源的任务中最高逻辑优先级；任务优先级等于天花板时拿到 `&mut` 直接访问，否则拿到资源代理。
4. `rtic/src/export.rs` 与 `export/cortex_basepri.rs` —— 读目标：看后端抽象怎么用 cfg 特性切换，BASEPRI 临界区如何实现（抬高动态优先级而非简单关中断）。
5. `rtic-sync/src/channel.rs` —— 读目标：看无堆 MPSC 通道的工程实现：空闲队列/就绪队列双 Deque、waker 注册、数据搬运不全程持锁。

## 6. 核心模块/函数导读

- **`#[app]` 过程宏（rtic-macros/src/lib.rs 的 `pub fn app`）**：整个框架的入口。它把用户声明转换成完整的调度程序：静态分配所有任务状态、生成中断向量表初始化、按分析结果生成临界区。工程角色：相当于后端的"框架容器 + 依赖注入"，但产出物不是对象图而是裸机代码。
- **`RacyCell<T>`（rtic/src/lib.rs）**：资源的存储单元，`#[repr(transparent)]` 包装 `UnsafeCell<T>`，只允许 RTIC 内部通过 `get_mut`/`get` 拿裸指针，唯一可变引用的保证由编译期分析背书。工程角色：把"全局可变状态"关进一个类型里，外部无法绕过规则访问。
- **`Mutex` / `Exclusive`（rtic-core）**：资源代理的两种形态。优先级低的任务拿到的是 `Mutex`（需 `lock` 进临界区），优先级等于天花板的任务拿到 `Exclusive`（`&mut` 直接访问）。工程角色：锁的"所有权"由编译器按优先级分配，而不是运行时抢。
- **`export::pend` 与中断挂起机制**：软件任务被 `spawn` 后，RTIC 并不直接调用函数，而是写 NVIC 挂起寄存器软件触发中断，让硬件按优先级排队执行任务。工程角色：这是"用硬件做调度器"的核心，也是 RTIC 自称 hardware accelerated 的原因。
- **`Channel<T, N>`（rtic-sync/src/channel.rs）**：无堆 MPSC 异步通道。内部 `freeq`（空闲槽索引）与 `readyq`（就绪槽索引）两个 `heapless::Deque<u8, N>`，`slots` 静态数组存数据，`receiver_waker` 注册唤醒器。工程角色：任务间通信的"消息队列"，但零堆、定长、上限 255。
- **`Monotonic` trait 与 `systick` 实现（rtic-time / rtic-monotonics）**：为 `delay`、周期任务、定时器队列提供单调时钟抽象。工程角色：嵌入式里的"时间服务"，把不同芯片的定时器外设统一成一个接口。

## 7. 软件工程师类比解释

- **硬件任务 ≈ 事件驱动的消费者**：`#[task(binds = UART0)]` 就像后端里"消息队列的消费者回调"，事件一来就被触发。**这个类比的局限是**：ISR 在硬件优先级上运行，必须短小、不能阻塞，也没有"等锁"的奢侈；后端消费者可以慢慢处理甚至丢弃消息，ISR 处理慢了会直接导致中断丢失或系统错乱。
- **资源天花板（ceiling）≈ 数据库行锁的"等级"**：谁访问某资源，锁的等级就是谁的最高优先级，低优先级任务访问时要"升级"自己。**这个类比的局限是**：数据库锁是运行期动态获取的，天花板是编译期静态算死的；也因此 RTIC 的临界区不需要"抢锁"，代价是设计期就要定死任务优先级。
- **编译期代码生成（codegen）≈ ORM/代码生成器**：`#[app]` 宏把声明式代码翻译成大量底层实现，就像 ORM 根据实体生成 SQL。**这个类比的局限是**：ORM 生成的是可读性尚可的代码，RTIC 生成的代码你基本不会去读；宏报错信息、编译时间、调试体验是它的软肋。
- **无堆 + 静态分配 ≈ 服务端热路径的"零分配"**：RTIC 所有数据结构编译期定死，同优先级软件任务共享一个异步栈，就像后端在 GC 停顿敏感的热路径上禁用分配。**这个类比的局限是**：后端零分配只是优化手段，MCU 上是"根本没有堆可用"的硬约束，数据结构的规模必须在编译期拍板。
- **定时器队列 ≈ 定时任务调度器（cron/Sidekiq）**：`Monotonic` 时钟 + 定时器队列实现 `delay` 和周期任务。**这个类比的局限是**：MCU 只有一个单调时钟源，没有墙钟、没有时区，还要处理定时器溢出回绕；你无法像服务器那样"到点没跑就补跑"。

## 8. 今日 10 个嵌入式概念卡片

1. **中断优先级（NVIC）**：硬件给每个中断分配的抢占等级，数字越小优先级越高（Cortex-M）。软件工程类比：操作系统线程优先级。常见场景：把控制回路放最高优先级，通信放低优先级。坑点：优先级是有限、离散的，不是 0～99 随便排。
2. **抢占式调度**：高优先级任务随时打断低优先级任务。类比：抢占式线程调度。场景：RTIC 中硬件任务直接由 NVIC 抢占。坑点：抢占点不可预测，共享数据必须走临界区。
3. **临界区**：禁止其他任务进入的一段代码，保护共享资源。类比：互斥锁的加锁区间。场景：RTIC 用 BASEPRI 抬高动态优先级实现。坑点：临界区越长，系统实时性越差，要短。
4. **优先级天花板协议（ICPP）**：访问共享资源时把优先级临时抬到所有使用者中的最高级，防止优先级反转。类比：数据库锁的等级提升。场景：RTIC 编译期算好每个资源的天花板。坑点：天花板过高会让低优先级任务长时间被"锁在外面"，共享资源要少而专。
5. **资源代理（Resource Proxy）**：编译器按任务优先级分发资源的访问形态，低优先级拿到需加锁的代理，高优先级拿到直接引用。类比：依赖注入的接口分派。场景：`resources = [x]` 声明后自动生成。坑点：形态是编译期决定的，运行时没有"换锁"余地。
6. **定时器队列**：按时间排序的待执行任务链表，由单调时钟驱动。类比：定时任务调度器。场景：RTIC 软件任务的 `delay` 与周期任务。坑点：时钟溢出回绕必须用无符号差值处理。
7. **消息传递（spawn 传参）**：任务间通过 `spawn` 传数据，而不是共享可变状态。类比：消息队列/事件总线。场景：传感器任务把读数 spawn 给处理任务。坑点：定长消息，超长数据要传指针或分段。
8. **无堆（no_alloc）**：所有内存编译期静态分配，运行期不 malloc。类比：热路径零分配。场景：`Channel<T, N>` 的定长槽位。坑点：队列长度、任务状态必须设计期拍板，改大小要重新编译。
9. **waker（唤醒器）**：异步任务在资源不可用时挂起，资源可用时被唤醒。类比：epoll 的就绪通知、协程调度器。场景：RTIC channel 的接收端等待。坑点：忘记唤醒会导致任务永远睡死，这是异步嵌入式最隐蔽的 bug。
10. **后端抽象（cfg 特性选实现）**：同一套 API 通过特性开关选择不同芯片的实现。类比：基础设施里的驱动适配层。场景：`cortex-m-basepri` 与 `riscv-slic` 后端切换。坑点：不同后端语义有细微差别（如临界区实现），换芯片要回归测试。

## 9. 30～60 分钟动手任务

- **目标**：不花一分钱硬件，在 QEMU 里跑起 RTIC 最小程序，并观察它的内存占用。
- **步骤**：
  1. 安装 Rust 与 `thumbv7m-none-eabi` 目标：`rustup target add thumbv7m-none-eabi`。
  2. 克隆仓库：`git clone https://github.com/rtic-rs/rtic.git`，进入 `examples/lm3s6965` 目录。
  3. 安装 QEMU（`apt install qemu-system-arm`）与 OpenOCD 不需要；直接跑：`cargo run --example smallest`（该示例工程已配置 QEMU 启动），看到串口输出即成功。
  4. 查看资源占用：`cargo xtask size --example smallest --backend thumbv7`，记录 flash 与 RAM 数值。
- **验收标准**：QEMU 中程序正常启动并周期性输出；`smallest` 的 flash 占用在 1KB 左右量级（官方文档称含中断向量表小于 1KB）；你能说出这个数字和服务器上一个空 Go 二进制（几 MB）差了多少个数量级。
- **无硬件替代**：本任务本身即无硬件方案；如果连 QEMU 都不想装，退而求其次：只读 `smallest.rs` 源码 + `book/en/src/by-example/app_minimal.md`，在纸上画出 `init → idle → 中断触发任务` 的执行时序。

## 10. 3 道深度追问题

1. **（时序/并发）** RTIC 文档说"同优先级的软件任务共享一个异步栈"。请分析：如果任务 A 在 `await` 点挂起、任务 B 开始执行并修改了共享资源，A 恢复时会发生什么？RTIC 是靠什么机制保证这种情况下不会踩坏彼此的状态？如果让你给这个共享栈模型加一个"任务 C 动态插入"的能力，你会怎么设计？
2. **（软件转嵌入式视角）** 你在后端写过一个高吞吐消息处理服务：线程池 + 有界队列 + 背压。现在同样的需求落到只有 16 级硬件优先级、几十 KB RAM 的 MCU 上，且 `Channel<T, N>` 的 N 上限是 255。请设计：什么数据放中断里直接处理、什么数据走 channel、channel 满时你选择丢数据还是丢实时性？为什么？
3. **（工程判断）** RTIC 用编译期天花板协议消除了运行期锁和死锁，但代价是"优先级必须设计期定死"。请对比：一个用 C + FreeRTOS 写的产品，和一个用 RTIC 写的产品，在需求后期突然要"新增一个必须抢占现有任务的新功能"时，各自的改造成本分别在哪？编译期保证在什么时候反而成为负担？

## 12. 工程点评

- **可维护性**：类型系统把任务、资源、优先级都变成可检查的声明，配合整本书级文档与大量示例，新成员上手路径清晰；过程宏生成的代码不可读是主要维护痛点。
- **可移植性**：后端抽象做得非常干净，同一份应用代码可切 Cortex-M / RISC-V 后端；`Monotonic` trait 让换定时器外设不碰业务代码。换后端仍需回归测试，因为临界区实现细节不同。
- **可靠性**：v2.3.0 的 changelog 里明确写着"Soundness fix: 断言 init 初始化的 Local 资源是 Send"——说明项目把内存安全当一等公民，soundness 修复可进 patch 版本；无堆、无运行期锁从结构上消灭了一整类 bug。
- **可测试性**：有 loom 并发测试、UI 测试（编译错误快照）、QEMU 示例，测试设施在嵌入式项目里属于顶配。
- **量产/运维**：1KB 级 flash 占用、无堆、WCET 可分析，适合对成本和时序敏感的产品；但 Rust 工具链、宏编译时间、以及"优先级必须设计期定死"的约束，要求团队在架构阶段就做足功课，现场调优空间小。
