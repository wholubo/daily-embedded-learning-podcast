# 每日嵌入式学习：U-Boot

## 1. GitHub 项目链接与一句话介绍

- 仓库链接: https://github.com/u-boot/u-boot （Das U-Boot，U-Boot 官方仓库，Git 主仓在 git.u-boot-project.org，GitHub 为镜像）
- **一句话介绍**：Das U-Boot 是嵌入式 Linux 世界事实标准的引导加载程序，负责在板子上电后初始化 CPU、DDR、串口、存储等硬件，再把 Linux 内核或裸机程序加载进内存并跳转执行。
- 项目状态：C 语言，约 5158 stars、4543 forks，仓库体积超过 300MB（含完整历史）；默认分支 main，最近一次推送 2026-07-31（昨天仍在合入各子系统维护者的代码），当前处于 v2026.10 开发周期（一年四个版本：01/04/07/10）。许可证为 GPL-2.0+。

## 2. 为什么今天选它

- 活跃度：U-Boot 是 Linux 基金会体系下最活跃的引导项目之一，每天都有来自几十个维护者子树的合入，昨天还有 2026.10 的 rc 标签合入，属于"永远不会死"的基础软件。
- 工程完整度：它是一套完整的现代 C 工程：Kconfig/Kbuild 构建、configs/ 下上千个板卡 defconfig、doc/ 用 Sphinx 生成文档、scripts/ 里有 checkpatch 和 get_maintainer.pl、自带 sandbox 目标可以在 Linux 用户态直接跑、还有 Azure/GitLab CI 和 pytest 测试。
- 学习价值：它是"软件与硬件交界处"最典型的大型开源项目——没有操作系统兜底，所有内存、时序、外设都由它自己管理。对纯软件工程师来说，它把"启动"这件事从黑盒变成可以逐行读的代码：从 ROM 里的第一段汇编，到 SPL 初始化 DDR，到重定位，再到把内核交给系统。学会 U-Boot 的思维，等于拿到了所有嵌入式 Linux 产品的"开机钥匙"。

## 3. 项目解决的问题

- 真实场景：一块跑 Linux 的开发板（路由器、机顶盒、工控机、汽车仪表、机器人控制器）上电后，片上 ROM 只认识固定的启动介质；DDR 还没初始化，任何 C 代码都无法运行。U-Boot 就是那个"在裸金属上把硬件拉起、把系统请进来"的程序。产品量产时还要靠它做工厂烧录、A/B 分区升级、串口恢复模式。
- 与普通软件项目相比多出来的约束：
  - 无运行时依赖：启动早期连"可写内存"都没有，代码可能要从只读的 flash 里执行，BSS 段都还没清零。
  - 资源极紧：SPL 阶段可能只有几十 KB SRAM 可用，连完整 U-Boot 都装不下，所以要分阶段引导。
  - 时序约束：硬件初始化有严格顺序（时钟→DDR→串口→存储），中间还要不断喂看门狗，否则芯片会被硬件定时器强制复位。
  - 可靠性约束：环境变量存在 flash 里，有 CRC 校验、写磨损、掉电写一半的问题；引导失败要有 fallback 路径，否则产品变砖。

## 4. 技术架构分析

- 顶层模块划分：arch/（CPU 架构相关，ARM/RISC-V/x86/MIPS 等）、board/（具体板卡代码）、drivers/（驱动模型 DM 下的所有驱动）、cmd/（命令行命令）、common/（核心初始化，board_f.c/board_r.c 在这里）、boot/（标准启动 bootstd 等）、env/（环境变量）、fs/、net/、lib/、dts/（设备树）、common/spl/（SPL/TPL/VPL 分阶段引导）、doc/、test/、tools/（mkimage、binman 等主机工具）。
- 运行流程（引导链）：片上 ROM → SPL（小体积第一级，初始化 DDR 并加载主 U-Boot）→ U-Boot 本体。U-Boot 本体分两个阶段：board_init_f 在重定位前运行（此时代码可能在 flash 里、只有少量可写内存），完成时钟、DDR、串口初始化并规划好内存布局；然后把自己整体搬运到 RAM 顶部（重定位），再进入 board_init_r 完成剩余初始化，最后进入 main_loop 命令行，执行 bootflow scan / bootm 启动内核。
- 硬件抽象：U-Boot 驱动模型（Driver Model，DM）用 uclass/driver/device 三个概念统一所有驱动：uclass 是"一类设备的接口"（比如 GPIO 的读写、I2C 的收发），driver 是具体实现，device 是绑定了某个硬件实例的对象。设备树（FDT）以声明式数据描述硬件拓扑，DM 在运行时把设备树节点和 driver 匹配起来。
- 配置系统：Kconfig 负责编译期开关，configs/*_defconfig 保存板卡默认配置；运行期配置靠环境变量（env），存在 flash/MMC 上，带 CRC 校验。
- 通信/存储/升级：支持 MMC、USB、网络（TFTP/NFS）、串口等加载途径；镜像格式有传统 uImage 和 FIT（多组件、可签名）；UEFI 支持让它能引导 Windows/标准发行版；标准启动（standard boot）用 bootdev/bootmeth/bootflow 抽象"从哪个设备、用什么方法、找到什么启动描述"。
- 说明：以上分析基于官方源码与 doc/ 目录公开文档，部分细节（如具体板卡的 memory map）因板而异，未逐一核对。

## 5. 源码陪读：今天只读哪几个文件

推荐按引导链的时间顺序读这 5 个文件，每个都控制在"读关键函数"的粒度：

1. common/spl/spl.c —— 第一棒：SPL 的入口逻辑、spl_parse_image_header 解析 U-Boot 镜像头（魔数、加载地址、入口点），理解"小程序加载大程序"。
2. common/board_f.c —— 第二棒：重定位前的初始化序列，核心是 initcall_run_f 里那一长串 INITCALL 宏表，配合注释看内存是如何自顶向下预留的。
3. common/board_r.c —— 第三棒：重定位后的初始化，从 initr_ 系列函数一路看到 run_main_loop 进入命令行。
4. drivers/core/device.c —— 第四棒：驱动模型的心脏 device_probe，看一个设备从"绑定"到"激活"发生了什么。
5. cmd/bootm.c —— 第五棒：bootm 命令的入口 do_bootm，看它如何解析参数、构造 bootm_info、调用 bootm_run 走完启动状态机。

阅读顺序就是 1→5，恰好等于一次完整的开机流程。读的时候建议对照 doc/develop/driver-model/design.rst 和 doc/develop/bootstd/overview.rst 两份文档。

## 6. 核心模块/函数导读

- board_init_f（common/board_f.c）：重定位前的总入口，本质是一张 INITCALL 宏表驱动的顺序初始化管线：setup_ram_base、dram_init（配置 DDR 容量）、dram_init_banksize、然后一串 reserve_*（reserve_video、reserve_trace、reserve_uboot、reserve_malloc、reserve_board、reserve_global_data、reserve_fdt……）从 RAM 顶部向下预留各区域，最后 clear_bss、jump_to_copy 完成重定位。注意表里穿插着 WATCHDOG_RESET，因为硬件看门狗不等你。
- board_init_r 与 run_main_loop（common/board_r.c）：重定位后把 gd->flags 里 SERIAL_READY/LOG_READY 清掉（重定位前驱动用的内存可能已失效），重新初始化中断、网络，发 EVT_LAST_STAGE_INIT 事件，最后 run_main_loop 进入命令行循环。这里能看到 U-Boot 的"事件系统"：用注册的回调代替散落的 ifdef。
- device_probe（drivers/core/device.c）：驱动模型的激活入口。流程：检查 DM_FLAG_ACTIVATED 防重复 → 发 EVT_DM_PRE_PROBE 事件 → device_of_to_plat 从设备树解析平台数据 → 递归探测父设备 → 打开电源域、处理 pinctrl 引脚配置 → 调用 driver 的 probe 回调。这个函数把"设备树→驱动→硬件"串成了一条链。
- uclass_get_device 系列（drivers/core/uclass.c）：驱动使用侧的 API，uclass_get_device_by_driver、uclass_get_device_tail 等，屏蔽"找设备+探测"细节，让上层代码只面向接口编程。
- do_bootm / bootm_run（cmd/bootm.c）：bootm 命令入口。先判断是不是子命令（bootm start/loados/……），解析地址参数（支持 FIT 的 addr:子镜像 和 addr#配置 语法），构造 bootm_info，交给 bootm_run 走状态机。bootm_maybe_autostart 则是"环境变量 autostart 打开时自动启动"的桥。
- spl_parse_image_header（common/spl/spl.c）：SPL 解析加载进来的镜像头：校验魔数、读出 header 里的 payload 大小和入口地址，决定"加载整个 U-Boot"还是"直接跳内核"。spl_start_uboot 等一堆 __weak 函数是板卡定制点——这就是嵌入式里"默认实现可被覆盖"的经典手法。

## 7. 软件工程师类比解释

1. gd 全局数据 ↔ 无框架环境下的请求上下文对象/线程局部存储：整个启动过程只有一个 gd 结构，靠它传递内存布局、波特率、启动标志。局限：ARM 上 gd 占一个专用寄存器，全局只有一份，没有隔离和生命周期管理，任何模块都能改它，出了问题很难追踪。
2. 驱动模型 uclass/driver/device ↔ Go 接口 + 实现 + 依赖注入容器：uclass 是接口，driver 是实现，device 是实例；上层代码面向 uclass 编程，换硬件只换 driver。局限：绑定发生在编译期/链接期，靠设备树 compatible 字符串匹配，探测顺序和副作用（打开电源域、配引脚）是隐式的，不像 DI 容器能自动解析依赖图、也没有循环依赖检测。
3. 设备树 FDT ↔ 声明式基础设施配置（Kubernetes YAML / Terraform）：用数据描述"板上有什么、接在哪、怎么配"，驱动代码和硬件描述解耦。局限：它不是图灵完备语言，不能表达复杂逻辑，不能热加载，改动要重新编译 dtb 并跟着内核/引导程序一起发布。
4. 环境变量 ↔ 12-Factor 配置 + 键值存储：baudrate、bootargs 这些变量决定运行时行为，类似环境变量/配置中心。局限：存在 flash 里，有 CRC 校验但写入有磨损寿命、掉电可能写坏一半，没有事务和版本控制，save 才落盘。
5. INITCALL 宏表 ↔ Spring Boot 自动装配/启动管线的执行顺序：一张静态表定义了初始化顺序，加一个步骤就往表里插一行。局限：完全靠人工排序，没有依赖图推断，也没有失败回滚编排——一个 initcall 返回错误通常就是 hang 住或复位。
6. SPL→U-Boot 分阶段引导 ↔ initramfs→systemd 的分阶段启动：先跑一个最小程序把环境准备好，再交棒给完整系统。局限：每一阶段的内存资源天差地别（SPL 可能只有几十 KB SRAM），不能像用户态那样随意 fork/exec，交棒是"跳转+交出寄存器状态"，没有进程边界。

## 8. 今日 10 个嵌入式概念卡片

1. 交叉编译：在 x86 主机上编译出 ARM/RISC-V 目标机可执行的程序。类比：用 CI 的 mac runner 给 Linux 打产物。场景：任何嵌入式构建。坑：忘了指定工具链前缀，编出来的是主机程序，一上板就段错误。
2. 链接脚本与 TEXT_BASE：链接脚本决定代码段、数据段、BSS 段放在哪个地址，TEXT_BASE 是 U-Boot 期望的运行基址。类比：打包配置里声明"代码部署在哪个地址"。坑：基址和实际运行地址不一致时，绝对跳转全部失效。
3. BSS 段：未初始化全局变量的存放区，启动时统一清零。类比：进程启动时内核帮你清零的静态区。坑：重定位前可能没有可写内存来放 BSS，所以早期代码不能依赖静态变量。
4. 重定位：把代码从 flash 复制到 RAM 顶部，并修正所有绝对地址引用。类比：把容器镜像从 registry 拉到本机并重写启动路径。坑：漏了某个重定位表项，函数指针调用会随机崩溃。
5. gd 全局数据：保存在寄存器里的全局上下文，启动全程传递内存布局等信息。类比：单例 Context。坑：多核/中断上下文里改 gd 会互相踩踏。
6. 设备树 FDT：描述硬件拓扑的二进制数据块，内核和 U-Boot 都读它。类比：一份声明式基础设施清单。坑：compatible 字符串写错一个字母，驱动就静默不匹配。
7. 驱动模型 DM：uclass/driver/device 三层抽象。类比：接口+实现+实例。坑：探测顺序由父子关系隐式决定，循环依赖或电源域没就绪时 probe 失败很难排查。
8. SPL/TPL 分阶段引导：用最小程序初始化关键硬件再加载主程序。类比：bootloader→OS 的两段式启动。坑：每阶段内存预算不同，SPL 里 malloc 很容易爆。
9. 环境变量：flash 里带 CRC 的键值配置。类比：配置中心 KV。坑：写磨损、掉电写坏一半、忘了 save。
10. FIT 镜像与签名：把内核、设备树、ramdisk 打包成一个可校验的多组件镜像。类比：带签名的 OCI 镜像清单。坑：签名验证失败要设计好回退路径，否则设备变砖。

## 9. 30～60 分钟动手任务

目标：无硬件条件下，把 U-Boot 跑起来并亲手追踪一次"开机"。

步骤：
1. 安装依赖：gcc、make、bison、flex、swig、libssl-dev、python3-dev（Debian/Ubuntu 用 apt 装）。
2. 拉源码（今天已拉好 /tmp/uboot_src，也可 git clone --depth 1 https://github.com/u-boot/u-boot）。
3. make sandbox_defconfig && make -j$(nproc)，得到用户态可执行文件 ./u-boot。
4. 运行 ./u-boot -d u-boot.dtb，进入命令行。
5. 依次执行：bdinfo（看内存布局与 gd 信息）、dm tree（看驱动模型树：uclass/device）、env print（看环境变量）、bootflow scan -l（让标准启动扫描可启动介质）、help bootm。
6. 回到源码，在 common/board_f.c 里找到 initcall_run_f 的 INITCALL 表，对照输出解释：是哪一步让串口控制台出现、哪一步规划了 RAM 布局。
7. 进阶（可选）：装 qemu-system-arm，make qemu_arm_defconfig 后用 qemu-system-arm -M virt 启动，体验真实目标机引导。

验收标准：能说出 board_f 阶段至少 3 个 INITCALL 的职责；能从 dm tree 输出中指出一个 uclass、它的 driver 和至少一个 device 实例；bootflow scan 能扫出 bootflow 并说出它来自哪个 bootdev；能解释"为什么 sandbox 能在 Linux 用户态跑 U-Boot"（因为 U-Boot 把硬件访问抽象成了 host 系统调用，这就是可测试性设计）。

## 10. 3 道深度追问题

1. （时序/并发）board_f 的 INITCALL 表里为什么到处穿插 WATCHDOG_RESET？如果某个 initcall 阻塞时间超过看门狗超时，会发生什么？反过来想：你们后端服务里"看门狗"的等价物是什么，为什么它不需要像 U-Boot 这样手动喂？
2. （软件视角转嵌入式视角）device_probe 会递归探测父设备，还会隐式打开电源域、配置 pinctrl。把它和依赖注入容器的懒加载对比：这种"探测副作用"在什么场景下会变成难以排查的 bug？如果让你设计，你会加什么保护机制（超时？依赖声明？死锁检测？）？
3. （资源限制）U-Boot 要把自己搬到 RAM 顶部并自顶向下预留视频、trace、uboot、malloc、board、gd、fdt、bootstage 等区域。为什么重定位之前不能依赖 BSS 和静态可写数据？如果产品 RAM 只有 64MB，而你要保留最大的 malloc 堆，你会优先砍掉哪些 reserve 项、依据是什么？

## 11. 今日复盘问题

如果让你负责一个嵌入式产品的引导加载程序（从烧录到量产升级），你会把"可恢复性"设计成什么样？它和你平时维护的后端服务 SLA 里的"可用性"有什么本质区别——比如，后端可以重启、扩容、回滚，而引导程序一旦坏了，机器可能连重启的机会都没有？

## 12. 工程点评

- 可维护性：Kconfig/Kbuild 统一配置；SPDX 头；scripts/checkpatch.pl 规范风格；get_maintainer.pl 按路径定位负责人；doc/ 用 Sphinx 持续维护；提交按"标签合入"流程管理。对一个三十年历史的项目来说，这套秩序是它能持续演进的关键。
- 可移植性：arch/ + board/ + DM + __weak 默认实现 + defconfig 的组合，让"加一块新板卡"变成"加一个目录+一个配置文件"，这是可移植性的教科书写法。
- 可靠性：看门狗、环境变量 CRC、bootstage 启动阶段记录、FIT 签名校验、SPL/主 U-Boot 分级容错。缺点是错误处理策略偏"简单粗暴"（很多路径直接 hang），这也是裸机软件的现实。
- 可测试性：sandbox 让 U-Boot 在 Linux 用户态跑起来，test/ 目录有 pytest 级联测试，CI 覆盖多架构编译。这是老牌 C 项目里少见的高测试性设计，非常值得学习。
- 量产/运维：工厂烧录、A/B 升级、UEFI 兼容、distro boot 让操作系统发行版在任意硬件上即插即用；镜像打包用 binman，安全启动链支持签名校验。作为一个"开机即用"的组件，它把运维思维做进了固件里。

## 13. 明天可以延展的方向

1. 深入设备树：学 dts 语法与绑定文档，重点看 U-Boot 的 CONFIG_OF_BOARD_FIXUP 如何在运行时修补设备树，再对比 Linux 内核里的设备树用法。
2. 引导链安全：研究 FIT 镜像签名与 verified boot 的完整流程，和你已经学过的 MCUboot、wolfBoot 对照，理解"MCU 安全引导"与"Linux 引导"两条技术线的异同。
3. 从 U-Boot 到内核的交接：精读 bootm 的状态机（bootm_start/loados/go）、EFI stub 引导，以及 U-Boot 驱动模型与 Linux 驱动模型、Zephyr devicetree 体系的横向对比。
