# 每日嵌入式学习：MAVLink

## 1. GitHub 项目链接与一句话介绍

- 仓库：https://github.com/mavlink/mavlink
- **一句话介绍**：MAVLink（Micro Air Vehicle Message Marshalling Library）是无人机与地面站之间的轻量级二进制通信协议库，用 XML 定义消息集、用代码生成器产出多语言源码，专门服务于带宽极低、链路不可靠的数传场景，是 PX4、ArduPilot、QGroundControl 等整个无人机生态的互操作底座。

## 2. 为什么今天选它

- 活跃度：master 分支在 2026-08-12 仍有提交，仓库约 2391 星；它不是某个公司的内部协议，而是由 Dronecode 社区维护的开放标准，常年有真实提交和版本演进（MAVLink 1 诞生于 2009 年，MAVLink 2 于 2017 年前后引入）。
- 工程完整度：仓库里同时具备三样东西——消息集规范（XML 方言）、代码生成器（mavgen）、多语言运行时（C 头文件库、Python 的 pymavlink，以及社区维护的 Rust、C#、JavaScript 等实现），外加完整示例和 mavlink.io 文档站，是一个"协议规范 + 工具链 + 运行时"三位一体的完整工程。
- 学习价值：对从纯软件转嵌入式的工程师来说，MAVLink 是最好的"协议工程"入门样本。你熟悉 protobuf、Thrift 那一套 schema 驱动代码生成的思路，MAVLink 正是同一思路在字节级、资源受限、链路不可靠环境下的重写，能直观看到后端经验哪些能迁移、哪些必须让步。

## 3. 项目解决的问题

- 真实场景：飞控（运行在 MCU 上）要跟地面站、遥控器、相机、云台、任务规划器通信。链路往往是 915MHz SiK 数传电台或普通 UART，带宽只有几十到几百 kbps，还有高丢包、半双工、可能被干扰或监听的问题。MAVLink 解决的是"不同厂商的组件如何可靠互操作"——官方 README 原话是"在组件之间充当互操作接口，已经过多产品现场验证"。
- 与普通软件项目相比多出的约束：
  - 资源约束：目标平台是 RAM 以 KB 计、Flash 以几十到几百 KB 计的 MCU，所以 C 参考实现是 header-only、零动态分配。
  - 带宽约束：每条消息要省到字节级，协议不在负载里携带任何自描述信息，双方必须共享同一份消息定义。
  - 链路约束：UART 是字节流没有帧边界，需要自己设计帧同步；链路会丢包、乱序，需要序号和校验和，但没有重传和拥塞控制。
  - 时序约束：失联判定靠心跳超时（典型 1Hz 心跳、3 秒超时触发 failsafe），这是实时系统里"时间即状态"的典型体现。
  - 安全约束：数传链路可被监听、注入，MAVLink 2 因此支持消息签名。
- 关键数字：MAVLink 1 最小包 8 字节、最大 263 字节；MAVLink 2 最小 12 字节、最大 280 字节；负载最长 255 字节；校验用 CRC-16/MCRF4XX。

## 4. 技术架构分析

整体分四层：

- 规范层：message_definitions/v1.0/ 下是一组 XML 方言，minimal.xml 定义最基础消息（如 HEARTBEAT），common.xml 是被广泛使用的公共消息集（约 233 条消息），其余是各厂商扩展方言（ardupilotmega、development 等）。
- 生成层：mavgen 代码生成器读取 XML，按 --lang 生成 C、C++、Python 等语言的序列化代码；--wire-protocol 决定生成 v1 还是 v2 版本。这与 protoc 从 .proto 生成代码是同构的管线。
- 运行时层：C 端是生成的 header-only 库，核心是逐字节喂入的解析状态机 mavlink_parse_char()；Python 端是 pymavlink 子模块，提供连接抽象（udpin、udpout、serial）。
- 应用层：一系列"微服务"协议——心跳、任务（mission）、参数（parameter）、命令（command）、相机、云台等，都是建立在消息之上的有状态交互流程。

关键设计（结合公开文档与示例代码归纳，部分运行细节基于公开文件推断）：

- 字段重排：消息字段在线上按原生长度从大到小排列（8 字节、4 字节、2 字节、1 字节），避免 MCU 上的对齐填充浪费字节；CRC_EXTRA 在重排之后计算，所以重排错了 CRC 也会错。
- 兼容性校验：每条消息有一个 CRC_EXTRA 种子字节，由消息名加按线上顺序的字段类型和名字（数组加长度）算出。收端算出的 CRC 对不上，就说明双方消息定义不一致，直接报 MAVLINK_FRAMING_BAD_CRC 丢弃。
- MAVLink 2 的演进：24 位消息 ID；incompat_flags 与 compat_flags 区分"必须理解否则丢弃"和"不理解也能处理"的特性；发送时截掉负载尾部全零字节省带宽；扩展字段只允许追加在末尾且不参与 CRC_EXTRA，保证旧实现仍能解析；可选 13 字节签名。
- 寻址：sysid 标识系统（一架飞行器），compid 标识系统内组件（飞控、相机、数传），广播地址 0 不能用作源地址。
- 健康上报：SYS_STATUS 用三个 32 位位图分别表示传感器 present/enabled/health，另有主循环负载（千分比）、电池电压（mV）、电流（厘安）、通信丢包率等字段，是整机健康监控的锚点。

## 5. 源码陪读：今天只读哪几个文件

阅读顺序与目标：

1. message_definitions/v1.0/minimal.xml —— 先读 HEARTBEAT（id=0）的定义，理解"一条消息 = 字段 + 类型 + 枚举 + 语义注释"，这是整个协议的最小单元。
2. message_definitions/v1.0/common.xml —— 文件约 690KB、233 条消息，不要通读，重点读 SYS_STATUS（id=1）和 PARAM_VALUE（id=22）、PARAM_SET（id=23）。目标：看懂字段的单位编码（电压 mV、电流 cA、负载 d‰）、无效值哨兵（UINT16_MAX、-1）和位图语义，体会"为省字节连单位都要编码进字段"。
3. examples/c/udp_example.c —— 真实收发循环：把 UDP 收到的每个字节喂给 mavlink_parse_char()，返回 1 就拿到一帧，switch(msgid) 分发，再 decode。目标：建立"字节流状态机"的心智模型。
4. 本地生成的头文件（按 README 用 mavgen 从 common.xml 生成）—— 读 mavlink_helpers.h 里的解析状态机和 mavlink_msg_*.h 里某个消息的 pack/decode。目标：看生成代码如何实现字段重排和 CRC。
5. pymavlink 子模块里的 mavutil.py —— 看连接抽象和 udpin/udpout/serial 的封装。目标：对比高层 API 与 C 底层的差别。

## 6. 核心模块/函数导读

- mavlink_parse_char(chan, c, msg, status)：核心入口，逐字节有限状态机。找 STX 魔数（v1 是 0xFE，v2 是 0xFD）→ 收头部 → 收负载 → 校验 CRC → 返回 1 表示完整一帧。它是"在无帧边界的字节流上恢复帧结构"的教科书实现，和你在后端解析 TCP 粘包是同一类问题，只是发生在单字节中断或轮询循环里。
- mavlink_msg_heartbeat_pack / encode / decode：生成器为每条消息产出的对称接口。pack 时做字段重排、追加 CRC_EXTRA 参与校验；decode 时反向。理解一个消息的这三个函数，就理解了全部消息。
- HEARTBEAT 微服务：1Hz 周期广播，携带 type、autopilot、base_mode、custom_mode、system_status 和协议版本；对端连续约 3 秒收不到就判定失联，触发 failsafe。这是嵌入式里"用周期信号当状态"的典范。
- MAVLINK_MESSAGE_CRCS 表与 CRC_EXTRA：生成期用 x25crc 对"消息名 + 有序字段类型/名字（+数组长度）"求 CRC，异或高低字节得种子。运行期任何一端改了字段名、类型、顺序或长度，CRC 立刻对不上——这是用 1 个字节实现的"协议版本握手"，比后端常见的版本号协商更硬性。
- mavgen（pymavlink.tools.mavgen）：代码生成管线入口，--lang 选语言、--wire-protocol 选 v1/v2、--output 指定输出目录。理解它，你就理解了"规范单一来源"在嵌入式协议里的落地方式。
- SYS_STATUS 的传感器位图：present/enabled/health 三个 32 位位图分别回答"有没有这个传感器、开没开、健不健康"，配合负载、电池、丢包统计，构成整机的健康检查端点。

## 7. 软件工程师类比解释

- XML 消息定义 + mavgen ≈ protobuf 的 .proto + protoc。都是"规范即代码"：改规范、跑生成器、双方同步更新。局限：MAVLink 没有 protobuf 那样丰富的标量类型和嵌套结构，也没有运行时反射，所有类型信息只存在于生成代码里。
- 心跳 + 超时 ≈ 微服务的健康检查 / etcd lease。都在用周期信号判断对端死活。局限：嵌入式链路可能是半双工甚至单向的，超时阈值受链路时延和丢包影响很大，3 秒是工程折中而不是理论值；也没有租约续期那种协商机制。
- seq 序号 + CRC ≈ TCP 的序号与校验和。都用于检测丢失和损坏。局限：MAVLink 没有重传、没有拥塞控制、没有连接状态，是纯尽力而为的 UDP 风格，可靠性要靠应用层微服务自己重试（比如 PARAM_SET 超时重发）。
- sysid/compid ≈ 分布式系统里的 service/instance 标识。一个系统里多个组件各有一个 compid。局限：都只有 8 位，上限 255，且 0 是广播地址不能当源地址；没有服务发现，双方必须预先约定好 ID 分配。
- MAVLink 2 消息签名（共享 32 字节密钥 + 48 位单调时间戳 + HMAC-SHA256 前 48 位）≈ JWT/HMAC 防篡改与防重放。局限：是对称预共享密钥，没有公钥体系、没有证书吊销、没有密钥轮换协议，密钥分发是工程里最头疼的部分。
- 扩展字段只追加尾部、不进 CRC_EXTRA ≈ API 的向后兼容策略。局限：它只允许"追加"，删除、改名、改类型都会立刻破坏线上兼容；而且接收方代码要自己处理"字段不存在"的情况，没有 protobuf 那种 optional 语义。

## 8. 今日 10 个嵌入式概念卡片

1. 心跳消息（Heartbeat）：周期性发送的最小存活信号，接收方超时未收到即判定失联。类比：健康检查探针。场景：飞控-地面站、设备-网关。坑点：心跳频率要和链路时延、丢包率匹配，过快浪费带宽、过慢误判失联。
2. 帧同步（Frame Sync）：在无帧边界的字节流里，用魔数 + 状态机恢复帧结构。类比：TCP 粘包/拆包。场景：任何 UART/串口协议。坑点：魔数可能出现在负载里，必须靠长度字段 + CRC 双重确认，不能只看魔数。
3. CRC 校验：用多项式除法生成校验值检测传输损坏。类比：TCP 校验和。场景：无线链路、存储。坑点：CRC 只能检错不能纠错，且不能防恶意篡改（没有密钥参与）。
4. CRC_EXTRA / 模式版本握手：把消息定义本身做哈希塞进校验值，检测双方 schema 不一致。类比：API 版本协商、契约测试。场景：固件升级前后的兼容判断。坑点：它只保证"定义一致"，不保证语义一致，注释里写的含义错了它检测不出来。
5. 字节序与小端序列化：多字节字段按小端排布，默认运行在小端 MCU 上。类比：JSON 里数字的表示约定。场景：任何二进制协议。坑点：大端 MCU 或异构网关必须显式转换，否则数值错乱。
6. 字段对齐与重排：线上字段按长度 8/4/2/1 排序，避免 MCU 对齐填充浪费。类比：数据库行存储的列裁剪/压缩。场景：带宽敏感协议设计。坑点：重排必须收发双方一致，所以 CRC_EXTRA 在重排后计算；手写实现很容易在这里出错。
7. 尽力而为传输与丢包检测：有序号、有校验，但无重传。类比：UDP + 应用层自研可靠性。场景：遥测流（姿态、GPS），丢了就丢下一帧。坑点：不能拿它传关键指令，关键操作要走带确认的重试型微服务。
8. 消息签名与防重放：13 字节签名 = 6 字节单调时间戳 + 1 字节链路 ID + HMAC-SHA256 截断值，时间戳必须严格单调递增。类比：JWT 的 jti/nonce。场景：防注入、防重放攻击的数传链路。坑点：设备没 RTC 时要用 GPS 时间或持久化存储兜底，时间戳回退会直接导致签名失效。
9. 位图状态上报：用一个 32 位整数的一位表示一个传感器/子系统的状态。类比：feature flag 位图、权限位。场景：健康监控、外设状态。坑点：位号是 ABI 的一部分，新增传感器要占用新位，不能重排已有位。
10. 代码生成与方言（Dialect）：XML 定义消息，生成器产出多语言代码，各厂商可扩展自己的方言。类比：protoc/OpenAPI 生成 SDK。场景：多厂商互操作协议。坑点：方言膨胀会导致同一 msgid 在不同方言里含义不同，跨方言通信必须基于 common.xml。

## 9. 30～60 分钟动手任务

目标：亲手走完"看定义 → 生成代码 → 打包收发 → 验证 CRC"闭环，并复现一次"schema 不兼容导致老设备立刻拒绝"的现象。

步骤：
1. git clone --recursive https://github.com/mavlink/mavlink.git，装好 pymavlink 依赖。
2. 用 README 里的命令生成 C 头文件：python3 -m pymavlink.tools.mavgen --lang=C --wire-protocol=2.0 --output=generated/include/mavlink/v2.0 message_definitions/v1.0/common.xml。
3. 参考 examples/c/udp_example.c，写一个 20 行左右的小程序：pack 一条 HEARTBEAT，把原始字节打印出来（注意首字节应是 0xFD，v1 则是 0xFE），再用 mavlink_parse_char 逐字节喂回去 decode，确认字段一致。
4. 修改 common.xml 里 HEARTBEAT 的任意一个字段名，重新生成头文件，重新编译运行：观察 CRC 校验失败（MAVLINK_FRAMING_BAD_CRC），体会"改了定义，老设备立刻不认"。
5. 可选：用 pymavlink 的 mavutil.mavlink_connection('udpin:127.0.0.1:14550') 与 C 程序在 localhost 上互通，观察心跳消息。

验收标准：打印的字节与文档中的 v2 包格式逐字段对得上；改动字段名后能稳定复现 CRC 报错；全程不需要任何硬件。若本机没有 pip 权限，可用 Python 版 mavgen 生成的 dialect 文件替代 C 部分。

## 10. 3 道深度追问题

1. （时序/资源）为什么接收端要设计成"逐字节喂入的状态机"而不是"攒够一帧再解析"？在 115200 波特的 UART 上，如果每收到一个字节的中断处理耗时超过约 87 微秒会发生什么？再算一笔账：1Hz 的 HEARTBEAT（约 9 字节负载）和 50Hz 的 ATTITUDE（约 28 字节负载）各占 115200 波特链路的多少带宽？
2. （软→嵌视角转换）后端你给接口加字段通常追求向后兼容；在 MAVLink 里给消息加字段为什么只能追加在末尾、还不能参与 CRC_EXTRA？如果某个厂商删掉一个字段并重新发布固件，地面站端会发生什么？这和 protobuf 的 field number 永不重用策略相比，各自的取舍是什么？
3. （工程判断）MAVLink 2 签名需要双方共享 32 字节密钥，且时间戳必须单调。在一款量产消费级无人机上，密钥怎么出厂写入、怎么在用户手里轮换、丢了怎么办？对比你后端习惯的 KMS/证书体系，嵌入式侧到底缺了什么基础设施，导致签名方案只能做到这一步？

## 12. 工程点评

- 可维护性：XML 单一来源 + 生成代码，改消息只改规范文件，多语言同步更新；代价是生成代码不可读、排查问题时要回到规范层。
- 可移植性：C 实现 header-only、零依赖、无动态内存，裸机、RTOS、Linux 都能跑；默认小端假设在异构网关上需要显式处理。
- 可靠性：CRC + 序号 + 心跳超时 + 可选签名，多层防护；但传输层不重传，可靠性被上移到各微服务自己实现（如 PARAM_SET 的确认与重发），这是清晰的分层取舍。
- 可测试性：有 Wireshark 解析器、pymavlink、test.xml 测试方言和 CI，协议级仿真容易；但端到端时序问题（超时、乱序）仍需要真实链路或网络损伤模拟。
- 量产/运维：生态成熟、互操作经过多年现场验证；CRC_EXTRA 机制让新旧固件混跑时能硬性隔离不兼容消息，但也意味着协议演进必须走"扩展字段"或"新消息 ID"的渐进路线，跨大版本升级要规划过渡期。
