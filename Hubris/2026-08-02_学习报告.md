# 每日嵌入式学习：Hubris

## 1. GitHub 项目链接与一句话介绍

- 仓库：`oxidecomputer/hubris`（https://github.com/oxidecomputer/hubris），Rust 编写，MPL-2.0 协议。
- **一句话介绍**：Hubris 是 Oxide Computer 公司为深度嵌入式系统设计的一个轻量级、带内存保护、基于消息传递的微内核操作系统——它让多个任务在无 MMU 的 MCU 上彼此隔离地运行，任何一个任务崩溃都不会拖垮整台设备。

## 2. 为什么今天选它

- **活跃度**：仓库创建于 2020 年 4 月，最近一次提交是 2026 年 7 月 31 日，即两天前仍在持续更新；当前约 3572 star、234 fork、335 个 open issue，issue 讨论活跃，是典型的"产品驱动、长期维护"的工业级仓库。
- **工程完整度**：这不是教学玩具，而是 Oxide 机架级服务器里真实量产运行的固件。仓库包含内核、任务库、驱动、构建系统、文档、测试框架和配套调试器 Humility，从 `app.toml` 配置到内核启动再到崩溃恢复策略，是一条完整可读的工程链路。
- **学习价值**：对纯软件工程师来说，Hubris 是理解"嵌入式操作系统到底在解决什么问题"的绝佳样本——它把 Linux 里进程、系统调用、进程间通信、init 进程这些概念，在"没有 MMU、内存以 KiB 计、没有虚拟内存"的约束下重新实现了一遍。读它等于做一次"从零理解操作系统"的思维体操，而且是用现代 Rust 写的，没有 C 内核那种难啃的宏和指针迷宫。
- **明确适合软件工程师的原因**：Hubris 的设计文档反复强调"少写代码""务实避开学术理想"等工程哲学，和做后端系统时的取舍思路高度同构；任务、IPC、监督者这些概念几乎可以直接映射到微服务、RPC、编排系统，迁移成本极低。

## 3. 项目解决的问题

- **真实产品/工程场景**：Oxide 的整机柜服务器里，有一块叫 Sidecar 的服务处理器（SP）板卡，负责管理电源、风扇、温度、传感器、前面板，还承担安全启动等职责。这类板卡 7×24 小时无人值守运行，出问题没有操作员能上去按重启键，所以固件必须"自己照顾自己"。Hubris 就是为这种"deeply embedded、无人干预、可靠性优先"的场景写的。
- **和普通软件项目相比多出的约束**：
  - 硬件约束：目标芯片是 32 位 MCU，没有 MMU，内存保护只能靠 ARM 的 MPU（内存保护单元）按区域粗粒度划分；RAM 以 KiB 计，Flash 也就几十到几百 KiB，每个任务的 flash/ram 上限要在构建时就定死。
  - 资源约束：没有动态内存分配的自由，任务的栈、堆、消息缓冲都要预先规划；任务数量固定，运行期不能创建或销毁任务。
  - 时序约束：中断延迟、调度延迟、IPC 延迟都要可预测；同一优先级内不做时间片轮转，避免不确定性。
  - 可靠性约束：任何任务都可能崩溃，系统必须能检测崩溃、隔离崩溃、自动重启崩溃的任务，而且不能因为一个驱动崩溃导致整机瘫痪或反复重启。

## 4. 技术架构分析

整体架构分为两层：一个极小的特权态内核，加上一群运行在非特权态、彼此内存隔离的任务。

- **内核（sys/kern）**：只提供"任务切换、消息传递、定时器、内存区域保护"这几样最基础的抽象，其余一律不管。内核本身用 safe Rust 为主，少量 unsafe。
- **任务（task、drv）**：所有业务逻辑和驱动都在任务里。任务被单独编译、不共享代码，运行在非特权模式，受 MPU 内存保护，无法直接踩踏内核或其他任务的内存。驱动通常实现为一个 server 任务，通过 IPC 对外提供接口；但也允许"驱动 crate 直接链接进调用方"这种更省资源的做法（比如一条 I2C 总线上只有一个设备时）。
- **物理寻址**：Hubris 是物理寻址系统，任务的内存是地址空间里互不重叠的区段，内核单独占一段。没有虚拟内存，所以也不需要页表；好处是调试极其直观，坏处是保护粒度粗（只能按区域，不能按页）。
- **配置系统**：每个应用由一份 `app.toml` 描述——声明内核、板卡、芯片、每个任务的名称/优先级/flash/ram 上限/使用的硬件资源/中断/通知/依赖的任务槽位。构建系统（build/）在编译期读取这份配置，生成 `kconfig.rs`（任务表、区域描述表），与内核一起打包成单一固件镜像。
- **通信机制（IPC）**：同步会合式消息传递，灵感来自 L4 微内核。发送方调用 send 后阻塞等待回复；接收方 recv 阻塞直到有消息到达；内核在双方"会合"时做一次小数据拷贝。没有内核消息队列，因此不存在队列被塞爆的 DoS 问题。另外还有一种更轻的通知机制（notification），本质是一个位图，不带数据载荷，用于中断通知和崩溃通知。
- **调度**：严格优先级抢占调度，0 是最高优先级，最多 256 级；同级之间是协作式（不做时间片轮转）。调度规则里有一条著名的"上坡发送规则"（uphill send）：任务只允许给比自己优先级高的任务发消息，否则可能饥饿或死锁。
- **故障与监督**：任务崩溃（硬件故障、系统调用错误、显式 panic）后，内核记录故障并停掉该任务，但内核不负责重启。真正的恢复策略由"监督者"任务决定——监督者固定是任务索引 0、优先级 0，收到崩溃通知后扫描各任务状态、记录日志、调用 reinit_task 重启崩溃任务。如果监督者自己崩溃，系统直接重启。参考实现叫 El Jefe（task/jefe）。
- **升级/部署**：应用是"整体部署"的——所有任务和内核一起构建、一起测试、一起烧录，刻意不支持运行时部分升级，也不承诺任务间 ABI 稳定。这是为了规避"组合爆炸"式的测试矩阵。
- **调试支持**：配套 Humility 调试器，加上"任务物理地址可预测""栈内存用特征值涂抹以测峰值栈深"等设计，让现场调试和容量规划都更可操作。

以上除特别说明外，均基于仓库 README、doc/ 目录官方文档与示例 app.toml 原文整理；源码内部实现细节如任务状态机字段，建议以实际阅读为准。

## 5. 源码陪读：今天只读哪几个文件

按"从整体到局部、从配置到内核到策略"的顺序读：

1. **app/demo-stm32f4-discovery/app.toml** —— 先读这份 79 行的最小应用配置。阅读目标：搞懂一个 Hubris 应用由哪些"零件"组成，priority、start、notifications、interrupts、task-slots、max-sizes 这些字段分别对应什么运行时行为。
2. **sys/kern/src/startup.rs** —— 内核启动路径。阅读目标：看 `start_kernel` 如何读取 App/RegionDesc/TaskDesc 表、校验完整性、初始化任务簿记，最后挑出最高优先级的 START_AT_BOOT 任务切换过去。
3. **sys/kern/src/task.rs** —— 任务状态与调度的核心数据结构。阅读目标：理解任务的状态机（Runnable/Blocked/Stopped/Faulted）、代际编号 generation 的作用、阻塞在什么对象上（消息、通知、定时器）。
4. **sys/userlib/src/hl.rs** —— 任务侧的高层封装。阅读目标：看 `recv_without_notification` 等封装如何把裸系统调用变成"写业务逻辑"的体验，理解 server 主循环的标准写法。
5. **task/jefe/src/main.rs** —— 监督者参考实现（El Jefe）主循环。阅读目标：看崩溃恢复策略的真实代码——收通知、扫任务、记日志、reinit，总共不到百行，是"策略与机制分离"的典范。

## 6. 核心模块/函数导读

- **start_kernel（sys/kern/src/startup.rs）**：系统入口。它把构建期生成的 kconfig.rs 里的任务表装载成内核簿记数据，是"配置即代码"的落地处——app.toml 的每一项最终都变成这里的数据结构。它直接串联启动流程与构建系统。
- **系统调用分发（sys/kern/src/syscalls.rs）**：内核提供给任务的唯一入口，包括 send、recv_open、recv_closed、reply、read_task_state、reinit_task 等。理解它就能理解"任务与内核的边界"——这对应 Linux 的系统调用表，但语义完全不同：把"用错系统调用"直接定义为任务故障，而不是返回错误码。
- **调度器与任务状态机（sys/kern/src/task.rs）**：负责保证"当前运行的永远是就绪任务里优先级最高的那个"，并维护代际编号。代际编号是理解崩溃恢复的关键：任务重启后 generation+1，所有还堵在旧代际上的调用方会收到一个"对方已死"的错误码。
- **sys_send / sys_recv_open / sys_reply（sys/userlib/src）**：任务侧 IPC 三件套。send 像一次阻塞式 RPC，recv_open 接受任何来源的消息，reply 唤醒发送方。server 就是这三者的无限循环。
- **监督者主循环（task/jefe/src/main.rs）**：崩溃恢复策略本体。它体现了一个重要设计：内核只负责"机制"（检测故障、记录、提供重启原语），"策略"（要不要重启、重启谁、记什么日志）全部外置到应用层任务。
- **app.toml + 各 app 的 build.rs**：构建期配置点。它把"多少个任务、谁优先级高、谁用哪个外设、谁依赖谁"全部变成编译期事实，从而让峰值内存可以在编译期核算——这是嵌入式里"静态资源规划"的典型姿势。

## 7. 软件工程师类比解释

- **任务 ≈ 微服务/独立进程**：任务单独编译、内存隔离、通过 IPC 通信，和拆微服务后用 RPC 通信几乎一一对应；驱动 server 就像"硬件设备微服务"。局限：Hubris 的任务数量固定、运行期不能扩容，而微服务可以弹性伸缩——嵌入式里资源是编译期定死的，没有"加一台机器"的选项。
- **同步 IPC ≈ 同步 RPC（gRPC/HTTP 请求-响应）**：send 阻塞等回复、server 循环 recv-reply，就是"函数调用式"的远程调用，心智负担低、容易推理。局限：它没有异步队列、没有超时重试的中间件，消息体必须小（大块数据要走专门的 lease 机制）；并发模型也完全不同，Hubris 里一个任务同时只能发一条消息。
- **监督者 El Jefe ≈ 系统里的 init/进程管理器（systemd、Kubernetes 控制器）**：负责拉起任务、观察谁死了、按策略重启。局限：监督者是单点且固定优先级最高，它崩溃等于整机重启；没有 k8s 那种控制器多副本、leader 选举、滚动更新的能力。
- **app.toml ≈ 基础设施即代码（docker-compose / K8s manifest）**：一份声明式配置决定整个应用的拓扑和资源配额。局限：这是编译期静态解析，不是运行期 API；改配置必须重新构建整个固件镜像，不支持热加载或局部更新。
- **代际编号 generation ≈ 分布式系统中的 epoch/租约版本号**：任务每重启一次版本+1，调用方用旧版本号发起请求会收到"对方已换代"的信号，类似 etcd 里 revision 不匹配就重试。局限：它是单机内核直接强制、零网络开销的机制，不需要分布式共识；而且"换代"只发生在重启时，不像 epoch 那样还会因主节点选举而变化。
- **MPU 内存保护 ≈ Docker 容器隔离**：都让一段代码"以为"自己拥有资源、越界就报错。局限：容器隔离依赖 MMU 的虚拟地址翻译，粒度是页；MPU 只能按内存区域粗粒度保护，且没有地址翻译，任务看到的地址就是物理地址，保护强度低一个量级。

## 8. 今日 10 个嵌入式概念卡片

1. **微内核（Microkernel）**：内核只保留最少的机制（调度、IPC、定时器），其余都放用户态。类比：把单体后端拆成网关+业务服务。场景：高可靠性系统。坑点：微内核不等于慢，同步 IPC 可以非常快；但"机制少"意味着很多活要应用层自己做。
2. **无 MMU 的内存保护**：没有内存管理单元时，用 MPU 按区域做粗粒度保护，且无虚拟地址。类比：没有 Docker 网络隔离，只有 iptables 白名单。场景：低成本 MCU。坑点：保护粒度粗，一个区域内的越界要靠 Rust 所有权兜底。
3. **同步会合式 IPC**：收发双方必须同时就绪才发生一次消息拷贝，无内核队列。类比：TCP 三次握手式的一问一答，而不是消息队列。场景：需要可预测延迟和互斥的嵌入式系统。坑点：没有队列意味着"并发突发流量"无处缓冲，必须靠优先级和上坡规则设计来避免死锁。
4. **严格优先级抢占调度**：就绪任务中数值最小的优先级（0 最高）总是拿到 CPU。类比：生产环境 QoS 队列，高优请求永远插队。场景：实时控制。坑点：低优先级任务可能饥饿；Hubris 靠"上坡发送规则"把这种风险转成编译期可推理的约束。
5. **协作式多任务（同级）**：同一优先级内不做时间片，任务不主动让出 CPU 就没人抢。类比：Node.js 单线程事件循环里"别阻塞事件循环"。场景：减少不确定性和上下文切换开销。坑点：一个同级任务死循环会饿死同级的其他任务。
6. **任务代际编号（generation）**：每次重启任务编号+1，用于让旧调用方识别"对方已换人"。类比：服务重启后客户端用旧连接重试，收到 connection reset。场景：崩溃恢复、IPC 可靠性。坑点：调用方必须处理"死了重试"还是"死了自己也死"的策略选择，处理不好会无限重试打转。
7. **监督者模式（Supervisor）**：把"崩溃了怎么办"的策略外置给一个特殊任务。类比：systemd 的 Restart=always。场景：无人值守设备。坑点：监督者自身是单点，它挂了系统只能重启；不能把监督者当成万能看门狗，策略要尽量简单可证明。
8. **构建期静态资源分配**：任务数、栈大小、内存上限在编译时确定。类比：给每个微服务固定内存配额并禁止动态扩容。场景：需要峰值内存可证明的系统。坑点：灵活性差，负载模型变了要重新构建镜像；好处是"运行期不可能 OOM 式失控"。
9. **通知（Notification）**：一种不带数据载荷的位图信号，用于中断到达、崩溃事件等"只需要唤醒"的场景。类比：k8s 里的 Event 或 Unix 信号量里只置位不传参。场景：驱动中断处理、监督者唤醒。坑点：通知不带数据，想知道"谁崩了、为什么"还得再走 IPC 查询。
10. **整体镜像部署（Holistic Deployment）**：所有任务与内核一起构建、测试、烧录，不支持部分升级。类比：全量发布代替金丝雀发布。场景：无法回滚、无人维护的设备。坑点：升级成本高、迭代慢，但换来了"只测组合过一次的配置"的可信度。

## 9. 30～60 分钟动手任务

- **目标**：不买硬件，纯阅读+模拟，把"一个 Hubris 应用从配置到启动"的链路走通。
- **步骤**：
  1. 用浏览器或 git clone 拉取仓库（`git clone --depth 1 https://github.com/oxidecomputer/hubris.git`）。

- **验收标准**：能画出完整的任务依赖图；能说出"为什么 jefe 必须是 priority 0 且 task index 0"；能解释崩溃后 ping 任务给 usart_driver 发消息会发生什么（会收到换代错误码，重试或 panic）。
- **无硬件替代方案**：本任务全程不需要板子；如果本机有 Rust 工具链，可以尝试 `cargo xtask` 相关构建命令体验配置→生成 kconfig 的过程（以仓库 README 说明为准）。

## 10. 3 道深度追问题

1. Hubris 用"上坡发送规则"（只允许给更高优先级任务发消息）来规避死锁和优先级反转。请推演：如果打破这条规则，允许一个高优先级任务去 send 给低优先级任务，会构造出什么样的死锁或优先级反转场景？现实中"必须向下发消息"的需求（比如 server 要通知 client 事件）在 Hubris 里应该用什么机制实现？（提示：通知 notification 的方向性）
2. 假设你要给 Hubris 增加"运行期动态创建任务"的能力，从软件工程视角看这像"给系统加容器编排"；但从嵌入式视角，请列出至少三个必须在架构层面解决的新问题（例如：内存从哪来、任务表如何扩容、峰值内存如何证明），并说明为什么 Hubris 团队选择"干脆不支持"。
3. Hubris 的 IPC 是同步的、没有内核队列。请对比：在 Linux 里用 socket/消息队列做进程间通信时，队列是天然的背压缓冲；Hubris 去掉队列后，如果多个 client 同时向一个 server 发请求，请求在哪个"队列"里等待？这对 server 的优先级设计和请求处理表格大小有什么要求？（提示：阻塞在发送方的任务本身、pipelining 请求表、NUM_TASKS 上界）

## 11. 今日复盘问题

如果让你把公司里一个"7×24 无人值守、出错不能人工介入"的后端服务，用 Hubris 的整套设计哲学（固定资源、整体部署、策略外置、同步通信）重新设计一遍，哪些做法你会照搬，哪些做法在云原生环境里反而会成为灾难？为什么？

## 12. 工程点评

- **可维护性**：文档与代码同仓、AsciiDoc 手册完整、命名规范统一（drv-SYSTEM-DEVICE / -server 约定），Rust 类型系统把大量非法状态变成"编译不过"；缺点是仓库庞大、目录多，新人上手需要先读 README 的导航说明。
- **可移植性**：架构层（arch/arm_m.rs）与 SoC 层（chips/）分离，已有多个 demo 板（STM32F4/G0/H7、LPC55、Gemini 等）；但物理寻址+无共享库的设计决定了移植到带 MMU 的芯片反而要重写保护模型——这是有意的取舍。
- **可靠性**：内存安全语言、故障隔离、代际编号、整体部署、监督者外置，层层都是为"崩溃可恢复"服务；同步 IPC 消灭了一大类竞态。
- **可测试性**：有 test/ 框架和 framulator 等模拟器思路，配合 Humility 调试器可离线复现任务状态；但硬件相关逻辑最终仍需真实板卡验证，这是嵌入式的宿命。
- **量产/运维**：整体镜像+构建期资源核算让"烧进板子的组合一定被测试过"；现场故障靠监督者日志与 Humility 事后分析。代价是更新必须整包替换，运维节奏偏"重"。

## 13. 明天可以延展的方向

1. **Humility 调试器**（oxidecomputer/humility）：读它的任务状态查看、栈回溯命令，理解"物理寻址让调试器能直接看全地址空间"到底意味着什么。
2. **Idol 接口定义语言与 build.rs 代码生成**：研究 Hubris 如何用 IDL 生成 IPC 编解码与 server 骨架，这对应后端里的"接口契约驱动开发"，是理解"嵌入式 RPC 框架"的好入口。
3. **真实产品板卡应用**：读 app/gimlet 或 app/sidecar 的 app.toml 与任务划分，看一个量产服务处理器如何把传感器、电源、安全启动、前面板等拆成几十个任务，学习"任务粒度怎么定"的工程判断。
