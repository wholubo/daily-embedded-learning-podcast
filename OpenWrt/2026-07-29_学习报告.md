# 每日嵌入式学习：OpenWrt

## 1. GitHub 项目链接与一句话介绍

- **仓库链接**: https://github.com/openwrt/openwrt
- **一句话介绍**: OpenWrt 是一个面向嵌入式设备的 Linux 操作系统发行版，它不像传统固件那样是"烧死"的静态镜像，而是提供了一个完全可写、带包管理的文件系统，让路由器、网关、IoT 设备可以像普通 Linux 服务器一样自由安装软件和定制功能。

## 2. 为什么今天选它

- **活跃度**: 27,745 个 Star，12,696 个 Fork，项目从 2004 年持续维护至今，最近更新就在今天。它不是"玩具项目"，而是全球数百万台路由器实际运行的生产级系统。
- **工程完整度**: OpenWrt 包含完整的交叉编译工具链、内核补丁管理、包管理系统（opkg）、构建系统（自定义 Makefile 架构）、设备树支持、UCI 统一配置接口、LuCI Web 管理界面——几乎涵盖了嵌入式 Linux 产品开发的每一个环节。
- **学习价值**: 对于有软件工程背景（后端、全栈、基础设施）的开发者来说，OpenWrt 是从"纯软件世界"跨入"软硬一体世界"的绝佳桥梁。你不需要先买开发板——可以在 QEMU 虚拟机或 WSL 里编译运行 OpenWrt，理解完整的嵌入式 Linux 产品构建流程，再逐步深入到驱动、内核、硬件抽象层。
- **未重复**: 确认不在历史学习项目列表中。

## 3. 项目解决的问题

### 真实工程场景

OpenWrt 解决的根本问题是：**消费级路由器/嵌入式设备的固件是封闭的、静态的、不可定制的**。厂商给你什么功能你就用什么功能——不能升级 OpenSSL 版本、不能换 Web 服务器、不能加 VPN 协议、不能改防火墙规则。OpenWrt 用标准 Linux 发行版的思路重构了嵌入式固件。

### 与普通软件项目的区别

| 维度 | 后端/云原生项目 | OpenWrt（嵌入式） |
|------|---------------|-------------------|
| **硬件约束** | CPU/内存/磁盘几乎无限 | 4MB Flash、32MB RAM 是常见配置，资源是"数着比特用的" |
| **存储模型** | 可写文件系统 + 包管理 | 部分设备是 read-only squashfs + overlayfs 实现"伪可写" |
| **交叉编译** | 极少碰到 | 整个项目就是一套交叉编译体系：x86 笔记本编译 MIPS/ARM 架构的二进制 |
| **内核版本** | 用发行版提供的 | 必须自己配置内核选项、打补丁、管理设备树 |
| **Flash 布局** | 不需要关心 | 需要定义分区表（bootloader、kernel、rootfs、art...）、管理 mtd 驱动 |
| **升级风险** | 回滚即可 | 刷错固件=板砖，必须实现 failsafe/双分区升级机制 |

### 嵌入式特有约束

- **存储空间**: 一个完整的 Web 界面 + 网络栈 + VPN + 防火墙可能要在 8MB 以内塞下。OpenWrt 使用 squashfs（压缩只读文件系统）+ overlayfs（可写层）来解决，所有包都是"按需压缩存储"。
- **内存紧张**: 路由器启动后可能只有不到 10MB 空闲内存。每个进程的启动参数、缓冲区大小、并发连接数都要精打细算。
- **无 MMU 情况**: 部分低端路由器使用 MIPS 架构且没有 MMU，这意味着没有进程隔离——一个进程崩溃可能拖垮整个系统。
- **掉电安全**: 嵌入式设备经常直接拔电。OpenWrt 的 `jffs2`/`ubifs` 文件系统要保证掉电不损坏。

## 4. 技术架构分析

OpenWrt 的构建系统是一个非常巧妙的"三层递归 Makefile"架构，下面从顶层到底层分析。

### 4.1 整体模块架构

```
┌───────────────────────────────────────────────┐
│               package/（应用包）                 │
│  busybox, dnsmasq, dropbear, luci, nginx ...   │
├───────────────────────────────────────────────┤
│               target/（目标板支持）              │
│  内核配置、设备树、分区布局、镜像生成脚本           │
├───────────────────────────────────────────────┤
│               toolchain/（工具链）              │
│  gcc, binutils, uClibc/musl/glibc, headers    │
├───────────────────────────────────────────────┤
│               tools/（宿主机工具）              │
│  make, cmake, meson, quilt, mkimage ...       │
├───────────────────────────────────────────────┤
│               include/（构建规则库）             │
│  kernel-build.mk, package.mk, image.mk ...    │
├───────────────────────────────────────────────┤
│               scripts/（辅助脚本）              │
│  镜像打包、补丁管理、配置生成、签名工具            │
├───────────────────────────────────────────────┤
│               feeds/（包源配置）                │
│  feeds.conf → packages, luci, routing, video  │
└───────────────────────────────────────────────┘
```

### 4.2 构建流程

```
make menuconfig      ← 选择目标架构、内核选项、要包含的包
  ↓
./scripts/feeds update -a   ← 从远程源拉取包定义
  ↓
./scripts/feeds install -a  ← 将包链接到 package/feeds/
  ↓
make                    ← 自动下载源码 → 构建工具链 → 交叉编译 → 打包镜像
  ├─ tools/stamp-compile   (编译宿主机工具)
  ├─ toolchain/stamp-compile (编译交叉编译器)
  ├─ target/stamp-compile  (编译内核 + 模块)
  └─ package/stamp-compile (编译所有选中的包)
```

### 4.3 关键技术设计

**1. UCI（Unified Configuration Interface）统一配置接口**
OpenWrt 最优雅的设计之一。所有系统配置（网络、防火墙、WiFi、系统）统一用 UCI 管理，配置文件在 `/etc/config/` 目录下，命令 `uci` 提供了 get/set/commit/import/export 操作。上层的 LuCI 和 `libubus` 都基于 UCI。

**2. Procd 初始化系统**
取代了 System V init。Procd 是 OpenWrt 自己写的轻量级 init 和进程管理守护进程，支持热插拔（hotplug）、服务自动重启、看门狗（watchdog）、基于 `ubus` 的服务状态查询。

**3. Libubus 进程间通信总线**
OpenWrt 的"嵌入式版本 D-Bus"。Procd、Netifd、LuCI 等核心组件通过 ubus 交换消息，而不是靠共享文件或临时 socket。

**4. Netifd 网络守护进程**
不再靠 `/etc/init.d/network` 脚本启停网络。Netifd 是一个常驻守护进程，通过 ubus 接收 UCI 配置变更，动态管理接口、路由、DHCP、DNS——不用重启服务。

**5. Opkg 包管理器**
嵌入式版的 `apt-get`/`yum`。通过 opkg 可以在运行中的设备上安装/卸载/升级包，自动处理依赖。这是 OpenWrt 与"静态固件"最本质的区别。

**6. Image Builder 镜像生成器**
允许用户在 x86 PC 上选择包、生成自定义固件镜像，而不需要部署完整的构建环境。这在量产和 CI/CD 中非常实用。

### 4.4 基于公开文件推断的补充

OpenWrt 的主 Makefile 和多层 `include/*.mk` 文件构成了一个复杂的"递归模板系统"。`kernel-build.mk` 文件管理着内核下载、解压、打补丁、配置、编译、打包的全部流程。`package.mk` 则定义了应用包的通用构建规则。这种设计让任何包都可以用十几行 Makefile 定义完整的交叉编译流程。

- **目标**: 理解嵌入式 Linux 内核是如何"被构建"的——不是直接 `make`，而是经过下载、校验、打补丁、配置、编译、打包六步。
- **阅读要点**: 关注 `define Kernel/...` 模板，看看内核模块是如何被编译成 `.ko` 文件并打包到固件中的。
- **阅读顺序**: 第 2 个。

### 文件 3: `package/network/services/dnsmasq/Makefile`
- **目标**: 以一个真实的包（DNS/DHCP 服务器）为例，理解 OpenWrt 的包定义格式。
- **阅读要点**: 看 `Package/dnsmasq` 段，了解 `TITLE`、`DEPENDS`、`SUBMENU`、`MAKE_PATH`、`CONFIGURE_ARGS` 各字段的含义。尤其注意 `DEPENDS` 如何表达依赖关系。
- **阅读顺序**: 第 3 个。

### 文件 4: `scripts/feeds`
- **目标**: 理解"包源"机制——OpenWrt 如何管理上千个第三方包的索引和同步。

- **阅读顺序**: 第 4 个。

- **阅读要点**: 不需要逐行看完（文件巨大），搜索 `CONFIG_USB`、`CONFIG_NETFILTER`、`CONFIG_MTD` 等关键词，了解 OpenWrt 对内核的典型裁剪方式。
- **阅读顺序**: 第 5 个。

## 6. 核心模块/函数导读

### 6.1 `scripts/feeds` —— 包源管理入口
- **工程角色**: 类似 `apt-get update` + `apt-get install` 的包源同步机制。`feeds update` 从 Git/SVN 仓库拉取包索引，`feeds install` 将选中的包链接到 `package/feeds/` 目录下，纳入构建。
- **与构建系统的关系**: 不运行 `feeds update && feeds install`，`make` 就找不到任何第三方包。这是构建的**前置条件**。

### 6.2 `include/package.mk` —— 通用包构建规则
- **工程角色**: 定义了 `Package/...` 和 `Build/...` 模板宏。所有 `package/*/Makefile` 都继承自这套规则。
- **关键函数**: `PackageHeir`（包依赖关系解析）、`Build/Compile`（交叉编译流程）、`Package/Install`（文件安装到目标目录）。
- **与 RTOS/操作系统的关系**: 这里的"包"概念类似 FreeRTOS 的"组件"或 Zephyr 的"模块"，但 OpenWrt 是 Linux 用户态包，依赖的是内核已经提供的系统调用接口。

### 6.3 `target/linux/generic/image/Makefile` —— 固件镜像生成
- **工程角色**: 将编译好的内核 + 文件系统 + 设备树打包成特定格式的二进制固件文件（如 `squashfs`、`ubi`、`jffs2`）。
- **关键配置点**: `DEVICE_DEFINES`（设备宏）、`KERNEL_LOADADDR`（内核加载地址）、`IMAGE_SIZE`（固件大小限制）。这些参数由硬件物理限制决定。
- **与 Flash 存储的关系**: 镜像大小必须小于 Flash 分区大小，不同 Flash 类型（NOR vs NAND）需要不同的 FS 格式。

### 6.4 `package/base-files/files/lib/functions.sh` —— 基础函数库
- **工程角色**: OpenWrt 启动脚本的公共函数库。定义了 `include`、`config_load`、`config_get` 等 shell 函数。
- **关键函数**: `config_load` 将 UCI 配置文件解析为 shell 变量，是 UCI 机制在 shell 层的实现。
- **与 UCI 的关系**: 这是 UCI 在运行时（run-time）的读取端；写入端是 `/sbin/uci` 二进制工具。

### 6.5 `procd/procd.c` —— Procd 初始化守护进程
- **工程角色**: PID=1 的用户态 init 进程。负责启动系统服务、监控进程状态、处理热插拔事件。
- **函数导读**: `procd_state_next()`——状态机转换函数，管理 PREINIT → INIT → RUNNING → SHUTDOWN 的完整生命周期。
- **与嵌入式约束的关系**: 在只有 32MB RAM 的设备上，Procd 必须在 microsecond 级别响应事件，不能 fork 太多子进程，所以大量使用 `ubus` 和 `uloop` 的事件驱动模式。

## 7. 软件工程师类比解释

### 类比 1: UCI ↔ Redis/MongoDB 配置中心
- **类比**: UCI 就是嵌入式的"配置中心"。后端工程师习惯用 Redis/Consul/etcd 统一管理配置，UCI 做同样的事情——所有组件（网络、防火墙、WiFi）都通过统一的命令和文件格式读写配置。
- **这个类比的局限**: UCI 不是分布式配置中心，它只跑在单设备上。也没有监听/推送机制——配置变更后需要手动 `commit` 或触发服务 reload。真正的微服务配置中心支持实时推送、版本控制、灰度发布，UCI 做不到。

### 类比 2: Procd ↔ Kubernetes 的 kubelet
- **类比**: Procd 管理设备上所有服务的生命周期，类似 kubelet 管理 Pod 的生命周期。Procd 通过 ubus 监听事件，kubelet 通过 API Server 监听事件；Procd 支持服务自动重启和健康检查，kubelet 支持 Pod 自动恢复。
- **这个类比的局限**: kubelet 管理的是容器化的应用，有网络插件、存储插件、镜像仓库等复杂生态。Procd 管理的是传统的进程，没有容器隔离。一个崩溃的服务在 Procd 下就是"杀进程→重启进程"，没有回滚、灰度、亲和性调度能力。

### 类比 3: Squashfs+Overlayfs 的文件系统 ↔ Docker 的镜像层
- **类比**: OpenWrt 的 squashfs（只读底包）+ overlayfs（可写层）和 Docker 的镜像层（read-only）+ 容器层（writable）是同一个概念。固件升级就是"换底包"——新 squashfs 加上已有的 overlayfs 配置，实现了"系统升级不丢配置"。
- **这个类比的局限**: Docker 层可以叠加任意多层，支持 `docker commit` 将可写层变成新镜像。OpenWrt 的 overlayfs 只有两层，且 overlay 是实时在线的——改错了不能像 Docker 那样 `docker diff` 对比差异后轻松回滚。"配置备份"仍然需要手动操作。

### 类比 4: OpenWrt 构建系统 ↔ Bazel/Pants 多语言构建系统
- **类比**: 想象一个 Bazel 项目需要为 3 种不同架构（MIPS/ARM/x86）各编译一份内核 + 200 个用户态程序，还要打包成不同的 Flash 镜像格式——这就是 OpenWrt 的 `Makefile` 做的事情。它的 `include/*.mk` 类似 Bazel 的 `rules_*` 规则库，`feeds` 类似 Gazelle 的依赖管理。
- **这个类比的局限**: Bazel 有远程缓存、增量分析、分布式执行，OpenWrt 的 make 是单机串行的。每次 `make clean` 后重新构建可能花几个小时。OpenWrt 的选择是"简单但可工作"——用 Makefile 模板而非声明式规则，维护成本更低，但对大规模 CI 不友好。

### 类比 5: Opkg 包管理 ↔ apt-get / yum
- **类比**: Opkg 就是嵌入式 apt-get。它维护一个包索引、处理依赖关系、解压 .ipk 文件包到目标文件系统。对于有后端背景的人来说，**OpenWrt 是唯一一个让你可以在路由器上 `opkg install nginx` 的嵌入式系统**。
- **这个类比的局限**: apt 仓库有几万个包，opkg 官方仓库大约 4000+ 个。apt 支持事务性安装、自动移除未使用的依赖（`apt autoremove`），opkg 没有。而且嵌入式设备的 Flash 空间有限，装两三个大包可能就满了。

## 8. 今日 10 个嵌入式概念卡片

### 卡片 1: 交叉编译（Cross Compilation）
- **一句话解释**: 在你的 x86 笔记本上编译出 MIPS/ARM 架构上能跑的可执行文件。
- **软件工程类比**: 好比你在 Windows 上编译 macOS 的可执行文件——但嵌入式世界这不仅是可能的，而且是唯一的方式（目标设备根本跑不了编译器）。
- **常见工程场景**: 任何没有 x86 CPU 的嵌入式设备（路由器、MCU、IoT 模块）。
- **容易误解/坑点**: 你以为加个 `-march=armv7-a` 就行，但工具链（gcc 版本、libc 实现、内核头文件）必须和目标系统完全匹配。用错工具链会在运行时出现"Segmentation fault, Illegal instruction, 或者什么都分析不出来就挂掉"。

### 卡片 2: Flash 存储布局（Flash Layout）
- **一句话解释**: 嵌入式设备的固件不是"一个大文件"，而是按扇区划分的多个区域（bootloader、kernel、rootfs、配置区、ART）。
- **软件工程类比**: 类似磁盘分区表（MBR/GPT），但更脆弱——因为 Flash 的擦写寿命有限（NAND 约 10 万次），且按块擦除而不是按字节写。
- **常见工程场景**: 刷机、OTA 升级、分区扩容。
- **容易误解/坑点**: 很多嵌入式开发新手以为 Flash 像硬盘一样可以随机写。实际上 NOR Flash 写前必须擦除整块，NAND Flash 还有坏块管理——写操作失败后需要标记坏块并跳过。

### 卡片 3: Squashfs（压缩只读文件系统）
- **一句话解释**: 一种高压缩比的只读文件系统，常用于嵌入式固件的根文件系统。
- **软件工程类比**: 相当于 Docker 镜像的只读层——不可变、可压缩、可按需解压。但 Squashfs 是在内核中直接挂载的，不需要 Docker 守护进程。
- **常见工程场景**: 路由器固件、Live CD、IoT 设备的出厂系统。
- **容易误解/坑点**: Squashfs 是只读的。你无法在运行时修改它的内容。OpenWrt 用 overlayfs 在上面叠一层可写层来绕过这个限制。

### 卡片 4: Overlayfs（叠加文件系统）
- **一句话解释**: 在一个只读文件系统上叠加一层可写层，所有修改都存到可写层，底层不变。
- **软件工程类比**: 这就是 Docker 的 OverlayFS 存储驱动——一模一样的概念。
- **常见工程场景**: "固件升级不丢配置"——升级时只换底包 squashfs，你的 overlay 修改保留。恢复出厂设置则清空 overlay。
- **容易误解/坑点**: Overlay 层本身也占用 Flash 空间。一个日志文件无限增长可能导致 overlay 写满，然后设备行为诡异（配置写不进去、包装不上）。内核不会自动 warning。

### 卡片 5: UCI（Unified Configuration Interface）
- **一句话解释**: OpenWrt 自己的配置管理框架，所有系统服务都用统一的格式和命令读写配置。
- **软件工程类比**: 一个只跑在本机的、无 watch 机制的 etcd/Consul——都是 key-value 配置存储，只是使用场景和性能不同。
- **常见工程场景**: 网络配置、WiFi 设置、防火墙规则、DHCP 选项。
- **容易误解/坑点**: 很多开发者以为改了 `/etc/config/network` 就行，但实际上只是改了文件，服务不会自动 reload。必须执行 `uci commit`（写入）并 `service network restart`（应用）。

### 卡片 6: Ubus（OpenWrt 总线）
- **一句话解释**: OpenWrt 的轻量级进程间通信（IPC）系统，类似 D-Bus 但更小巧。
- **软件工程类比**: Redis Pub/Sub 或 RabbitMQ 的直连版本——都是发布/订阅消息模式，只是 ubus 只在同一设备上运行，没有网络层。
- **常见工程场景**: Procd 通知 Netifd 网络配置已变更、LuCI 通过 ubus 读取系统状态。
- **容易误解/坑点**: Ubus 不是 D-Bus，不支持 D-Bus 的类型系统和方法签名验证。消息是 JSON 格式的，解析开销在嵌入式设备上不可忽略。

### 卡片 7: MTD（Memory Technology Device）
- **一句话解释**: Linux 内核中专门管理 Flash 存储设备的抽象层，将 Flash 分区暴露为 `/dev/mtd*` 设备。
- **软件工程类比**: 类似块设备（`/dev/sda*`），但 MTD 是"字符设备 + 块设备的混合体"——你可以读取/写入字节，但也需要按块擦除。既像 `/dev/sda` 又不像。
- **常见工程场景**: 读写 flash 分区、升级固件时擦写 kernel 分区、备份 ART 分区。
- **容易误解/坑点**: `dd if=image.bin of=/dev/mtdblock2` 是非常危险的操作——可能会因为文件系统缓存导致写入顺序不对，直接砖机。正确的做法是用 `mtd write` 或 `flashcp`。

### 卡片 8: 设备树（Device Tree / DTS）
- **一句话解释**: 描述嵌入式硬件配置的数据结构文件（`.dts`→`.dtb`），告诉内核"这个板子上有哪些外设、连在哪个 GPIO 上、用哪个中断号"。
- **软件工程类比**: 类似 Kubernetes 的 YAML 声明式配置——描述目标状态（硬件拓扑），而不是写代码去注册设备。Kernel 启动时读取 `.dtb` 来初始化驱动。
- **常见工程场景**: 移植 OpenWrt 到新硬件时，通常需要编写或修改 `.dts` 文件来适配。
- **容易误解/坑点**: 不是所有架构都用设备树。x86 用 ACPI，老式 ARM 用 board file。设备树只是一个"转移硬件描述义务"的方案——你不用改内核代码，但不能不写 DTS。

### 卡片 9: 热插拔（Hotplug）
- **一句话解释**: 系统在设备（USB 设备、WiFi 网卡、按键）插拔时自动执行预定义的脚本。
- **软件工程类比**: Linux 的 udev 规则、macOS 的 launchd 监听、Windows 的 Device Installation。概念完全一样，只是嵌入式场景下可能是"插上 USB 4G 模块自动拨号"。
- **常见工程场景**: USB 存储自动挂载、GPIO 按键触发脚本、WiFi 网卡热插拔。
- **容易误解/坑点**: OpenWrt 的 hotplug 是基于 procd 的 `/etc/hotplug.d/` 目录，不是 `udev`。不要在上面安装 `udev`（会冲突且浪费空间）。hotplug 脚本的执行环境是非常受限的——没有 PATH，没有环境变量。

### 卡片 10: 固件镜像格式（Firmware Image Format）
- **一句话解释**: 把内核、文件系统、设备树、bootloader 打包成一个文件的特定格式（TRX、BIN、IMG、FIT）。
- **软件工程类比**: 类似 `docker save` 导出的 `.tar` 文件——包含多个层（layer）和一个 manifest。只是嵌入式固件的"层"是物理分区（kernel、rootfs、config）。
- **常见工程场景**: 刷机、OTA 升级、工厂烧录。
- **容易误解/坑点**: 不要以为所有设备的固件格式通用。A 路由器的 .bin 刷到 B 路由器上=砖。OpenWrt 的 Image Builder 和固件选择器正是为了解决"不同设备不同格式"的问题而存在。

## 9. 30～60 分钟动手任务

### 目标
在虚拟机中编译一个自定义 OpenWrt 固件，为 x86/64 架构添加一个额外包，理解完整的构建流程。

### 步骤

1. **准备构建环境**（10 分钟）
```bash
# 在 Ubuntu/Debian/WSL 上安装依赖
sudo apt update
sudo apt install build-essential libncurses-dev gawk git subversion libssl-dev gettext unzip file python3 python3-distutils rsync wget curl
```

2. **克隆仓库**（5 分钟）
```bash
git clone --depth=1 https://github.com/openwrt/openwrt.git
cd openwrt
```

3. **运行 feeds**（5 分钟）
```bash
./scripts/feeds update -a
./scripts/feeds install -a
```

4. **配置菜单**（10 分钟）
```bash
make menuconfig
```
- 选择 Target System → x86
- 选择 Subtarget → x86_64
- 进入 Base system 取消不必要的包（仅为了体验）
- 进入 Network → Web Servers/Proxies 添加 `nginx`
- 保存退出

5. **编译**（将花费 15～60 分钟，取决于机器性能）
```bash
make -j$(nproc)
```

6. **验证输出**（5 分钟）
```bash
ls -la bin/targets/x86/64/
# 应该看到 openwrt-x86-64-generic-rootfs.tar.gz、openwrt-x86-64-generic-ext4-combined.img.gz 等文件
```

### 验收标准

- [ ] `bin/targets/x86/64/` 目录下有 `.img.gz` 固件镜像。
- [ ] 在解压的 rootfs 中能看到 `/usr/sbin/nginx`。
- [ ] 理解了 `make menuconfig` 中选择包后如何影响最终镜像大小（对比选择 nginx 前后 rootfs 的大小差异）。

### 无硬件替代方案

在 QEMU 中运行编译出的 x86/64 OpenWrt 镜像：
```bash
# 解压镜像
gunzip bin/targets/x86/64/openwrt-x86-64-generic-ext4-combined.img.gz

# 启动 QEMU（需要提前安装 qemu-system-x86）
qemu-system-x86_64 -drive file=bin/targets/x86/64/openwrt-x86-64-generic-ext4-combined.img,format=raw -net nic -net user -nographic

# 启动后登录，用户名 root，无密码
# 验证 nginx 已安装：opkg list-installed | grep nginx
```

## 10. 3 道深度追问题

**问题**: 为什么普通 Linux（ext4/xfs）掉电时通常不会完全损坏，而 OpenWrt 的 overlayfs+jffs2 掉电后更容易出问题？如果要设计一个"掉电安全"的包安装机制，你会怎么做？

### 问题 2（软件工程视角转嵌入式视角）

### 问题 3（工程判断）
**场景**: 你要为某款新路由器芯片移植 OpenWrt。你拿到了 SDK，但里面没有现成的 OpenWrt target 支持。官方 SDK 只在 Buildroot 上跑过。
**问题**: 你是应该从零编写一个 OpenWrt target（包括 kernel config、设备树、分区布局、镜像生成脚本），还是建议厂商直接把 Buildroot 方案转正？判断依据是什么？OpenWrt 的包管理（opkg）和 LuCI 带来的维护优势能否覆盖移植成本？请给出你的决策树。

## 12. 工程点评

### 可维护性 ★★★★☆
OpenWrt 的 Makefile 架构虽然看起来"不现代"，但有很强的自文档能力。每个包的 Makefile 只有 20～50 行，格式高度统一，新包贡献者可以在 10 分钟内看懂怎么写。UCI 和 ubus 的分层设计也保证了各组件之间低耦合。

扣分项：`rules.mk` 和 `include/*.mk` 之间有大量隐式全局变量传递，新手调试构建失败时很难追踪变量的值在哪个 `.mk` 文件中被修改。

### 可移植性 ★★★★☆
支持 20+ 种 CPU 架构（MIPS、ARM、x86、RISC-V、ARC...），数百种硬件设备。Image Builder 和 SDK 体系让厂商可以快速适配。

扣分项：内核补丁管理依赖 quilt 工具，每次内核版本升级需要重新 rebase 数百个补丁，这是一项繁重的手工工作。部分设备支持依赖于后向兼容代码，长期维护成本高。

### 可靠性 ★★★★☆
Procd + ubus 的进程管理比传统 init 脚本可靠得多。failsafe 模式、dual-image 分区升级、内核 panic 自动重启等设计考虑了嵌入式场景的典型故障。

扣分项：opkg 包安装没有事务保证（也不能有，因为 Flash 空间是稀缺资源无法预分配）。`opkg install` 中途失败可能导致系统状态不一致。

### 可测试性 ★★★☆☆
主要测试方式是"刷机到真实设备上跑"。社区有基于 QEMU 的 CI 测试（`tests/` 目录），但覆盖率远不如云原生项目。一个包的修改可能影响几十种设备，要靠社区众测。

扣分项：没有单元测试框架，没有集成测试模拟环境（如用网络命名空间模拟路由器网络拓扑的测试）。**这是从软件工程视角看最应该改进的地方**。

### 量产/运维角度 ★★★★☆
Image Builder 和 SDK 的设计非常适合量产——OEM/ODM 可以用脚本批量生成定制固件。opkg 支持 OTA 升级包安装。LuCI 提供网页管理界面，降低现场运维门槛。

扣分项：日志管理弱（默认不持久化日志，重启后日志丢失）。没有内置的远程诊断/遥测系统。大规模设备集群的集中管理需要第三方方案。
