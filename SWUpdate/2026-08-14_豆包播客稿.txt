今天这一期，我们来聊一个嵌入式 Linux 产品里绕不开的话题，就是设备出厂之后的软件升级，也叫 OTA。主角是一个在嵌入式圈子里非常有名、但纯软件背景的朋友可能没听说过的开源项目，叫 SWUpdate。它解决的问题很直白：一台嵌入式 Linux 设备，比如工业网关、医疗仪器、车载控制器或者摄像头，已经卖到客户现场去了，怎么把新固件、新内核、新系统安全可靠地装上去？注意，是"安全可靠"，因为现场的设备可能没人在旁边守着，网络说断就断，电说停就停，要是升级到一半变砖了，要么返厂，要么工程师出差，代价都很大。SWUpdate 就是专门为这个场景设计的一个更新框架，它从 2013 年维护到现在，项目非常活跃，就在昨天还有新的提交，被 Yocto、Buildroot 还有 Debian 官方仓库都集成了，可以说是嵌入式 Linux 更新领域事实上的标准方案之一。

先说为什么值得学。如果你是从纯软件转过来做嵌入式的，OTA 这个领域几乎是"软件工程概念和嵌入式约束"碰撞最密集的地方。你会发现很多你熟悉的东西在硬件世界里有完全不同的样子：蓝绿部署变成了 A/B 双分区，数据库的事务日志变成了 bootloader 环境变量里的一个字符，供应链安全变成了镜像签名，增量发布变成了基于 librsync 的增量更新。把 SWUpdate 读明白，等于同时复习了部署、事务、安全和容灾这四门课。而且我们之前已经学过 MCUboot、wolfBoot 这些 MCU 层的升级方案，SWUpdate 是 Linux 应用层的整机更新框架，两者在实际产品里经常配合使用，一个管单片机固件，一个管 Linux 系统，正好互补。

那它到底要面对哪些普通软件项目没有的约束呢？第一是断电安全。云端部署失败了可以马上回滚重试，但嵌入式设备升级写到一半停电，开机必须还能跑，这是第一优先级。第二是存储。eMMC、NAND 空间有限，搞双拷贝要牺牲一半容量，搞单拷贝又得保证出问题能恢复。第三是更新对象特别杂，内核、设备树、根文件系统、bootloader 的环境变量、UBI 卷、裸分区，甚至外挂单片机的固件，都得统一管理。第四是硬件兼容和版本控制，不能把 A 型号的镜像刷进 B 型号的机器，也不能降级到有已知 bug 的版本。最后还有安全，镜像要防篡改、防窃取、防中间人。这些约束堆在一起，决定了嵌入式 OTA 不能简单照搬云端的部署思路。

接下来看它的架构。SWUpdate 是一个单进程多线程的 C 程序，用 Kconfig 裁剪功能，编译期决定支持哪些后端。代码分层非常清楚。core 目录是核心，包括主入口、安装编排、handler 注册表、状态机、配置解析、bootloader 环境抽象，还有加密和流式安装这些工具。handlers 目录下有三十多个安装器，比如负责整体安装的 archive handler，把镜像直写裸分区的 raw handler，做 GPT 和 MBR 分区的 diskpart handler，写 UBI 卷的 ubivol handler，做增量更新的 delta handler，甚至还有管理容器、刷外部单片机固件、把更新转发给同网络其他设备的 handler。parser 目录解析 sw-description 描述文件，就是升级包的清单。suricatta 目录是远程更新通道，名字是狐獴的意思，像站岗放哨的哨兵，里面对接了 hawkBit 车队管理服务器、通用 HTTP 服务器，还允许用 Lua 写自定义通道。ipc 目录通过 Unix socket 把升级进度实时推给界面程序。bootloader 目录适配 U-Boot、GRUB、EFI Boot Guard 这些引导程序的环境变量读写。crypto 目录在 OpenSSL、mbedTLS、wolfSSL 三个加密库之间做可插拔选择。另外还有两种可选的嵌入式 Web 服务器，让你能用浏览器做本地升级。

运行流程是这样的：启动以后解析命令行和配置文件，注册所有 handler，然后按模式分发。本地文件模式直接安装一个升级包，下载模式先从 URL 拉镜像再装，suricatta 模式去轮询服务器看有没有新任务，Web 模式起一个网页界面。安装阶段，解析器把描述文件变成一张镜像列表，安装器遍历这张表，对每个镜像按类型字符串找到对应的 handler，执行安装，再跑安装前和安装后的脚本。最精彩的是状态持久化：升级开始前，SWUpdate 把 recovery_status 这个变量写进 bootloader 的环境区，置为 progress，成功之后清除，失败就置为 failed。下次开机，bootloader 一看到这个变量还挂着，就知道上次升级没完成，自动进入恢复流程或者启动旧副本。整套设计把升级当成一个事务来处理，而不是一次简单的文件拷贝。

源码陪读这部分，我建议按这个顺序看六个文件。第一个是 include 目录下的 swupdate_image.h，先看 img_type 这个结构体，它里面有类型名、归档里的文件名、目标设备、校验和、SHA 哈希、AES 密钥这些字段，这是贯穿整个项目的地图。第二个是 core 目录的 handler.c，只有一百六十多行，看 register_handler 和 find_handler，理解类型字符串到安装函数的路由机制，这是整个扩展体系的心脏。第三个是 installer.c，看安装编排：脚本执行、handler 分发、版本记录、bootloader 环境更新。第四个是 swupdate.c 里的 main 函数，理解启动流程和模式分发。第五个是 state.c，只有一百一十二行，看状态是怎么落到 bootloader 环境里的。最后选读 raw_handler.c，两百六十行，看一个最朴素的真实 handler：打开设备、写入、同步、回读校验，这是最容易上手的读码起点。

核心函数导读方面，main 函数是入口，选项字符串都是编译期根据 Kconfig 拼出来的，体现了配置驱动代码的思路。handler 注册表最多注册六十四个 handler，加一种新镜像格式就是写一个 C 函数加一行注册，这就是扩展点。installer 里的安装函数是编排核心，失败路径保证旧系统不被碰。状态机的读写函数是整个断电安全设计的基石。suricatta 的 hawkBit 客户端体现了设备主动拉取的模式，设备躲在 NAT 后面也能被统一管理。raw handler 里的写入函数则告诉你，嵌入式里写入为什么不能只调一次 write，必须 fsync，还要回读校验。

软件工程类比这块特别有意思。A/B 双拷贝更新就像蓝绿部署，两个副本一次只动一个，坏了切回去。但这个类比有局限：蓝绿部署在云端几乎零成本，嵌入式要付出一半存储空间，而且切换动作由 bootloader 决定，那是一个极简的、不在你代码控制范围内的程序。recovery_status 事务标记像数据库的提交日志，先写"正在升级"再动手，崩溃后靠它恢复。但这个日志只有一个字符的取值空间，没有回放能力，恢复动作全交给 bootloader 端简陋的逻辑。sw-description 描述文件像部署清单，声明这次发布包含什么、装到哪、允许什么版本，但它跑在老式配置解析器上，没有模板和变量，复杂逻辑全靠 Lua 补。镜像签名和加密像供应链安全工具，但公钥固化在设备里，一旦某台设备被物理破解，所有设备都面临风险，而且没有云端那种集中吊销的便利。handler 注册表像策略路由，但 C 语言手写注册，没有动态加载，加一个 handler 就要重新编译整个固件。

概念卡片这一块，我挑十个最关键的。OTA 就是通过网络把新软件送到现场设备并安装，类比生产环境的自动部署管道，坑点是很多人以为 OTA 只是传文件，其实安装阶段才是变砖高发区。A/B 分区是存两份系统一次只动不运行的那份，类比蓝绿部署，坑点是存储成本翻倍，而且切换逻辑在 bootloader，测试容易漏。事务标记是用持久化标志记录升级是否完成，类比数据库提交日志，坑点是标记写入本身也可能失败。bootloader 环境变量是引导程序存配置的持久化区，类比独立的配置存储，坑点是它有损坏风险，需要校验和双副本。CPIO 归档和升级包格式，是 SWUpdate 把描述文件和镜像打包成一个自包含的升级包，类比自带清单的发布压缩包，坑点是手工打包容易出错。流式安装是边下载边解包边写入，不落盘，类比流式处理管道，坑点是中断恢复更复杂。镜像签名校验用非对称密钥验证升级包来源，类比软件包签名，坑点是公钥轮换机制缺失会让密钥泄露变成灾难。硬件兼容性检查是安装前核对镜像和当前设备的型号，类比部署前的环境检查，坑点是硬件版本信息本身要可靠。增量更新只传新旧版本的差异，类比 rsync，坑点是旧版本不可控就没法生成差异，版本碎片化是最大敌人。最后是设备主动轮询模式，设备定期问服务器有没有新版本，类比消息队列里的拉模式，坑点是轮询周期要在流量成本和升级及时性之间权衡。

动手任务这里，给你一个完全不需要真实硬件的三十分钟任务。第一步，在 Ubuntu 或者 Debian 环境里安装 swupdate 包，或者从源码编译。第二步，写一个最简单的 sw-description，声明一个 raw 类型的镜像，指向一个测试文件，然后用 cpio 命令打成升级包，官方文档有现成的打包命令。第三步，用 dd 创建一个空镜像文件当目标磁盘，运行安装命令观察 handler 分发的日志。第四步，故意改坏测试文件重新打包，让校验不通过，观察它拒绝安装。验收标准就是你能看到注册的 handler 列表、分发到 raw handler 的日志、校验失败的报错，并且能向自己解释升级包里每个文件的作用。

最后留三道思考题。第一道偏时序和可靠性：升级中突然断电，重启后 bootloader 看到 progress 标记会怎么做？为什么先写标记再动手这个顺序本身就能保证安全？如果写标记这一步因为 NAND 磨损失败了怎么办？第二道要求你从软件工程视角转成嵌入式视角：云端部署失败就回滚很常见，为什么嵌入式设备的回滚不能简单等于重新部署旧版本？请至少列出三个嵌入式特有的障碍，再说明 A/B 方案是怎么规避的。第三道是工程判断：有人提议用 deb 包方式做增量更新省流量，请从可测试性、原子性、依赖管理、离线场景四个维度评价这个方案在量产设备上的风险。

今天的复盘问题也留给你：如果明天你的产品要上线 OTA 功能，你会先设计"更新失败时设备怎么办"，还是先设计"更新怎么传"？回顾 SWUpdate 的整个设计，你会发现它几乎处处都是失败路径优先，你自己写代码的时候，是成功路径优先还是失败路径优先？

最后做个工程点评。SWUpdate 的模块边界清晰，内核代码风格统一，文档完整，十年积累下来依然整洁。可移植性上，加密库三选一、Web 服务器二选一、bootloader 多适配，移植到新产品主要就是写 handler 和做 bootloader 适配。可靠性上，事务标记、回读校验、断电安全、双拷贝策略，把升级当作事务处理，这是它最值得学习的地方。可测试性上，它带测试目录，但强依赖真实硬件环境，纯单元测试覆盖有限，这恰恰说明了硬件在环测试的必要性。量产运维上，Yocto 和 Buildroot 集成、hawkBit 车队管理、进度接口对接界面，是被十年工业实践验证过的成熟方案。局限也有，配置面复杂，Kconfig、libconfig、Lua 三套东西叠加，学习曲线比较陡。

明天你可以往三个方向延伸。一个是搭一个本地 hawkBit 实例，用 Docker 起服务，配一个模拟设备，跑通服务器下发、设备拉取、安装、上报的完整闭环。第二个是研究增量更新，读 delta handler 的实现，理解 librsync 在窄带场景下的取舍。第三个是把 SWUpdate 和之前学过的 MCUboot 放在一起对比，想想两层怎么协作，画出 U-Boot 做 A/B 切换、SWUpdate 写备用分区的完整升级时序图。今天的分享就到这里，我们明天见。
