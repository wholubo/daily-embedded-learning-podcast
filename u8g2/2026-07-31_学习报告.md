# 每日嵌入式学习：u8g2

## 1. GitHub 项目链接与一句话介绍

**仓库地址：** https://github.com/olikraus/u8g2

u8g2 是一个纯 C 编写的单色图形库，专为嵌入式设备上的 OLED 和 LCD 显示屏提供统一的绘图、字体渲染和硬件抽象能力。

## 2. 为什么今天选它

u8g2 拥有超过 6600 颗 Star，持续维护至今（2026 年 7 月仍有更新），是嵌入式显示库领域最成熟的开源方案之一。它支持 50 多种显示控制器芯片，覆盖从 64×32 像素的微型 OLED 到 256×128 像素的大屏 LCD，几乎所有你做硬件项目时会用到的单色屏都能被它驱动。

对于有软件工程背景的开发者来说，u8g2 是一个学习"如何用 C 实现面向对象设计"和"如何在极低资源环境下做图形系统"的绝佳教材。它没有用 C++ 的虚函数，而是用回调函数指针和结构体组合来实现多态，这种做法在嵌入式 C 代码中非常普遍。

## 3. 项目解决的问题

在嵌入式产品中，几乎任何带屏幕的设备——智能手表、工业面板、手持仪器、3D 打印机状态屏、ESP32 物联网设备——都需要在单色屏上显示文字、图标、波形和简单 UI。但单色屏没有自己的帧缓存控制器，你需要用 MCU 的 RAM 缓存画面，再通过 SPI 或 I2C 逐像素推送到屏幕。

与普通的桌面或手机图形库不同，u8g2 面临的约束包括：

- **内存极度受限**：目标 MCU 可能只有 2KB RAM，而一块 128×64 的屏幕需要 1024 字节帧缓存，几乎占掉一半内存。
- **没有 GPU**：画线、画圆、字体渲染全靠 CPU 逐像素计算。
- **通信带宽低**：I2C 速率通常 400Kbps，刷满一屏需要数十毫秒。
- **控制器协议碎片化**：每块屏的初始化命令序列不同，有的用 SPI 有的用 I2C，有的需要特殊的 D/C 引脚切换。

u8g2 通过分层架构和"分页渲染"（page mode）机制解决了这些问题，让开发者可以用统一 API 操作任意屏幕，同时在内存不足时只缓存一小块画面就刷新一部分。

## 4. 技术架构分析

u8g2 采用四层架构，从底向上依次是：

### GPIO 与延时层
最底层负责实际的引脚操作和时间延迟。不同 MCU 平台（AVR、STM32、ESP32、Linux）各自实现一组回调函数，提供毫秒级延时、GPIO 读写等基础操作。

### 字节传输层（Byte Layer）
这一层负责通过 SPI、I2C 或软件位操作将字节发送到显示屏。它屏蔽了物理总线差异，向上提供统一的"发一个字节"接口。

### 命令/参数/数据层（CAD Layer）
显示屏控制器通常需要区分"命令字节"和"数据字节"，靠一根 D/C（数据/命令）引脚线来切换。CAD 层封装了这套协议，向上提供 `SendCmd`、`SendArg`、`SendData` 三个语义清晰的接口。

### 显示驱动层（Display Driver）
每种屏幕控制器（如 SSD1306、SH1107、ST7567）有自己的驱动文件，负责初始化序列、设置对比度、关闭显示等操作。

### u8g2 图形层
最上层提供绘图 API：画点、画线、画框、画圆、字体渲染、位图绘制、Unicode 支持等。它维护一个"tile 缓冲区"——以 8 像素高为一行的显示内存——并通过 FirstPage/NextPage 循环实现分页渲染。

### U8x8 文本子库
u8g2 内部还包含 U8x8，一个极简的纯文本输出库。它不缓存帧，直接向屏幕写字符，只需 8×8 像素网格字体，适合 RAM 极度紧张的场景。

### MUI 用户界面子系统
u8g2 还附带 MUI（Monochrome User Interface），一套轻量级菜单和表单系统，用声明式 FDS（Form Definition String）语法定义 UI 布局，支持按钮、选择列表、数值输入等控件。

## 5. 源码陪读：今天只读哪几个文件

**阅读顺序建议：**

1. **`csrc/u8x8.h`** — 先读这个头文件，理解底层回调架构。重点看 u8x8_t 结构体和消息枚举定义。
2. **`csrc/u8g2.h`** — 核心头文件，理解 u8g2_t 结构体、16 位/8 位模式切换、功能裁剪宏。
3. **`csrc/u8g2_setup.c`** — 初始化流程入口，理解 `u8g2_SetupBuffer` 如何把缓冲区、回调、旋转方向串联起来。
4. **`csrc/u8g2_buffer.c`** — 分页渲染的核心逻辑，重点看 `u8g2_FirstPage`、`u8g2_NextPage`、`u8g2_SendBuffer`。
5. **`csrc/u8g2_font.c`** — 字体渲染引擎，理解 u8g2 自定义的二进制字体格式和 RLE 编码方案。

## 6. 核心模块/函数导读

### `u8g2_SetupBuffer()`（u8g2_setup.c）
这是整个库的初始化入口。它接收一个缓冲区指针、缓冲区高度（以 tile 为单位）、底层画线回调和旋转配置，把所有内部状态清零并计算显示尺寸。类比后端的 `app.bootstrap()`，但每一步都手动配置，没有默认值魔法。

### `u8g2_FirstPage()` / `u8g2_NextPage()`（u8g2_buffer.c）
这两个函数实现了 u8g2 最核心的"分页渲染"模式。FirstPage 重置缓冲区到第一行，NextPage 把当前缓冲区刷到屏幕并前进到下一行。开发者在 `do { ... } while(u8g2_NextPage(u8g2))` 循环中写绘图代码，每次循环只画一页大小的区域。这种模式让 128×64 的屏只用 128 字节就能完整渲染——代价是所有绘图操作会被重复执行多次。

### `u8x8_cad_SendCmd()` / `u8x8_cad_SendData()`（u8x8_cad.c）
CAD 层是驱动与硬件的翻译层。`SendCmd` 拉低 D/C 引脚然后发字节，`SendData` 拉高 D/C 引脚然后发字节。每种屏幕控制器有不同的 CAD 变体（如 `u8x8_cad_ssd13xx_i2c`），处理不同控制器的特殊协议要求。

### `u8g2_m_16_8_f()`（u8g2_d_memory.c）
这是自动生成的内存分配函数。每个显示屏尺寸对应一个函数，返回一个静态分配的缓冲区。后缀 `_1`、`_2`、`_f` 分别代表 1 页、2 页和全页（full）缓冲模式。全页模式一次性分配整个帧缓存，分页模式只分配一小块。

### MUI 表单系统（mui.h / mui.c）
MUI 用一种紧凑的声明式语法（FDS）定义 UI 表单，包含样式切换、标签、按钮、数值输入等控件。它在极低资源下实现了类似 HTML 表单的交互模型，是嵌入式 UI 设计中"声明式 UI"思想的早期实践。

## 7. 软件工程师类比解释

### 类比 1：u8g2_t 结构体 ≈ 依赖注入容器
`u8g2_t` 里存了显示回调、字体指针、缓冲区、裁剪窗口、绘图状态等，类似 Spring 的 ApplicationContext。你把平台相关的实现"注入"进去，上层代码就不再依赖具体硬件。
**局限**：DI 容器通常有自动装配和生命周期管理，u8g2 完全是手动接线，没有自动解析依赖。

### 类比 2：FirstPage/NextPage 分页循环 ≈ 流式分页查询
想象你在查询一个大数据集但内存只能放 100 行——你用 cursor 翻页，每页处理后丢弃。u8g2 的分页渲染同理：缓冲区只够放一小块，渲染完刷到屏幕，清空后继续下一块。
**局限**：数据库分页是一次性读取，u8g2 的分页循环里所有绘图命令会被重复执行多次（每页都重新画一遍），这在后端是完全不存在的模式。

### 类比 3：CAD 层 ≈ HTTP 中间件
CAD 层在"应用层意图"（发命令/发数据）和"传输层细节"（SPI/I2C 字节发送）之间做协议适配，类似 Express 中间件在路由逻辑和 TCP 连接之间做 HTTP 协议解析。
**局限**：HTTP 中间件通常是可组合的链式结构，CAD 层是单层适配，没有链式组合能力。

### 类比 4：u8g2 字体格式 ≈ Web Font 子集化
u8g2 的自定义二进制字体格式把字形数据用 RLE 压缩存储，支持按需裁剪字符集（只包含你需要的字符），类似 Web 开发中用 fonttools 做字体子集化来减小传输体积。
**局限**：Web Font 子集化发生在构建时，u8g2 字体是在编译时就固定好的，运行时不能动态加载新字体文件。

### 类比 5：MUI 表单系统 ≈ React 声明式 UI 的极简版
MUI 用 FDS 字符串声明 UI 布局，回调函数处理交互，和 React 用 JSX 声明 UI、用事件处理函数响应交互的思路类似。
**局限**：MUI 没有虚拟 DOM、没有 diff 算法、没有组件树，它的"声明式"更接近配置文件而非编程框架。

## 8. 今日 10 个嵌入式概念卡片

### 卡片 1：Tile（瓦片）
u8g2 把屏幕按 8 像素高切分成若干行，每一行叫一个 tile。这是帧缓存的最小单位。
**类比**：数据库的分片（shard），把一个大的数据集切成可管理的小块。
**场景**：128×64 的 OLED 有 8 个 tile 行（64÷8）。
**坑点**：tile 高度固定为 8，不是任意值；如果你的显示内容跨 tile 边界，绘图函数需要处理跨行计算。

### 卡片 2：Page Mode（分页模式）
当 RAM 不够存整屏帧缓存时，u8g2 只分配 1 个或几个 tile 的缓冲区，通过 FirstPage/NextPage 循环多次渲染整屏。
**类比**：流式处理大文件，每次只读一个 chunk。
**场景**：ATmega328P 只有 2KB RAM，用分页模式驱动 128×64 屏只需 128 字节。
**坑点**：循环内所有绘图命令会被执行多次，不要在循环里做随机数或递增计数器。

### 卡片 3：Full Buffer Mode（全缓冲模式）
RAM 充足时，一次性分配整屏帧缓存，所有绘图操作直接写入缓存，最后一次性刷到屏幕。
**类比**：把整个文件加载到内存再处理。
**场景**：ESP32 有 520KB RAM，全缓冲 128×64 屏只占 1024 字节，毫无压力。
**坑点**：全缓冲模式下 FirstPage/NextPage 循环只执行一次，但调用方式不变，代码兼容。

### 卡片 4：D/C Pin（数据/命令引脚）
SPI 和并行接口显示屏用一根额外的 GPIO 线区分当前发送的是命令还是数据。
**类比**：HTTP 协议用 Content-Type 头区分请求体是 JSON 还是文件上传。
**场景**：SSD1306 的 SPI 模式下，D/C=0 表示命令，D/C=1 表示数据。
**坑点**：I2C 显示屏通常没有 D/C 引脚，改用 I2C 地址位区分命令和数据，CAD 层会自动处理这种差异。

### 卡片 5：Framebuffer（帧缓存）
存储当前屏幕所有像素状态的内存区域。单色屏每个像素只需 1 bit。
**类比**：前端 Canvas 的 ImageData 对象。
**场景**：128×64 单色屏需要 128×64÷8 = 1024 字节帧缓存。
**坑点**：帧缓存的位排列方式取决于控制器，有的是列优先（column-major），有的是行优先，u8g2 的 ll_hvline 回调负责适配。

### 卡片 6：Callback-driven HAL（回调驱动的硬件抽象层）
u8g2 不直接调用硬件 API，而是通过函数指针回调让平台层注入具体实现。
**类比**：Node.js 的依赖注入模式，把 db connection 通过构造函数传入 service。
**场景**：同一份 u8g2 代码可以在 STM32 上用硬件 SPI，在 ESP32 上用软件 SPI，只需换回调。
**坑点**：回调函数签名必须严格匹配，C 没有编译器级别的类型安全保证，容易传错参数。

### 卡片 7：RLE Font Encoding（游程编码字体）
u8g2 的字形数据用游程编码压缩——连续相同像素用"重复 N 次"表示，大幅减少字体体积。
**类比**：CSS 的 `repeating-linear-gradient`，用简短描述表达重复模式。
**场景**：一个 8×16 的字符如果用原始位图要 16 字节，RLE 编码后可能只需 6-8 字节。
**坑点**：RLE 参数（bits_per_0、bits_per_1）在字体头中定义，不同字体使用不同参数，解码时必须按头信息解析。

### 卡片 8：Clip Window（裁剪窗口）
限制绘图操作只在指定矩形区域内生效，区域外的像素不写入帧缓存。
**类比**：CSS 的 `overflow: hidden` 和 `clip-path`。
**场景**：在滚动列表中，只显示可见区域的条目，其余裁剪掉。
**坑点**：裁剪窗口需要消耗约 200 字节 Flash，在 AVR 上可以通过 `U8G2_WITHOUT_CLIP_WINDOW_SUPPORT` 关闭。

### 卡片 9：Font Rotation（字体旋转）
u8g2 支持 0°、90°、180°、270° 四个方向的文字绘制。
**类比**：CSS 的 `writing-mode: vertical-rl`。
**场景**：竖屏设备上需要横着显示文字时用到。
**坑点**：启用字体旋转会增加约 600 字节 Flash 开销，在资源紧张的 AVR 上可以用 `U8G2_WITHOUT_FONT_ROTATION` 关闭。

### 卡片 10：PROGMEM（程序存储器）
AVR 架构中，字体数据等大常量存储在 Flash 而非 RAM 中，需要通过 `pgm_read_byte` 特殊指令读取。
**类比**：把静态配置文件放在磁盘而非加载到内存，需要时再读取。
**场景**：u8g2 的字体数据全部标记为 `PROGMEM`，避免占用宝贵的 2KB RAM。
**坑点**：忘记用 `pgm_read` 读取 PROGMEM 数据会得到垃圾值，在非 AVR 平台上这个宏退化为直接内存访问，容易忽略这个差异。

## 9. 30～60 分钟动手任务

### 任务：在 Linux 上用 u8g2 的 SDL 模拟器画一个简单界面

**目标**：不需要硬件，在 PC 上编译运行 u8g2 的 SDL 模拟版本，画出一个包含矩形、圆形和文字的简单界面。

**步骤**：
1. 克隆仓库：`git clone https://github.com/olikraus/u8g2.git`
2. 进入 sys 目录找 SDL 相关示例（通常在 `sys/sdl` 目录下）
3. 确保安装了 SDL2 开发库：`sudo apt install libsdl2-dev`
4. 编译示例程序：`make`
5. 修改主循环，添加自己的绘图代码：
   - 画一个 128×64 的边框
   - 在中间画一个圆
   - 在圆下方写一行 "Hello u8g2"
6. 运行查看效果

**验收标准**：
- 程序能编译运行并弹出 SDL 窗口
- 窗口中显示你画的矩形、圆和文字
- 能用 FirstPage/NextPage 循环观察分页渲染的过程

**无硬件替代方案**：本任务本身就是纯软件模拟方案。

## 10. 3 道深度追问题

### 追问题 1（时序/并发）
在 FreeRTOS 多任务环境中，如果任务 A 在 u8g2 分页循环的中间被任务 B 抢占，而任务 B 也调用 u8g2 绘图函数，会发生什么？你应该如何保护 u8g2 的共享状态？请对比互斥锁保护和消息队列排队两种方案的优劣。

### 追问题 2（软件工程视角转嵌入式）
在后端开发中，我们习惯用"一次性加载所有数据到内存然后处理"的模式。u8g2 的分页模式要求"所有绘图操作被重复执行多次"。请分析这种模式在以下场景中的性能影响：循环中有一个复杂的贝塞尔曲线绘制函数，每次调用需要 200 微秒，屏幕有 8 个 tile。总耗时是多少？你会如何优化？

### 追问题 3（资源权衡）
一块 256×128 的单色屏需要 4096 字节帧缓存。你的 MCU 有 8KB RAM，但同时还需要运行 MQTT 客户端（约 2KB）、传感器缓冲（约 1KB）和 TCP 栈（约 2KB）。你会选择全缓冲模式还是分页模式？分页模式下 4 页渲染的总耗时与全缓冲模式相比，差多少？请考虑 SPI 传输时间和 CPU 绘图时间。

## 12. 工程点评

**可维护性**：u8g2 的代码结构清晰，分层明确，但大量自动生成的驱动文件（如 `u8g2_d_memory.c`）让维护变得机械。字体文件 `u8g2_fonts.c` 有几百 KB，包含数百种预编译字体，修改和维护成本较高。

**可移植性**：通过回调机制实现了极好的可移植性，从 8 位 AVR 到 64 位 Linux 都能用同一套 API。这种"C 语言面向对象"的模式值得学习。

**可靠性**：代码经过十余年打磨，边界检查充分，分页模式的内存使用经过精确计算。但在多线程环境下没有内建保护，需要使用者自行加锁。

**可测试性**：SDL 模拟器提供了很好的集成测试手段，但缺少单元测试框架。字体解码、裁剪计算等纯函数非常适合用 gtest 或 Unity 做单元测试。

**量产/运维**：u8g2 被广泛用于商业产品，Arduino 库管理器中安装量巨大。但它的许可证是 BSD 两条款，对商用友好。需要注意的是，字体文件体积较大，在 Flash 紧张的产品中需要裁剪不用的字体。
