# 每日嵌入式学习：Mbed TLS

## 1. GitHub 项目链接与一句话介绍

- 仓库链接：https://github.com/Mbed-TLS/mbedtls
- Mbed TLS 是 ARM 主导的开源嵌入式 TLS/DTLS 协议栈实现，提供 X.509 证书解析、PSA Crypto API 密码学抽象层，为物联网设备提供与云端安全通信的最小化 C 语言库。

## 2. 为什么今天选它

Mbed TLS 是嵌入式安全通信的"事实标准"——它在全球数十亿台物联网设备上运行，包括智能家居、工业传感器、汽车 ECU、医疗设备和边缘网关。选择它的核心原因有三：

- **工程完整度极高**：项目有近 7000 颗 Star，持续活跃开发中（上次提交 2026 年 7 月 20 日），拥有完整的 CI/CD 测试体系、文档、示例程序和测试套件。
- **软件工程师的理想过渡桥**：TLS/HTTPS 是每个后端工程师熟悉的网络概念，但把 TLS 塞进一个只有几十 KB RAM 的 MCU，和在 Linux 服务器上用 OpenSSL 完全是两回事。Mbed TLS 让你从"后端安全协议使用者"变成"嵌入式安全库的设计者和裁剪者"。
- **模块化设计极具学习价值**：它把 TLS 协议拆成密码学库（Crypto）、X.509 证书库（X.509）和 TLS 协议层（TLS）三个库，每个都可以独立编译和裁剪，完美体现嵌入式软件的"按需取用"设计哲学。

## 3. 项目解决的问题

Mbed TLS 解决的核心问题是：**在资源极度受限的微控制器上实现 TLS/DTLS 安全通信**。

真实产品场景：
- 一个温度传感器通过 Wi-Fi 模块把数据加密上报到 AWS IoT Core
- 一个智能门锁通过 BLE 接收手机发来的加密开锁指令
- 一个工业 PLC 通过 DTLS 与云平台建立安全的 UDP 通信通道
- 一个汽车 OBD-II 诊断仪验证服务器的 X.509 证书身份

和普通软件项目的区别在于硬件资源约束：

- **内存约束**：一个典型的 Cortex-M4 MCU 可能只有 64KB RAM 和 256KB Flash。Mbed TLS 需要在这 64KB 里完成 TLS 握手、证书链验证、密钥协商和加解密。作为对比，一台 Linux 服务器的 OpenSSL 可以随意分配几 MB 内存做同样的工作。
- **时序约束**：TLS 握手涉及多个网络往返。在 DTLS 模式下，握手可能因为丢包而重传，代码需要处理超时和重传逻辑。
- **可靠性约束**：证书解析必须在有限的栈空间内完成。一个格式错误的证书不能导致整个设备崩溃——而服务器端的 OpenSSL 遇到崩溃可以快速重启，嵌入式设备重启可能意味着用户需要拔插电池。
- **功耗约束**：TLS 握手是计算密集型操作。在电池供电设备上，每多一次证书验证，都直接缩短续航。

## 4. 技术架构分析

Mbed TLS 采用经典的三层架构设计（基于公开文件推断）：

### 分层架构

```
┌─────────────────────────────────┐
│     用户应用程序                │
│  (MQTT/CoAP/HTTP over TLS)      │
├─────────────────────────────────┤
│   TLS 协议层 (libmbedtls)       │
│   - 握手状态机 (ssl_tls.c)      │
│   - TLS 1.2 客户端/服务器       │
│   - TLS 1.3 客户端/服务器       │
│   - DTLS 支持                   │
│   - 会话缓存/恢复               │
├─────────────────────────────────┤
│   X.509 证书层 (libmbedx509)    │
│   - 证书解析 (x509_crt.c)       │
│   - CRL 解析                    │
│   - CSR 生成                    │
│   - 证书链验证                  │
├─────────────────────────────────┤
│   密码学层 (libtfpsacrypto)     │
│   - 对称加解密 (AES/CHACHA20)   │
│   - 公钥运算 (RSA/ECC)          │
│   - 哈希 (SHA256/SHA384)        │
│   - 随机数生成 (CTR_DRBG)       │
│   - PSA Crypto API 实现         │
├─────────────────────────────────┤
│   硬件抽象层                    │
│   - 网络 I/O (net_sockets.c)    │
│   - 时间/定时 (timing.c)        │
│   - 熵源 (硬件TRNG/HAL)         │
│   - PSA 驱动级接口              │
└─────────────────────────────────┘
```

### 配置系统

项目的灵魂在 `mbedtls_config.h`——这是一个 1189 行的头文件，每一行都是一个编译时开关。你在 64KB Flash 的 MCU 上部署时，关掉不需要的密码套件（比如关掉 RSA 只用 ECC），把 SSL 输入缓冲区从 16KB 缩小到 2KB——每个配置项都直接影响二进制大小和运行时内存。

关键设计特点：
- **编译时裁剪**：所有功能模块均通过 `#define` 宏在编译前决定是否包含。未启用的功能不产生任何代码和数据结构。
- **PSA Crypto API**：ARM 推出的跨平台密码学 API 标准，Mbed TLS 是其参考实现。这让上层应用可以用统一接口调用密码学操作，底层可以替换为硬件密码学加速器（如 NXP LPC55xx 系列内置的 CryptoCell）。
- **MPS（Message Passing System）**：一个内部消息传递抽象层，用于管理 TLS 记录的序列化、反序列化和数据流处理。这是 Mbed TLS 2.x 时代引入的重要重构。
- **Session 序列化**：支持将 TLS 会话保存到 NVM（非易失存储器），下次开机直接恢复，绕过完整的握手过程——这在低功耗设备上可以节省大量握手时间的电量。

## 5. 源码陪读：今天只读哪几个文件

推荐以下 5 个文件，按此顺序阅读：

### 1. `include/mbedtls/mbedtls_config.h`
**阅读目标**：理解嵌入式 C 库的"编译时配置"设计模式。看到 1189 行条件宏如何控制整个库的大小和功能集。

### 2. `include/mbedtls/ssl.h`
**阅读目标**：理解一个嵌入式 TLS API 的总设计——错误码体系、上下文结构体（mbedtls_ssl_context）、配置结构体（mbedtls_ssl_config）的分层设计。

### 3. `library/ssl_tls.c`
**阅读目标**：这是 TLS 协议实现的"中枢神经系统"——会话初始化、密钥派生、握手状态重置。重点看 `mbedtls_ssl_setup` 和 `ssl_handshake_init` 函数的上下文管理逻辑。

### 4. `include/mbedtls/x509_crt.h`
**阅读目标**：理解 X.509 证书在嵌入式环境下的数据结构设计——链式结构、内存管理策略（谁拥有 raw buffer？）、解析流程。

### 5. `library/ssl_client.c`
**阅读目标**：一个实际的 TLS 客户端实现源码。看它如何使用 MPS 层、如何管理发送和接收缓冲区、如何处理非阻塞 I/O 和重试逻辑。

## 6. 核心模块/函数导读

### 1. `mbedtls_ssl_setup()`（位于 `ssl_tls.c`）
这是每个 TLS 连接的初始化入口。它接收一个已初始化的 `ssl_context` 和 `ssl_config`，分配握手所需的内部数据结构。重点：在分配失败时返回 `MBEDTLS_ERR_SSL_ALLOC_FAILED`，上层应用必须检查返回值——嵌入式代码没有异常机制。

### 2. `mbedtls_ssl_handshake()`
TLS 握手的顶层状态机。它被设计为"可重入"的——在有 DTLS 或非阻塞网络 I/O 时，一次 `handshake` 调用可能返回 `MBEDTLS_ERR_SSL_WANT_READ` 或 `MBEDTLS_ERR_SSL_WANT_WRITE`，上层必须在下次事件循环中重新调用。这与 Linux 下 `connect()` 阻塞直到完成的方式完全不同。

### 3. `mbedtls_ssl_config` 和 `mbedtls_ssl_context`
嵌入式 TLS 库的核心数据结构分离设计：
- `mbedtls_ssl_config`：保存"配置"——哪些密码套件、证书链、认证模式。多个连接可以共享同一个配置对象。
- `mbedtls_ssl_context`：保存"状态"——当前握手阶段、发送/接收缓冲、会话密钥。每个连接一个，独立分配。

### 4. `ssl_handshake_init()`（静态函数，`ssl_tls.c`）
在 `mbedtls_ssl_setup` 内部被调用，做握手数据的实际分配。注意看它的错误回滚逻辑：如果握手初始化在中途失败，它必须回滚已经分配的所有子结构。这在嵌入式 C 中是用 goto cleanup 模式实现的——没有 RAII，没有析构函数，全靠手动管理。

### 5. `mbedtls_x509_crt_parse()`
X.509 证书解析的核心入口。它接受 DER 或 PEM 格式的证书数据，把它解析成链式结构。它对栈空间非常敏感——一次证书链验证可能涉及多个递归的 ASN.1 解析调用。如果栈帧分配太大，在 8KB 栈空间的 MCU 上就会直接栈溢出。

## 7. 软件工程师类比解释

### 类比 1：编译时配置（`mbedtls_config.h`） vs Spring Boot 的 application.yml
- **嵌入式**：`mbedtls_config.h` 中的每个 `#define` 开关在编译器预处理阶段就被解析。未启用的功能直接从代码中剔除，产生的二进制文件不包含任何相关指令或数据。
- **后端**：Spring Boot 的 application.yml 在运行时由框架解析，虽然也能控制功能开关，但所有 Bean 定义仍然在 classpath 中，只是在运行时不初始化。
- **局限**：编译时配置意味着改变一个功能开关必须重新编译整个固件。这在 IoT 场景下需要 OTA 更新，不像后端改配置文件后热重启那么简单。

### 类比 2：PSA Crypto API（`psa_crypto_init()`） vs JDBC 标准接口
- **嵌入式**：PSA Crypto API 定义了一套统一的密码学操作接口。底层可以用纯软件实现（比如 AES 用查表法），也可以用硬件密码学加速器。上层代码不需要知道底层是软件还是硬件。
- **后端**：JDBC 也是统一接口，底层可以用 MySQL 驱动、PostgreSQL 驱动或 H2 内存数据库。上层只用 `Connection`、`Statement`、`ResultSet`。
- **局限**：JDBC 的 SQL 语法有一定标准可依赖。而 PSA Crypto API 的硬件加速实现可能只支持特定算法——如果硬件不支持 SHA-384，库必须回退到软件实现，性能和功耗差异巨大。应用层难以感知这种降级。

### 类比 3：`MBEDTLS_ERR_SSL_WANT_READ` 非阻塞返回值 vs JavaScript 的 async/await
- **嵌入式**：`mbedtls_ssl_handshake()` 在 DTLS 或非阻塞模式下，遇到网络数据未就绪会返回 `WANT_READ`。调用者必须保存上下文，在下次事件循环中再次调用同一个函数。
- **前端**：JavaScript 的 async/await 在遇到 await 时也会"暂停执行"，但语言运行时自动管理栈帧的保存和恢复。
- **局限**：嵌入式非阻塞返回完全由开发者手动管理——你必须手动保存当前状态、在下次调用时恢复、确定当前该发送还是接收。没有语言级的 async state machine 帮你做这些事情。一个常见的 bug 是在 `WANT_READ` 返回后错误地重传了已经发送的数据。

### 类比 4：会话序列化（`ssl_session_save/load`） vs Redis 的 Session Store
- **嵌入式**：TLS 握手完成后，可以通过 `ssl_session_save()` 把会话状态序列化到 NVM（Flash/EEPROM）。设备下次上电时直接 `ssl_session_load()` + `mbedtls_ssl_set_session()` 恢复，跳过完整的握手。
- **后端**：Redis Session Store 保存的是 HTTP 会话——用户登录状态、购物车内容等应用层数据。
- **局限**：Redis Session 保存的是纯应用数据，恢复后不存在协议层兼容性问题。嵌入式 TLS 会话恢复需要 TLS 服务器端也支持会话恢复（RFC 5077 或 Session ID）。而且 Flash 写入有擦除次数限制——每次握手后都写 Flash 会很快磨损存储介质。

## 8. 今日 10 个嵌入式概念卡片

### 卡片 1：编译时配置（Compile-Time Configuration）
- **一句话**：通过预处理宏在编译前决定哪些功能被编译进固件，未启用的功能完全不产生代码。
- **软件类比**：类似后端框架的 feature flag，但后端是在运行时判断，嵌入式是在编译时就决定了。
- **常见场景**：Mbed TLS 的 `mbedtls_config.h`、FreeRTOS 的 `FreeRTOSConfig.h`、Zephyr 的 Kconfig。
- **坑点**：改一个配置就要重新编译整个固件。如果产品有多个 SKU，需要维护多套配置文件。

### 卡片 2：PSA Crypto API
- **一句话**：ARM 推出的统一密码学接口标准，让上层应用不依赖具体密码学实现（软件或硬件）。
- **软件类比**：类似 Java JCA（Java Cryptography Architecture），应用通过 `Cipher.getInstance("AES/GCM/NoPadding")` 获得标准密码学操作。
- **常见场景**：IoT 设备身份认证、固件签名验证、安全通道建立。
- **坑点**：不是所有硬件加速器都支持 PSA API 的全部功能。依赖硬件加速的代码在移植到不同 MCU 时可能暴露功能缺失。

### 卡片 3：ASN.1 解析
- **一句话**：X.509 证书使用 ASN.1（Abstract Syntax Notation One）编码，解析器需要逐字节解码 TLV（Tag-Length-Value）结构体。
- **软件类比**：类似 Protobuf 的 `.proto` 文件定义的数据结构，但 ASN.1 更古老、更复杂，没有自动代码生成工具链。
- **常见场景**：解析 SSL 证书、解析 SNMP MIB、解析 PKCS#7 签名。
- **坑点**：ASN.1 解析是栈消耗大户。一个深度嵌套的证书链解析可能导致栈溢出。需要精确控制递归深度和栈分配。

### 卡片 4：WANT_READ / WANT_WRITE 非阻塞模式
- **一句话**：TLS 协议库在非阻塞 I/O 模式下，每次握手续传都需要应用层重新调用的设计模式。
- **软件类比**：类似 Linux epoll 的 EAGAIN 返回值，但 TLS 握手的"重新调用"更复杂，因为握手状态机有多条路径。
- **常见场景**：DTLS 通信、低功耗蓝牙 TLS、资源受限设备上的 TCP/TLS 混合栈。
- **坑点**：开发者可能错误地假设 `mbedtls_ssl_handshake()` 一次性完成；在非阻塞时必须实现状态恢复逻辑，否则会发送重复数据或丢失握手状态。

### 卡片 5：熵源（Entropy Source）
- **一句话**：密码学安全随机数生成器需要从物理噪声源（硬件 TRNG、ADC 噪声、时钟抖动）获取熵（entropy）。
- **软件类比**：类似 `/dev/urandom` 在 Linux 上的角色，但 MCU 上没有内核帮你管理熵池和随机数生成。
- **常见场景**：TLS 握手中的临时密钥生成、固件升级时的质询-响应。
- **坑点**：没有硬件 TRNG 的 MCU 需要软件熵源（如多个 ADC 采样的最后几位）。如果熵不够"随机"，生成的私钥容易被预测。这是 IoT 设备安全漏洞的常见来源。

### 卡片 6：握手状态机（Handshake State Machine）
- **一句话**：TLS 握手过程被建模为一个有限状态机，每个状态对应一个握手消息的发送或接收。
- **软件类比**：类似 HTTP 协议的请求-响应状态机，但 TLS 握手有更多状态和更复杂的协商逻辑（版本协商、密码套件协商、密钥交换）。
- **常见场景**：任何 TLS 连接建立过程；MQTT over TLS 的第一个连接就是一次完整的 TLS 握手。
- **坑点**：客户端和服务器各自维护状态机，但两者不是完全同步的。TLS 1.3 简化了状态机但引入了"0-RTT 早期数据"等新概念，处理不当会导致数据丢失或安全漏洞。

### 卡片 7：内存池分配（Mbed TLS 内部缓冲策略）
- **一句话**：嵌入式 TLS 库通过预分配固定大小的内存缓冲区来避免动态内存碎片化。
- **软件类比**：类似 Go 的 `sync.Pool` 对象池，但 Mbed TLS 的缓冲区大小在编译时就固定了（`MBEDTLS_SSL_IN_CONTENT_LEN` 和 `MBEDTLS_SSL_OUT_CONTENT_LEN`）。
- **常见场景**：接收缓冲区 16KB 可以容纳最大 TLS 记录；发送缓冲区 16KB 缓存应用数据。
- **坑点**：如果缓冲区设小了（比如 2KB），无法接收来自服务器的超大证书链（超过 2KB）。如果设大了（16KB），64KB RAM 的 MCU 可能直接 OOM。内存是嵌入式项目中最需要精确计算的资源。

### 卡片 8：证书链验证（Certificate Chain Validation）
- **一句话**：验证服务器证书从叶子 CA 到根 CA 的完整信任链，每个证书的签名必须由上一级 CA 的私钥签署。
- **软件类比**：类似 HTTPS 中的证书验证，但后端通常由操作系统或运行时库处理，嵌入式需要在 MCU 上逐级验证。
- **常见场景**：设备连接 AWS IoT Core 时验证服务器证书、设备 OTA 更新服务器身份验证。
- **坑点**：根证书列表的存储方式——FATFS 上读文件、从 Flash 数组直接加载、还是编译时嵌入代码段？每种方式都有不同的安全含义和存储开销。嵌入在代码段中避免了文件系统依赖，但更新根证书需要 OTA 固件更新。

### 卡片 9：DTLS 抗重放（Anti-Replay）
- **一句话**：DTLS 通过记录序列号和位图窗口来检测和丢弃重复的握手/数据包。
- **软件类比**：类似 TCP 的序列号 + 窗口机制，但 DTLS 在应用层实现，且是"尽力而为"的抗重放——位图窗口只跟踪最近接收到的序列号范围。
- **常见场景**：UDP 通信需要加密的 IoT 场景（如 CoAP over DTLS）。
- **坑点**：位图窗口大小有限。如果一个恶意节点大量发送重复的旧包，可能导致窗口"翻转"，合法的新包被当作重放丢弃。

### 卡片 10：HMAC 与密钥派生（TLS PRF）
- **一句话**：TLS 使用伪随机函数（PRF）从预主密钥（pre-master secret）派生出会话加密密钥、MAC 密钥和 IV。
- **软件类比**：类似 KDF（密钥派生函数）在 OAuth2/OIDC 中从授权码派生出 access token 和 refresh token。
- **常见场景**：TLS 握手过程的一部分，计算 Finished 消息的验证值、加密记录层密钥。
- **坑点**：TLS 1.2 使用基于 SHA-256/SHA-384 的 PRF；TLS 1.3 改用 HKDF（HMAC-based Key Derivation Function）。两者完全兼容，但实现不同。如果硬件只加速特定哈希算法，TLS 版本升级可能导致性能显著变化。

## 9. 30～60 分钟动手任务

**目标**：在 Linux 环境下编译 Mbed TLS 最小配置版本，运行 TLS 客户端示例连接到 https://example.com。

**步骤**：
1. 克隆仓库并初始化子模块：
   ```bash
   git clone https://github.com/Mbed-TLS/mbedtls.git
   cd mbedtls
   git submodule update --init --recursive
   ```

## 10. 3 道深度追问题

### 问题 1（时序/并发）
在一个裸机（无 RTOS）系统上，Mbed TLS 的 `mbedtls_ssl_handshake()` 在需要网络 I/O 时返回 `WANT_READ`。你如何设计一个回调调度机制，使得握手过程在等待网络数据时不阻塞整个 CPU？你的方案如何处理多个并发的 TLS 连接？

### 问题 2（软件→嵌入式视角转换）
你习惯的 REST API 后端中，SSL 证书通常由 Nginx 或 ELB 管理，应用代码完全不关心证书解析和验证。现在你需要在 STM32F4（196KB SRAM）上实现一个 HTTPS 客户端。请回答：
- 你会选择 Mbed TLS 的哪种配置组合（TLS 1.2 vs 1.3、哪些密码套件、证书验证深度）？
- 你的选择依据是哪些具体的硬件资源限制？
- 在哪一个时间点你会意识到"后端思维"和"嵌入式思维"的差异最大？

### 问题 3（资源限制）
Mbed TLS 的会话恢复功能可以把握手后的状态序列化保存到 Flash。但 MCU Flash 的擦写寿命通常只有 1 万到 10 万次。如果设备每天与云服务器握手 100 次，每次握手都保存会话到 Flash，Flash 能坚持多久？你会如何设计一个兼顾安全性和 Flash 寿命的会话缓存策略？

## 12. 工程点评

**可维护性（8/10）**：代码采用 ANSI C99 标准，注释详尽，结构清晰。API 命名前后一致（`mbedtls_*` 前缀），但没有面向对象语言的接口隔离，大结构体容易成为"上帝对象"。

**可移植性（9/10）**：几乎所有平台相关代码都通过配置宏和硬件抽象层隔离。移植到新平台只需实现网络 I/O、时间/定时器和熵源三个接口。

**可靠性（7/10）**：错误码体系完善，每个公共函数都有详细的返回值文档。但 C 语言的手动内存管理意味着内存泄漏和悬空指针风险始终存在——`mbedtls_ssl_free` 和 `mbedtls_ssl_config_free` 的调用顺序一旦出错，可能导致资源泄漏。

**可测试性（8/10）**：项目自建了完善的测试框架，包含单元测试、SSL 互操作性测试和 fuzz 测试。测试数据文件覆盖了大量边界情况。但单元测试在低资源 MCU 上不能直接运行，需要交叉编译或模拟执行。

**量产/运维（6/10）**：编译时配置模式使得固件安全更新需要完整的 OTA 流程。生产环境中，根证书更新、密码套件淘汰、TLS 版本升级都需要固件更新，没有类似 Linux 包管理器的热升级机制。

## 13. 明天可以延展的方向

1. **Mbed TLS vs 其他嵌入式 TLS 库**：对比研究 wolfSSL（已在历史项目中）、BearSSL 和 Mbed TLS 的设计取舍——它们的配置系统、内存占用、API 设计有何不同？这种对比有助于深入理解嵌入式安全库的设计空间。

2. **TLS 1.3 协议实现深度**：深入阅读 `library/ssl_tls13_client.c`，理解 TLS 1.3 的 0-RTT 早期数据、PSK 预共享密钥和 1-RTT 握手在嵌入式实现上的挑战。特别是 0-RTT 的安全含义——为什么 0-RTT 数据天然存在重放攻击风险？Mbed TLS 是如何处理的？

3. **PSA Certified 与硬件安全**：研究 Arm Platform Security Architecture（PSA）认证体系，了解硬件安全模块（如 CryptoCell、TrustZone-M）如何与 Mbed TLS 的 PSA Crypto API 配合工作。这是从"纯软件安全"走向"软硬件协同安全"的关键一步。
