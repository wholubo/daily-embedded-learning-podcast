今天我们聊一个特别的小内核，叫 LK，全称是 Little Kernel，也就是"小内核"。听这个名字就知道，它不追求功能上的大而全，而是追求极致的简洁和高效。这个项目来自 Travis Geiselbrecht，这位工程师之前分别在 Google 和 Be Inc. 做过内核开发，所以 LK 的代码风格非常干净。而且它被广泛用在 Android 手机的启动加载器里，也就是说，你每天按电源键开机的那一瞬间，底层跑的就是 LK。

先说它解决的问题。LK 是一个 SMP 感知的嵌入式内核，能够管理多线程、多核、内存映射和硬件中断。在 Android 手机上，它的任务是在上电之后快速初始化硬件，检测启动模式，然后加载 Linux 内核。整个过程的可靠性和确定性要求极高，因为如果启动加载器坏了，手机也就变砖了。

为什么今天选 LK 而不是更常见的 FreeRTOS 或者 Zephyr 呢？因为 LK 不自称是 RTOS，它就叫 kernel。它没有文件系统、没有协议栈、没有设备驱动模型，它只做一件事：管理线程和内存。而且整个核心调度器的代码只有大约一千三百行 C。对于有软件工程背景、正在转向嵌入式的人来说，LK 是一个理想的第一课——你可以在这一个项目里看到抢占式内核的骨架，没有任何多余的东西遮住视线。

我们来看看它的架构。LK 的顶层分为几个目录：arch 目录放不同 CPU 架构的代码，包括 ARM、ARM64、RISC-V、x86、MIPS，甚至还有 VAX；kernel 目录是内核核心，包括线程管理、互斥锁、信号量、事件、定时器和多核支持；platform 目录是不同硬件平台的初始化代码；target 目录是具体的开发板配置；app 目录是应用和测试程序。

运行流程大概是这样的：芯片上电后，先从 start.S 汇编代码开始执行，设置栈指针、清零 BSS 段、建立 MMU 初始映射，然后跳转到 C 代码的 lk_main 函数。lk_main 会依次初始化平台、堆内存、线程系统、定时器和多核支持。最后创建空闲线程，调度器开始运行，系统进入多线程模式。

说到线程管理，我们看看它的调度器设计。LK 使用了一个非常经典的技术，叫做位图调度。调度器维护了一个三十二位的无符号整数，叫 run_queue_bitmap，每一位代表一个优先级是否就绪线程。当需要选择下一个运行的线程时，它调用 __builtin_clz 这条编译器内建函数，对应的底层指令是 ARM 的 CLZ 或者 x86 的 BSR，可以在一个 CPU 时钟周期内找到最高优先级的就绪线程。这是一个真正的 O(1) 调度算法，不管有多少个线程，选择下一个线程的时间都是恒定的。

它的同步原语也很有意思。LK 的互斥锁、信号量和事件全部构建在一个叫做 wait_queue 的等待队列机制之上。wait_queue 维护了一个阻塞线程的链表，支持超时唤醒。当你调用 mutex_acquire 获取锁时，如果锁已经被其他线程持有，当前线程就被放到等待队列里，状态变为 BLOCKED，然后调度器选下一个线程运行。当持有锁的线程调用 mutex_release 释放锁时，它从等待队列头部取出一个线程，放回运行队列。整个过程是协作的、高效的，而且没有自旋等待浪费 CPU。

在内存管理方面，LK 的 boot 阶段使用了一个叫 bump allocator 的分配器，它只有两个指针变量。一开始两个指针都指向内核代码末尾的 _end 符号，分配内存时就把 end 指针往前推，不做释放，不清零，极其简单。等 VMM 初始化完成之后，LK 切换到基于页的物理内存管理器，每四个 KB 为一页，每个页对应一个 vm_page 结构体，记录分配状态。pmm_add_arena 函数把一块物理内存注册为 arena，然后所有页都链入空闲链表，供 VMM 按需分配。

对于有软件工程基础的人，有几个关键的思维转换点。第一个是线程控制块的概念。LK 的 thread_t 结构体只有几十个字节，相当于 Linux task_struct 的最小可运行子集。它包含栈指针、优先级、状态和线程本地存储，但没有信号处理、没有 cgroup、没有命名空间。所有线程共享同一个地址空间，一个空指针解引用就能干掉整个系统。这种"没有进程隔离"的安全感缺失，是软件工程师转向嵌入式时感受到的最大差异。

第二个是中断上下文。LK 明确规定同步原语不能在中断上下文中使用。你在中断里写了一个 mutex_acquire，轻则死锁，重则破坏调度器状态。在 Linux 里你习惯了在后台线程里随便加锁，但在嵌入式中断处理程序里，能做的事情非常有限，通常是设置一个标志位、发一个信号、或者向一个队列里丢一个事件，然后尽快退出。

第三个是上下文切换的成本。从一个线程切换到另一个线程，需要保存和恢复 CPU 寄存器，这部分时间在微秒级别。如果切换太频繁，比如每毫秒切换一次，上下文切换的开销可能占到 CPU 的百分之十以上。在软件工程里我们不太关注"调度开销"这个概念，但在嵌入式系统里它直接决定了你能跑多少个线程、响应有多快。

说到 SMP 支持，LK 在多个核心上运行时，当一个 CPU 上出现了更高优先级的就绪线程，LK 通过发送 IPI 通知其他 CPU 重新调度。IPI 是硬件级别的核间中断，延时在微秒级。IPI 到达时会打断另一个 CPU 当前正在执行的中断处理程序，所以 IPI 回调本身也运行在中断上下文中，又回到了同一个约束——不能在里面加锁。

我们今天推荐的源码陪读清单有五份文件。按顺序看。第一份是 kernel 目录下的 thread.c，一千三百行，理解整个调度器的全部实现。重点看 insert_in_run_queue_head、find_top_thread 和 thread_resched 这三个函数。第二份是 kernel 目录下的 mutex.c，看最简洁的互斥锁实现。第三份是 kernel 目录下的 timer.c，看定时器如何驱动时间片抢占。第四份是 kernel 下的 vm 目录里的 vm.c，看物理内存管理和 boot allocator。第五份是 arch 目录下对应架构的 start.S 启动代码，看嵌入式系统上电后第一条指令到 C 环境建立的全过程。

动手任务方面，你可以克隆 LK 仓库，获取 RISC-V 工具链，编译 qemu-virt-riscv64-test 项目，然后在 QEMU 里运行它。进入 LK 的 shell 后，试试 help、threads、test_clock 这些命令。再试着在 app 目录下添加一个自定义的 shell 命令，让它打印一条消息后睡眠一秒再打印另一条消息。全部在模拟器里完成，不需要任何真实硬件。

最后留三道深度追问题。第一道关于调度器时序：find_top_thread 使用了 __builtin_clz，但如果 run_queue_bitmap 为零，也就是没有任何就绪线程时，这个函数的行为在不同架构上可能是未定义的。LK 怎么防御这种情况？你在移植到新架构时怎么处理？第二道从软件工程视角转嵌入式：你在微服务里加一个新功能是创建 HTTP 端点然后动态注册到路由表。为什么嵌入式内核里不能用同样的动态注册方式添加命令？从二进制体积、启动时间和内存分配阶段三个角度给出理由。第三道关于资源竞争：在 SMP 系统中两个 CPU 同时调用 thread_create 时，LK 用哪把锁保护线程链表和运行队列的并发访问？这把锁可以在中断上下文中获取吗？如果产生递归自旋会发生什么？

今天的复盘问题是这样：你从软件工程转向嵌入式工程的视角中，感受最强烈的一个认知冲突是什么？是没有进程隔离的不安全不适感，还是中断上下文不能加锁的约束感？试着用一句话描述这个冲突，然后想想你在日常工作中做的哪些假设，在嵌入式世界里完全不成立。
