# 每日嵌入式学习：Flipper Zero Firmware

## 1. GitHub 项目链接与一句话介绍
- **GitHub 仓库**：https://github.com/flipperdevices/flipperzero-firmware
- **一句话介绍**：这是一款面向开源硬件"海豚"Flipper Zero 的完整量产固件，把一颗 STM32WB55 双核微控制器变成能玩转 Sub-GHz 射频、NFC、红外、低频 RFID、USB 与蓝牙的多功能手持工具，并靠"插件化应用"机制让社区像装 App 一样扩展功能。

## 2. 为什么今天选它
- **活跃度**：dev 分支几乎每天都有提交，抓取资料当天（2026-08-03）仍有新提交，近期提交密集（7 月底连续多日）；GitHub 约 1.6 万 star，社区生态庞大，issue/discussion/PR 都在滚动。
- **工程完整度**：这不是 demo 或教学内核，而是一套真正量产出货的消费电子产品固件：自带构建系统（fbt）、CI、PVS-Studio 静态分析、单元测试、独立升级程序（updater）、双核协处理器管理、文件系统、GUI、蓝牙、USB CLI/RPC、资源（图标/动画/协议文件）自动生成流程，工程闭环非常完整。
- **学习价值**：对从纯软件转嵌入式的人，它是"完整产品固件"的最佳样本——你能在一套代码里同时看到线程原语、事件循环、发布订阅、消息队列、内存管理、崩溃处理、服务注册表、动态加载器、ABI 版本管理这些平时分散在各个项目里的东西是如何被组织成一个真实产品的。

## 3. 项目解决的问题
- **真实场景**：Flipper Zero 是一个口袋大小的多功能工具，替代一大堆专用设备：射频门禁测试、NFC 卡片模拟与读取、红外遥控、125kHz 低频钥匙、USB HID 键盘注入、蓝牙、GPIO 调试等。固件把这些硬件能力统一成一个可交互的图形界面系统，并允许第三方应用（FAP）按需加载。
- **和普通软件项目相比多出的约束**：
  - 资源：主控 STM32WB55 系列，1MB Flash、256KB SRAM（基于公开资料），所有内存要精打细算，栈大小要在 manifest 里逐个应用手动声明；
  - 双核：M4 主核跑固件与 UI，M0 协核单独跑蓝牙协议栈（固件里叫 Core2/FUS），跨核通信有固定开销；
  - 时序：Sub-GHz/NFC/红外都是对时序极其敏感的协议，中断与任务优先级直接决定功能是否可用；
  - 可靠性：电池供电、可能随时拔 SD 卡、可能升级到一半断电，固件必须能自救（恢复模式、升级失败回退）；
  - 外设多样性：屏幕、键盘、LED、震动马达、多个射频前端、USB、SD 卡同时工作，驱动与电源管理要协调。

## 4. 技术架构分析
- **顶层目录**（来自 README 原文）：`applications` 放应用与服务，`furi` 是 Furi Core——OS 级原语和辅助库，`lib` 放自研与第三方库，`targets` 是硬件平台相关代码（f7=Flipper Zero，f18 不是 Zero），`assets` 是图标/动画/协议资源，`site_scons` 是构建系统配置，`scripts` 是辅助脚本，`documentation` 是文档。这个分层和大型后端仓库的"内核/服务/应用/配置"划分几乎一一对应。
- **Furi Core**：自己实现的一套 OS 原语，包括线程（furi_thread）、事件循环（furi_event_loop）、记录注册表（furi_record）、消息队列、内存管理（memmgr）、检查与崩溃处理（check.h）。它把 RTOS 能力和自研抽象混在一起，对外提供统一 API。
- **服务层**：storage（存储）、gui（图形）、input（输入）、notification（通知/震动/灯）、power（电源）、bt（蓝牙）、cli（命令行）、loader（应用加载器）、rpc（远程调用）、desktop（桌面）、dolphin（养成系统）等后台服务，以"记录（record）"形式注册，供应用打开使用。
- **应用层**：main 菜单里的常规应用（subghz、nfc、infrared、lfrfid、ibutton、bad_usb、gpio、archive、u2f），settings 配置应用，system 里不显示在菜单的工具（updater、snake_game、js_app），以及 EXTERNAL 类型编译成 .fap 的插件应用。
- **启动与运行流程**（基于公开文档与代码推断）：复位后先做芯片与 HAL 初始化，furi 初始化记录系统，各服务按 manifest 中的 order 依次启动并把自己注册成 record，loader 负责拉起桌面与菜单，应用通过 record 拿到服务指针后运行；应用也可以从 SD 卡以 FAP 形式被 loader 动态加载。
- **构建系统 fbt**：本质是 SCons 的封装，自动下载预编译工具链、自动 git submodule 同步、生成 compile_commands.json 供 IDE 用、提供 fw_dist/fap_dist/flash/debug/lint/format/doxygen 等目标；应用清单 application.fam 用 Python 描述每个组件的依赖、栈大小、类型，构建时 fbt 解析依赖图只构建需要的组件。
- **插件体系 FAP**：FAP 本质是带元数据的 .elf。因为 MCU 不能从 SD 卡直接执行代码，loader 需要把 FAP 拷进 RAM、做重定位、用符号表解析导入符号，再启动；API 兼容性靠 api_symbols.csv 白名单和语义化版本控制，构建期强制人工确认每个 API 符号的增删。

## 5. 源码陪读：今天只读哪几个文件
1. `furi/core/thread.h` + `thread.c`——线程原语。阅读目标：理解在 MCU 上"线程"就是"一个入口函数 + 一块固定大小的栈 + 调度器登记"，看线程创建、栈分配、优先级、退出清理的完整生命周期。
2. `furi/core/event_loop.h`——事件循环。阅读目标：看它如何把 IO、定时器、消息统一成回调注册，理解裸机/RTOS 上事件驱动与后端事件循环的异同。
3. `furi/core/record.h`——记录注册表。阅读目标：只读这个头文件就能理解整个固件的"服务发现"机制：create/open/close/exists/destroy 五个函数就是全部。
4. `applications/services/storage/storage.c`——一个完整服务长什么样。阅读目标：看服务如何用消息队列接收请求、如何用 pubsub 通知、如何通过 record 使用 gui 服务画 SD 卡状态栏图标。
5. `applications/system/snake_game/snake_game.c`——最小完整应用。阅读目标：看一个应用如何同时拿 input、gui、notification 三个服务，输入怎么进状态机，画面怎么渲染。
- **阅读顺序**：thread → event_loop → record → storage → snake_game，从原语到服务到应用，正好复现一条"从零搭一个 App"的路径。

## 6. 核心模块/函数导读
- **furi_check / furi_assert / furi_crash（furi/core/check.h）**：断言与崩溃处理。设计亮点是崩溃时通过 r12 寄存器传递错误消息、把 r0-r10 保存到 ram2 再重启，重启后显示错误信息——这是嵌入式世界的"崩溃转储"。注意区别：furi_assert 只在 DEBUG 构建生效，furi_check 永远生效，关键检查必须用 check。
- **furi_record_create / open / close（record.h）**：服务注册表。所有服务用字符串名字注册，应用 open 拿指针、close 释放，成对使用；这和依赖注入容器是同一种思想，但实现只有几十行、运行期零动态分配。
- **storage 服务（storage.c）**：内部存储 + SD 卡双后端，用固定深度（8 条）消息队列接收请求，SD 卡状态机（未就绪/正常/错误）驱动状态栏图标更新，还带 pubsub 让其他模块订阅文件系统事件。
- **loader 服务 + FAP 加载**：从 SD 卡读 .elf → 校验 API 主版本 → 分配 RAM → 拷贝代码段数据段 → 处理重定位 → 用符号表解析导入符号 → 启动。这是"动态链接器"在无 MMU 的 MCU 上的实现，也是整个项目最值得精读的机制。
- **fbt 与 api_symbols.csv**：构建期自动比对头文件与符号表，发现 API 变化就停下构建，要求人工把每个新符号标成"+"（对外暴露）或"-"（不暴露），主版本号据此递增——把"语义化版本"从约定变成了构建期强制检查。

## 7. 软件工程师类比解释
- **record 服务注册表 ≈ 服务发现 / 依赖注入容器**（类似 Spring 容器或 Consul）。区别在于：没有网络、没有动态注册，依赖关系在编译期由 manifest 决定，运行期只是查一张哈希表。这个类比的局限：MCU 上不存在"运行时热替换服务实现"，解耦主要发生在编译期与代码组织层面，而不是运行期。
- **FAP 插件加载器 ≈ 浏览器插件系统 / dlopen 动态链接库**。区别在于：没有 MMU，代码必须拷进 RAM 并重定位，加载后可用堆变小；API 可用性由构建期生成的符号白名单决定，而不是运行期动态解析。这个类比的局限：不能像 dlopen 那样"加载失败就算了"，加载器失败可能直接导致系统内存紧张甚至崩溃，且插件与固件的版本耦合需要白名单机制硬性管理。
- **furi 事件循环 ≈ Node.js 事件循环 / 前端事件总线**。区别在于：单线程、无 GC，回调里不能做长阻塞操作，所有耗时操作要么拆成状态机要么交给专用线程。这个类比的局限：后端事件循环回调阻塞几毫秒无所谓，MCU 上可能直接导致射频协议超时或 UI 掉帧，时序预算完全不是一个量级。
- **check/crash 机制 ≈ 服务端 panic + 崩溃转储**。区别在于：没有 coredump 服务、没有日志采集管道，只能把寄存器存进预留 RAM、重启后显示一行错误消息。这个类比的局限：嵌入式现场信息极稀缺，所以断言消息本身就要求自带上下文；release 构建里 assert 会被编译掉，不能指望它兜底。
- **fbt 构建系统 ≈ Make/CMake/Gradle + CI 流水线**。区别在于：要为具体 MCU 管理工具链、链接脚本、启动文件、Flash 布局，构建产物是二进制镜像而不是可执行文件，还要顺带生成图标/协议/资源 C 数组。这个类比的局限：没有"服务器上随便跑"的余地，工具链版本、编译选项、优化级别都会真实影响设备行为，构建环境漂移是事故高发源。
- **存储分层（内部 Flash + SD 卡）≈ 本地数据库 + 对象存储的分层**。区别在于：Flash 有擦写寿命和磨损均衡问题，掉电可能损坏文件系统，需要专门的恢复设计。这个类比的局限：没有事务管理器帮你兜底，文件系统层面的原子性要靠应用自己设计。

## 8. 今日 10 个嵌入式概念卡片
1. **线程栈分配**：MCU 上每个线程的栈是编译/运行期固定分配的一块内存，大小要在 manifest 里声明。软件类比：线程池里固定大小的任务槽。常见场景：应用启动时按 stack_size 参数分配。坑：栈开小了溢出会静默踩坏相邻内存，开大了又挤压堆；只能用 CLI 的 top/free 实测调优。
2. **事件循环**：把 IO、定时器、消息统一成回调注册与派发。软件类比：Node.js 事件循环。常见场景：furi_event_loop 驱动应用主逻辑。坑：回调里绝不能长阻塞，否则定时器和射频采样全部超时。
3. **服务注册表（record）**：服务用字符串名字注册、按名字获取。软件类比：依赖注入容器。常见场景：应用 open RECORD_GUI/RECORD_STORAGE 拿服务。坑：open/close 必须成对，忘记 close 会泄漏引用计数，可能导致服务无法销毁。
4. **消息队列**：线程间传消息的固定深度缓冲区。软件类比：Kafka/RabbitMQ 的队列。常见场景：storage 服务用 8 条深度的队列接收请求。坑：队列满了要么阻塞要么丢弃，MCU 上"背压"是设计决策而不是异常。
5. **双核协处理器**：M4 主核跑应用，M0 核跑蓝牙协议栈。软件类比：把网络栈拆成独立微服务。常见场景：BLE 相关功能全走协核。坑：跨核通信有固定延迟与共享内存竞争，不能当普通函数调用。
6. **FAP 动态加载**：从 SD 卡加载 .elf 到 RAM 执行。软件类比：浏览器插件。常见场景：社区应用分发。坑：无 MMU 需重定位，加载后堆变小；API 只能从白名单取，版本不匹配直接拒绝加载。
7. **断言与崩溃处理**：check/assert 失败时保存现场并重启。软件类比：panic + 崩溃转储。常见场景：非法参数、状态机非法迁移。坑：assert 在 release 被编译掉，关键路径必须用 check。
8. **功耗管理**：按需开关外设时钟与射频。软件类比：云成本优化/缩容。常见场景：屏幕超时关背光、射频空闲关模块。坑：省电与唤醒延迟、功能可用性是三角权衡，每个外设都要单独考虑。
9. **Flash 擦写寿命**：Flash 有擦写次数上限，需要磨损均衡。软件类比：SSD 的磨损均衡。常见场景：配置持久化、日志落盘。坑：频繁写同一地址会提前报废，掉电可能损坏文件系统元数据。
10. **升级与恢复**：独立 updater 应用负责 OTA，失败可进恢复模式。软件类比：蓝绿发布/回滚。常见场景：USB 或 SD 卡刷机。坑：没有远程回滚面板，恢复靠硬件按键组合（KeyCombo），升级流程必须把"失败自救"设计进去。

## 10. 3 道深度追问题
1. **（时序/并发）** storage 服务用固定深度（8 条）消息队列接收请求。如果 SD 卡写入变慢导致队列打满，发送方会怎样？这种"背压"设计在 MCU 上为什么比"无限队列"更合理？如果改成阻塞式同步调用，又会引入什么样的死锁风险（提示：考虑中断上下文与多个服务互相等待）？
2. **（软件视角转嵌入式视角）** 你在后端会用服务发现 + 动态注入来解耦模块；Flipper 用 record 注册表 + 编译期 manifest 依赖。请从故障隔离、调试难度、启动顺序、资源开销四个维度对比两种方案，并说明为什么 MCU 上"静态优先"是理性选择而不是保守。
3. **（资源限制）** FAP 加载进 RAM 后堆空间变小，且只能调用 api_symbols.csv 白名单里的 API。假设你要给 Flipper 写一个需要频繁分配大缓冲的插件（比如波形采集），你会如何设计内存策略？manifest 里的 stack_size 参数设多少、怎么实测验证（提示：文档提到可用 top/free CLI）？

## 12. 工程点评
- **可维护性**：目录分层清晰（furi/applications/lib/targets），文档完善（fbt/FAP/AppManifests 都有专项文档），有 CODING_STYLE、clang-format、CI，还接入了 PVS-Studio 静态分析——规范程度接近大型后端团队。
- **可移植性**：targets 抽象（f7/f18）+ furi_hal_include 统一 HAL 头文件，硬件差异被隔离在 targets 目录；同一套应用代码可跨目标构建，这是嵌入式里难得的可移植性设计。
- **可靠性**：check/assert 分层、升级与恢复机制（KeyCombo）、SD 卡状态机、pubsub 解耦，量产品该有的失败路径基本都覆盖了。
- **可测试性**：内置 unit_tests 应用（`./fbt FIRMWARE_APP_SET=unit_tests` 即可构建含测试的固件），debug 目录有大量硬件测试应用，FAP 有 gdb 调试脚本——测试意识在固件项目里属于第一梯队。
- **量产/运维**：OTA（updater + DFU）、qFlipper 桌面工具、API 版本白名单机制保证旧插件在固件升级后仍可用，这是"软件产品的运维思维"在固件上的体现。
- **短板**：单仓库体量巨大、依赖大量 submodule，新手 clone 和首构建成本高；部分核心机制（如 FAP 重定位、双核 IPC）文档偏少，主要靠读源码；资源文件进构建生成 C 数组的流程对纯软件背景的人比较陌生。
